## 1. 영상 (O_zcc6Xl12g)

**확인한 사실** [확인: YouTube oEmbed·페이지 메타데이터]
- 제목: All Code Is Slop (Except Mine) — Lauren Tan, SpaceXSI
- 채널: AI Engineer(@aiDotEngineer). 게시: 2026-11-14. 길이: 17분 31초(1,051초).
- 설명란: 한 달 PR 1만 1천 건, 되돌림률 약 0.5%. Grok Bot 팀이 아키텍처, 린트 규칙, 자동 테스트, 런타임 검증, TLA+·Lean 형식 검증으로 코딩 에이전트를 확장하는 방법. Cursor 에이전트와 pstack으로 이 기반을 '믿을 수 있는 소프트웨어 공장'으로 바꾼다.
- 챕터: 슬롭을 금으로 / 신뢰 피라미드와 코드베이스 품질 / Dune과 강제 가능한 아키텍처 / 주석을 린트 규칙으로 / 런타임 검증과 기능 지도 / 형식 검증과 UI 테스트 / 토큰을 검증에 쓰기 / PR 1만 1천 건·되돌림 0.5% / 소프트웨어 공장보다 기반 먼저

**직접 보지 못함**: 자막 파일은 내려받지 못했다(자막 API가 빈 응답, 다운로드 도구는 권한 거부). 아래 내용은 설명란·챕터와 2차 요약 3곳(aiengineerguide, webreactiva, youtubesummary)을 서로 대조한 것이다. 세 곳이 일치하는 내용만 적었고, 한 곳에만 나온 숫자는 [2차]로 표시했다.

**핵심 주장**
1. **코드 품질은 누가 썼느냐가 아니라 에이전트가 일하는 환경이 정한다.** 사람이 안 보고 있어도 결과를 믿을 수 있게 환경에 검증을 심는 것이 목표다.
2. **신뢰 피라미드**(싼 것 → 비싼 것): 코드베이스(아키텍처·API 설계) → 정적 분석(타입·린트·테스트·CI) → 검증(런타임·형식) → 산문(규칙 문서·스킬·AGENTS.md) → 사람 리뷰. 아래 두 층은 결정론적이고 산문은 거의 맨 위다. 실수할 때마다 AGENTS.md에 한 줄 더하는 습관과 정반대 순서다.
3. **코드베이스는 정원이다.** 에이전트는 읽은 패턴을 베낀다. 땜질·안티패턴·폐기 코드는 잡초처럼 번진다. 한 저장소는 코드베이스를 에이전트의 가장 큰 입력으로 요약한다: "Your codebase is the agent's largest input" ([aiengineerguide](https://aiengineerguide.com/til/all-code-is-slop-except-mine-by-lauren-tan/)).
4. **판단(뉘앙스)이 필요한 것은 결국 슬롭이 된다 → 범주째 금지.** 자체 프레임워크 Dune에서 제품 코드의 `useEffect`를 금지했다(프레임워크 지정 API 안에서만 허용). Electron `main`·`renderer`를 최상위 디렉터리로 나누고 서로 import를 의존성 분석·린트로 막았다. '디렉터리 구조가 곧 맥락'이다.
5. **주석을 린트 규칙으로 바꾼다.** 에이전트는 주석으로 지름길을 정당화한다. Cursor에서는 이유를 단 `setTimeout` 땜질이 복제되어 타이머가 183개가 됐다. Grok Bot은 주석을 거의 금지했고(2차 요약 기준 65,824개 → 1,227개), 대신 **고칠 방법을 말해 주는 린트 오류 메시지**를 쓴다. [숫자는 2차]
6. **런타임 검증**: 에이전트가 앱을 직접 실행하고 조작한다(Chrome DevTools Protocol 등). 이를 받치는 두 장치는 **기능 지도**(사용자 관점의 기능 목록, 사람과 에이전트의 공용 어휘)와 **스킬 안의 전용 CLI**(같은 방식으로 반복 검증, 토큰 절약)다.
7. **형식 검증·속성 기반 UI 테스트**: TLA+로 여러 기기 알림 흐름을 모델 체크하고, Lean으로 목록 가상화 알고리즘의 깜빡임 없음을 증명했다. Antithesis의 Bombadil로 '항상 참이어야 할 속성'을 정하고 UI를 탐색하게 했다. 본인도 만능은 아니고 한 층을 더하는 것이라고 말한다.
8. **토큰 대부분을 검증에 쓴다.** 인용 사례는 하루 토큰의 약 70%가 패치 검증, 20~30%가 생성이다. 기법 자체는 오래됐지만 에이전트 덕분에 싸졌다. [2차]
9. **결과**: 월 PR 약 1만 1천 건, 되돌림 약 0.5%, 하루 한 번 안정 버전. 콜드 스타트 개선과 함께 퇴행(유휴 메모리·시작 번들 증가)도 공개했다. [설명란 확인 / 세부는 2차]
10. **공장보다 기반 먼저.** 안쪽 루프가 슬롭을 내면 그 루프의 자동화는 슬롭을 더 낼 뿐이다. 순서: 에이전트를 교정할 때 코드베이스를 고친다 → 새 발생을 막는 린트 → 옛 발생 정리 → 검증 단단히 → 그다음에 바깥 루프(릴리스마다 앱을 퍼징해 버그마다 PR·자동 머지).

- 공개 활동: AI Engineer 강연(2026-11), X에 올린 pstack 가이드 Part 1·2(2026-09, "2,500 PR" 글), Lightcone 팟캐스트 'From Software Factories to Everything Factories'(Roman Ugarte와 함께, 2026-11) [2차], 오픈소스 pstack(MIT). 개인 블로그는 프로필에 없다.
- 월 PR 수는 출처마다 2,000·2,500·3,000·4,000으로 다르다. 본인도 숫자가 목표는 아니었다고 했다. 숫자는 인용하지 말고 방향만 쓴다. [2차]

**반복되는 철학** (강연·pstack README·X 가이드·대담 요약에서 두 번 이상 나온 것만)
1. **신뢰가 먼저, 병렬은 그다음.** 처음엔 대화 1~5개만 감독할 수 있다. 그 단계에서 에이전트 100개를 띄우면 회귀가 쌓인 PR이 쏟아진다. 한 에이전트가 검증 가능한 좋은 코드를 쓴다고 믿을 수 있을 때 병렬로 넓힌다. 매니저가 새 팀원을 믿어 가는 과정에 비유한다.
2. **교정은 가장 강한 층에서.** 같은 지적이 반복되면 코드 스멜이다. 채팅에서만 고치면 다음 세션에 다시 나온다. 아키텍처·타입·린트·CI로 옮기고, 산문 규칙은 마지막이다. pstack 원칙의 '메타' 항목도 규칙을 글 대신 린트·검사·스크립트로 강제하라는 것이다.
3. **가장 짧은 길이 정답 길이 되게 설계한다.** 에이전트는 지름길을 좋아하므로 지름길을 막고 올바른 길 하나만 열어 둔다.
4. **'됐을 것'이 아니라 증거.** 에이전트가 실제 제품을 조작해 성공을 증명해야 완료다(스크린샷·영상·트레이스·힙 스냅숏). 리뷰는 코드 읽기에서 검증 산출물 확인으로 옮겨 간다.
5. **계획보다 코드, 프로토타입은 '코드로 하는 계획'.** 계획 모드를 쓰지 않는다고 말한다: "I don't believe in planning." ([The Neuron](https://www.theneuron.ai/explainer-articles/pstack-explained-lauren-tans-system-for-trustworthy-ai-agents/)). 단, 계획을 버리라는 게 아니라 **계획이 현실과 최대한 빨리 부딪혀야** 한다는 뜻이다. 설계안 2~3개를 경쟁시키고(`/arena`), 구현 중 타입 우회 같은 증상이 보이면 설계를 버리고 다시 한다.
6. **덜 쓰고 더 잘 쓴다.** pstack README는 처리량보다 품질, '빨리 가려면 먼저 깊이' 입장이다. 핵심 원칙 첫째가 삭제·최소 변경이고, 죽은 코드 먼저 제거, 중간 호환 코드 없이 목표 구조로 수렴, 호출자 옮긴 뒤 옛 API 삭제가 이어진다.
7. **맥락 정리는 사람의 일.** 버그 제보를 코드 만지기 전에 에이전트가 **자기 말로 다시 서술**하게 한다(`/in-your-own-words`). 오해를 일찍 잡고, 사람의 가설이 모델을 엉뚱한 방향에 고정하는 것도 막는다. `/why`(커밋·PR 기록에서 설계 이유 찾기), `/how`(동작 설명)를 쓴다.
8. **기능 지도는 '물질화된 기억'.** 짧은 기능 목록을 두고 최소 하루 한 번 실제 제품과 맞춘다.
9. **반복 일은 레버(도구)로 만든다.** 반복 검증은 에이전트가 부를 수 있는 CLI로 만든다. `/reflect`(작업 뒤 교훈을 스킬에 반영), `/correct`(반복 실수를 가장 위 층에서 막기).
10. **사람을 막지 말고 진행한 뒤 보여 준다. 되돌릴 수 없는 일만 확인받는다.** (pstack '위임' 원칙)
11. **자동화 범위**: 유지보수·성능·버그 수정은 공장에 맡기고, 사용자가 겪는 경험과 기능 결정은 사람이 맡는다. [2차: teamday, Lightcone 요약]
12. **평가는 에이전트의 단위 테스트.** 루브릭으로 점수를 매기고, 다른 모델을 심판으로 써서 편향을 교차 확인한다. [2차: SozAI 대담 자막]

**본인이 밝힌 한계** — 토큰이 거의 무제한인 AI 연구소 소속이라 이 방식을 모두에게 그대로 권할 수는 없다고 인정했다 [2차: SozAI]. 외부 실험에서도 pstack 방식은 기본 방식보다 시간이 약 2배, 토큰도 더 들었다. 대신 에이전트가 스스로 지어낸 거짓 주장 3건을 잡았다. 결론: **오류 비용이 큰 작업에만 검증 연산을 더 쓴다** [2차: The Neuron].

## 3. SpaceXSI (Grok Bot 팀)

**누구인가** — SpaceX의 AI 조직(옛 xAI·SpaceXAI). X 계정 @SpaceXSI, 팔로워 약 207만 명 [2차]. Grok Bot을 만든다. Grok Bot은 2026-08-11 베타 출시된 'AI 팀원' 제품으로, 봇마다 자기 컴퓨터를 갖고 사용자가 쓰는 도구 안에서 24시간 일하며, 승인이 필요할 때만 사람에게 돌아온다 [확인: x.ai 공식 글]. Grok Bot 개발은 Cursor 초기 멤버 Roman Ugarte가 이끌었고 poteto가 핵심 엔지니어다 [2차].

**반복되는 조언** (x.ai 공식 글과 Roman Ugarte 대담 요약)
1. **'과제'가 아니라 '업무(job)'를 맡긴다.** AI가 요청 하나를 돕는 데서 그치지 않고 워크플로 전체를 결과까지 책임진다. 누구의 책임도 아니던 반복 업무부터 맡긴다. [확인: x.ai IncidentSweep 글]
2. **빠르되 통제한다.** 자동화하되 발송 전에 사람이 묶음과 메시지를 승인한다. 승인 뒤에는 대상을 바꾸지 않고, 작은 묶음으로 보내며, 모든 작업을 기록한다. 실패하면 즉시 멈추고 보고한다. 결과: 장애 관련 문의 204건을 승인 거쳐 약 10분에 처리. [확인]
3. **고객 문의는 조기 경보다.** 내부 알림보다 문의 급증이 먼저 문제를 드러낸다. 5분마다 최근 15분 티켓을 보고 알려진 장애와 다른 패턴이면 당직에게 알린다. [확인]
4. **작은 팀이 틀어박혀 매일 결정한다.** 큰 집단 결정을 피하고 소수가 한 달 집중했다. 기존 제품에 끼우지 않고 따로 만들어 UX를 일관되게 통제했다. [2차: Lenny's Podcast 요약]
5. **덜어내기(unlaunch).** 핵심 가치가 분명하지 않은 기능은 계속 뺀다. [2차]
6. **첫 사용자를 직접 붙잡고 본다.** 얼리 유저 200~300명을 2주간 직접 온보딩했고, 비개발자(커피숍 주인)가 쓰는 모습에서 팀의 맹점을 찾았다. 사용자가 다른 봇을 관리하는 'chief of staff' 봇을 스스로 만든 것도 관찰로 알았다. [2차]
7. **봇은 '컴퓨터를 가진 동료'.** 사용자 기기를 빌려 쓰지 않고 봇마다 자기 환경을 준다: "colleague with a computer" ([Summify, Lenny's Podcast 요약](https://summify.io/discover/how-we-built-grok-bot-in-a-month-roman-ugarte-spacexai-maSdsT)).

## 4. 공통 원칙과 각자의 고유한 조언

**세 출처의 공통 원칙**
1. **신뢰는 쌓는 것이다.** 감독 → 증거 → 자동화 → 병렬·자동 머지 순서다. 단계를 건너뛰면 속도가 아니라 슬롭이 늘어난다.
2. **규칙은 글보다 구조로.** 아키텍처·타입·린트·CI·승인 절차처럼 어길 수 없는 형태에 둔다.
3. **완료는 증거로.** 실제로 돌려 본 산출물(캡처·영상·로그·승인 기록)이 있어야 끝이다.
4. **사람은 방향과 사용자 경험을, 기계는 반복과 유지보수를.**
5. **작게, 덜어내며, 빨리 현실에 부딪힌다.**

**각자의 고유한 조언**
- 영상: 신뢰 피라미드(고칠 위치의 우선순위), 주석 금지·린트 오류 메시지가 고칠 방법을 말하게, 토큰 대부분을 검증에, 공장보다 기반 먼저.
- Lauren Tan: 자기 말로 다시 서술, 기능 지도, 프로토타입 경쟁(arena), 레버 만들기, 되돌릴 수 없는 일만 확인받기, 평가는 단위 테스트처럼.
- SpaceXSI: 업무 단위 위임, 승인 → 작은 묶음 → 실패 시 멈춤, 고객 문의를 경보로, 덜어내기, 첫 사용자 직접 관찰.

## 5. 몽망이 팀에 적용할 것

현재 상황(근거): 오너 1인 + AI 에이전트 역할 팀(OPERATING 1절). D-22로 범위를 줄이지 않고 체크리스트를 쉬지 않고 수행하며(매시간 점검), 출시는 관문 통과 즉시. D-19 세 기둥(자유도·자랑·감정 교류)이 모든 기능의 기준이다. 저장소 관찰(11-20): 모바일에는 ESLint 설정과 CI가 없다(CI는 `server-ci.yml`만). 리뷰는 `docs/team/reviews/`에 16건이 문서로 쌓였다. 화면 캡처 스크립트는 `scripts/*-capture.mjs` 9개로 흩어져 있다. 구조적 검사의 좋은 선례로 `apps/mobile/test/i18n-static.test.ts`(영어 하드코딩 차단)가 있다. `apps/mobile/src`에 `useEffect` 28곳, `setTimeout` 29곳이 있다(grep 개수, 잘못 썼다는 뜻은 아님).

### 적용안 1 — 리뷰 지적을 '검사'로 승격한다 (최우선)
- 원칙: 교정은 가장 강한 층에서. 같은 지적이 두 번 나오면 구조로 옮긴다.
- 지금과의 차이: 리뷰 지적은 리뷰 문서와 DECISIONS 줄(산문)로 남는다. 다음 세션의 에이전트가 그 문서를 읽지 않으면 같은 실수가 반복된다. i18n 정적 검사만 예외적으로 구조화됐다.
- 바꿀 것:
  - 리뷰 문서 양식에 **'재발 방지 층' 열**을 둔다. 값은 `타입 / 린트 / 테스트 / API·구조 / 산문 / 일회성`. 산문이나 일회성을 고르면 이유를 한 줄로 쓴다.
  - 같은 지적이 두 번째 나오면 그 작업의 완료 조건에 '검사 추가'를 넣는다.
  - 모바일에 `expo lint`(ESLint)를 켜고, 아래 경계를 `no-restricted-imports`로 막는다. 오류 메시지는 고칠 방법을 쓴다.
    - `packages/core` → `react-native`·`expo-*`·`apps/*` import 금지(시뮬레이션 코어 순수성. 7일 시간 가속 테스트의 전제)
    - `apps/mobile` → `apps/server` 내부 import 금지(공유 타입은 core나 별도 패키지로만)
  - `mobile-ci.yml`을 추가한다(typecheck·test·lint). 서버 CI만 있는 상태를 끝낸다.
- 기대 효과: 같은 리뷰 지적이 반복되는 횟수가 줄고, 밤샘 자율 작업에서도 규칙이 자동으로 지켜진다.

### 적용안 2 — '정원 가꾸기': 번지는 패턴을 조사한 뒤 범주째 막는다
- 원칙: 에이전트는 읽은 패턴을 베낀다. 판단이 필요한 API는 결국 슬롭이 된다.
- 지금과의 차이: `useEffect`·`setTimeout`이 화면 코드에 퍼져 있고 사용 규칙이 없다. 애니메이션·시간 가속·알림이 얽힌 게임이라 타이머 땜질이 퍼지면 성능과 시간 시뮬레이션이 같이 망가진다.
- 바꿀 것:
  - 테크 리드가 두 패턴의 용도를 분류한다(1회, 반나절 이내).
  - 시간 흐름은 core 시계로, 애니메이션 지연은 Reanimated로 처리하는 '정답 길'을 정한다. 그 밖의 `setTimeout`은 린트로 막고 허용 위치만 연다.
  - 옛 사용처는 정리 작업 하나로 걷어낸다.
  - 금지 범위는 분류 결과를 보고 정한다. 지금 바로 전면 금지하지는 않는다.
- 기대 효과: 시간 가속 테스트(OPERATING 5절)의 신뢰도가 오르고, 저사양 Android에서 프레임 드롭 원인이 줄어든다.

### 적용안 3 — 완료 = 증거, 그리고 하나의 검증 CLI와 기능 지도
- 원칙: 됐을 것이 아니라 증거. 반복 검증은 레버(CLI)로. 기능 지도는 공용 어휘.
- 지금과의 차이: 디자인 관문(OPERATING 4절)은 이미 렌더·녹화를 요구한다. 하지만 캡처 스크립트가 작업마다 새로 생겨(9개) 다음 에이전트가 재사용하기 어렵다. 기능 목록도 기획 v2.2·로드맵·C-integrated에 흩어져 있다.
- 바꿀 것:
  - 캡처 스크립트를 `pnpm verify:screen <기능> [--widths 320,360,390,412,430] [--font 150,200] [--record]` 하나로 합친다. 4절 관문의 조합을 기본값으로 둔다.
  - `docs/team/feature-map.md`를 만든다. 열은 `기능 / 기둥(①②③) / 화면 진입 경로 / 플래그 키 / 검증 명령 / 마지막 확인일`이다.
  - 완료 보고에 증거 경로를 반드시 단다. 기능 지도의 '마지막 확인일'은 빌드마다 갱신한다.
- 기대 효과: 검증 비용이 줄어 더 자주 돌리게 된다. '기둥 한 줄 답'(0-2절)이 표로 강제된다. 소프트런칭 판정 때 무엇이 켜져 있었는지 바로 보인다.

### 적용안 4 — 형식 검증은 '오류 비용이 큰 곳'에만, 가벼운 형태로
- 원칙: 검증 연산은 오류 비용에 비례해 쓴다. 속성(불변식) 기반 테스트.
- 지금과의 차이: 시뮬레이션 코어는 예시 기반 단위 테스트 중심이다. 세이브 맡겨 두기의 기기 이동·충돌(Q9)은 자동 테스트 20회 이상으로 판정한다.
- 바꿀 것:
  - `packages/core`에 속성 기반 테스트(fast-check 등)를 도입한다. 불변식 후보는 다음과 같다.
    - 정은 줄지 않는다(D-20)
    - 세이브 마이그레이션은 두 번 돌려도 같다(멱등)
    - 시간 가속 7일과 실시간 7일의 결과가 같다
    - 처벌·죄책감 상태가 생기지 않는다(D-03)
  - 맡겨 두기 동기화(B2·C13)는 `/statechart` 수준의 **상태 표**를 먼저 그리고, 충돌 시나리오를 그 표에서 생성한다.
  - TLA+·Lean은 아래 '보류'에 둔다.
- 기대 효과: 세이브 유실은 반려동물 관계(기둥 ③)를 한 번에 끊는 최악의 버그다. 이런 버그를 예시 20회보다 넓게 잡는다.

### 적용안 5 — '쉬지 않고 달리기'(D-22)에 신뢰 단계를 붙인다
- 원칙: 신뢰가 먼저, 병렬은 그다음. 낮은 신뢰 루프를 자동화하면 슬롭만 늘어난다.
- 지금과의 차이: D-22는 매시간 다음 항목에 착수하라고 한다. 이것은 바깥 루프 자동화에 해당한다. 그런데 모바일 쪽은 린트·CI가 없어 안쪽 루프의 신뢰 근거가 리뷰 문서뿐이다.
- 바꿀 것: 영역별 **자율 단계**를 정한다.
  - 1단계: 작업마다 독립 리뷰 후 커밋(지금)
  - 2단계: CI·린트·속성 테스트가 있는 영역(core·server)은 병렬 에이전트 허용
  - 3단계: 되돌림률이 낮게 유지되는 영역만 야간 무인 연속 작업
  - 아트·UX·카피(기둥 판단)는 단계와 상관없이 사람·크리에이티브 디렉터 확인을 유지한다.
  - **신뢰 지표**로 주간 되돌림 커밋 수·리뷰 재지적 수를 `.claude/progress.md`에 기록한다.
- 기대 효과: 속도는 유지하면서 밤샘 작업이 회귀를 쌓는 위험을 줄인다. 그리고 '얼마나 믿어도 되나'를 숫자로 본다.

### 적용안 6 — 착수 전 '자기 말로 다시 서술' + 갈림길은 시안·프로토타입 경쟁
- 원칙: 맥락 정리는 사람의 일이고, 오해는 일찍 잡는다. 계획은 빨리 현실에 부딪힌다(코드로 하는 계획, arena).
- 지금과의 차이:
  - 오너 지시는 짧고 해석 여지가 크다(예: D-19 '자유도'는 오너에게 다시 물어서 해석을 확정했다).
  - 설계 문서가 매우 길다(기획 v2.2, 서버 v2.1, 정본 개정 30건).
  - 시안 2안 비교 규칙(1-1절)은 디자인에만 있다.
- 바꿀 것:
  - 오너 지시를 받은 에이전트는 착수 전에 **세 줄 재서술**을 진행 기록에 남긴다. 세 줄은 '무엇을, 왜(어느 기둥), 끝난 모습'이다. 해석이 갈리면 그때 오너에게 묻는다.
  - 화면·상호작용 갈림길은 문서보다 **작동하는 프로토타입 2~3개**를 먼저 만들어 비교한다. 1-1절 규칙을 UX·모션까지 넓힌다.
- 기대 효과: 오너 의도와 어긋난 대규모 작업을 막는다. 문서 왕복 대신 손에 잡히는 비교로 '독보성' 판단이 빨라진다.

### 적용안 7 — 출시·운영 자동화는 '승인 → 작은 묶음 → 실패 시 멈춤'
- 원칙: SpaceXSI의 IncidentSweep 방식과 고객 문의 조기 경보.
- 지금과의 차이: 소프트런칭 중 OTA·원격 플래그로 서버 기능을 켠다(D-23). 신고 자동 숨김(B5)도 있다. 하지만 '어떻게 단계적으로 켜고 언제 멈추나'는 문서에 없다.
- 바꿀 것:
  - 플래그·OTA 롤아웃 런북을 둔다. 순서는 오너(또는 PM) 승인 → 작은 비율로 시작 → 집계 핑 이상 시 자동 중단·보고 → 모든 변경 기록이다.
  - 스토어 리뷰·문의·신고 급증을 주기적으로 보는 감시 업무를 '업무(job)' 단위로 한 에이전트에 맡긴다.
- 기대 효과: 소프트런칭에서 작은 사고가 전체 이탈로 번지는 것을 막는다. 판정(01-21~26) 데이터가 오염되지 않는다.

### 적용안 8 — 첫 사용자를 직접 관찰한다
- 원칙: 얼리 유저 직접 온보딩, 비개발자 사용 장면에서 맹점 찾기.
- 지금과의 차이: 검증 계획(D2)은 블라인드 테스트·설문 중심이다. 첫 30초를 사람이 옆에서 보는 절차는 약하다.
- 바꿀 것: 비공개 테스트(빌드 1) 테스터 중 3~5명은 오너가 **첫 실행을 화면 녹화로 받는다**. UX 리서처가 '머뭇거린 지점·웃은 지점·공유하려 한 지점'을 기둥별로 표시한다.
- 기대 효과: OPERATING 2절의 '30초 질문'에 실제 증거가 생긴다. 기둥 ②(자랑) 동선의 실제 마찰을 찾는다.

### 적용안 9 — 덜어내기는 '범위'가 아니라 '기능 안'에서
- 원칙: unlaunch, 최소 변경, 죽은 코드 먼저 제거.
- 지금과의 차이: D-22는 출시 범위를 줄이지 않기로 했다(오너 방향). 그래서 기능 자체를 빼는 덜어내기는 적용하지 않는다.
- 바꿀 것: 각 기능의 리뷰에서 **'이 화면에서 뺄 수 있는 요소 하나'**를 반드시 묻는다(OPERATING 3절의 '과함' 관점을 구체화). 플래그로 꺼진 실험 코드는 판정 뒤 2주 안에 지운다.
- 기대 효과: 범위는 지키면서 '세련되고 우아한'(0-1절) 화면에 가까워지고, 코드 정원의 잡초가 줄어든다.

### 보류(우리 상황에 맞지 않는 것과 그 이유)
- **주석 전면 금지**: 보류. 우리 코드는 한국어 도메인 용어(먹·결·정·이레 등)와 기획 근거를 잇는 설명이 필요하고, 사람 기여자가 오너 한 명이라 주석이 '읽히지 않는' 문제가 Grok Bot 팀(227명)보다 작다. 대신 **'변명 주석'만** 막는다. 예: `// 임시`, `// 일단`, `// HACK`, `// TODO` 뒤에 이슈 번호가 없는 주석을 린트로 막는다.
- **TLA+·Lean 형식 검증**: 보류. 학습·유지 비용 대비 우리의 고위험 영역은 세이브·동기화 하나다. 속성 기반 테스트와 상태 표(적용안 4)로 먼저 덮는다. 맡겨 두기 충돌 버그가 소프트런칭에서 2건 이상 나오면 다시 검토한다.
- **월 PR 수천 건·자동 머지·퍼징 공장**: 보류. 연사 본인이 무제한 토큰 환경이라 일반화할 수 없다고 했다. 우리는 앱스토어 심사·OTA 채널이 있어 '머지 = 배포'가 아니다. 적용안 5의 3단계에 도달한 뒤에 검토한다.
- **계획 모드 폐지**: 부분 보류. 법무·개인정보·스토어 요건(D3·D9)과 판정 규칙(D-23)은 미리 고정한 문서가 반드시 필요하다. 화면·상호작용 설계에만 '프로토타입이 계획'을 적용한다(적용안 6).
- **기능 덜어내기(unlaunch)로 범위 축소**: 보류. D-22 오너 방향과 충돌한다. 기능 안에서만 덜어낸다(적용안 9). 12-03 처리량 점검의 '자르는 순서'(D-20)는 그대로 둔다.
- **pstack 플러그인 설치**: 제안만 하고 결정하지 않는다. Claude Code에 설치할 수 있지만 설정 변경은 오너 결정이다. 외부 실험상 시간과 토큰이 약 2배 든다. 설치한다면 세이브 마이그레이션·서버 동기화 같은 고위험 작업에서만 `/in-your-own-words`·`/blast-radius`·`/interrogate`를 시범으로 쓴다.

### 4-2. 핵심 주장
1. **일은 사라지지 않고 옮겨 갔다.** 1년 전에는 세션 한두 개를 띄우고 명령마다 사람이 승인했다. 지금 Anthropic에서는 세션 수십 개가 몇 시간씩 돌고, 세션이 다른 세션을 띄운다. 사람이 하던 일은 모델(방향 잡기)·auto mode(명령 승인)·deny 규칙과 환경(제한)·테스트·훅·CI(결과 확인)·코디네이터 세션(세션 띄우기)으로 옮겨 갔다. 사람에게 남는 일은 무엇을 시작할지와 언제 받아들일지다. [3곳 일치]
2. **지시 문서는 '코드에서 알 수 없는 것'만 남긴다.** 예: 코드 어디에도 흔적이 없지만 모바일 앱이 아직 쓰는 옛 데이터 소스. 기술 스택 설명이나 뻔한 디렉터리 안내는 지운다. 예전에 넣던 대문자 경고·'절대 하지 마' 줄은 지금 모델이 과하게 따라서 도구 호출이 늘고 결과가 나빠진다. 모델이 바뀌면 지시문·스킬을 감사한다(`/doctor prompt-audit`). 행사 페이지 요지는 이렇게 정리한다: "One calls for project knowledge from the developer." ([ai.engineer](https://www.ai.engineer/talks/vlfCjWuv4es-rethinking-claude-code-best-practices)) [3곳 일치]
3. **auto mode는 판단이지 보장이 아니다.** 분류기 모델이 행동마다 검토한다. 프로젝트 안 읽기·편집은 통과하고, 애매하면 막는다. 신뢰할 저장소·버킷·도메인은 설정(`autoMode.environment`)에 평문으로 알려 준다. 인용한 8월 연구에서 사람 수동 승인은 심어 둔 위험 명령의 약 14%만 잡았고 auto mode는 89%를 막았다. [수치: 2곳 일치, 원 연구는 미확인]
4. **하드 규칙의 기준은 '되돌릴 수 있는가'.** 한 번 틀려도 되돌릴 수 있으면(코드 변경) 모델에 맡긴다. 되돌릴 수 없으면(커밋 안 한 작업 날리기, 비밀이 대화 기록에 노출) 미리 deny 규칙을 둔다. deny 규칙은 분류기보다 먼저, 모든 권한 모드에서 적용된다. [3곳 일치]
5. **권한은 '실행 여부'만 정한다. 실행된 뒤 무엇을 건드리는지는 샌드박스가 정한다.** 승인된 `npm test` 안에서 오염된 의존성이 `.env`나 SSH 키를 읽어 내보낼 수 있다. 샌드박스는 OS 수준에서 파일·네트워크를 막고 자식 프로세스까지 덮는다. 단, 셸 명령만 덮는다(파일 도구·MCP·훅은 밖). [3곳 일치, 세부 한계는 2곳]
6. **클라우드 세션은 새 기계에서 시작한다.** 새 체크아웃이라 Git에 없는 `.env`·키가 없고, 네트워크는 정한 호스트만 열린다. 노트북을 닫아도 돈다. 비밀은 기계 밖에서 요청에 붙여 모델이 값을 보지 못하게 한다. 기계는 버려도 되지만 푸시한 커밋은 남으므로 클라우드에서도 deny 규칙을 저장소에 커밋한다. [행사 페이지·노트 2곳]
7. **검증은 '그럴듯한 오답'을 가르는 검사로.** 아무도 모든 변경을 읽지 않는다. 로그인을 새 API로 옮기는 예에서, 그럴듯한 결과가 여럿 나온다(옛 API 그대로, 새 로그인만 이전, 모두 로그아웃). 핵심 검사는 '이미 로그인한 사용자가 그대로 로그인 상태인가'다. 요청에 완료 모습을 적고, 작업을 각자 테스트가 있는 단위로 나누고, 실제 출력(빌드·스크린샷)을 보여 달라고 한다. [3곳 일치]
8. **훅으로 검사를 강제한다.** 편집 뒤 lint, 작업 완료 때 관련 테스트, 세션 끝에 전체 스위트. 완료를 막으려면 훅이 **종료 코드 2**를 돌려줘야 한다. 1은 막지 않는 오류라 작업이 완료로 표시된다(대부분 도구는 실패 시 1을 낸다). [3곳 일치]
9. **모든 세션은 PR로 끝나고, 리뷰는 위험에 비례한다.** CI가 모든 PR에 같은 검사를 돌리고, 자동 수정이 켜져 있으면 Claude가 실패를 고쳐 푸시한다. 새 맥락의 Claude가 먼저 리뷰하고, 리뷰가 찾은 버그는 별도 에이전트 묶음이 확인한다. 문서·카피는 검사만 통과하면 사람이 안 봐도 되고, 일반 제품 변경은 사람 1명, 위험한 변경은 2명. 자동 머지는 가능하지만 기본값은 아니다. [행사 페이지·노트 일치, 기사는 일부]
10. **코디네이터 세션.** Projects(당시 베타)에서는 메인 세션이 일을 나누고 작업마다 스레드(대개 클라우드 세션)를 띄우고 진행을 추적하며 덜 된 일을 돌려보낸다. 코디네이터는 코드를 쓰지 않는다. 코디네이터와 작업 스레드의 모델을 따로 고를 수 있다. [행사 페이지·노트 일치, 모델 이름은 출처마다 표기가 달라 생략]
11. **마무리 조언**: 평소보다 훨씬 큰 과제 하나를 골라라. CI가 내가 신경 쓰는 실패를 잡는지 확인하라. 클라우드 환경(네트워크·비밀·설정 스크립트)을 갖춰라. 그리고 세션이 어디서 다시 나를 필요로 하는지 적어라. [3곳 일치]
- 규모: Anthropic이 하루 3만 건 넘는 변경을 낸다는 언급 [2차·단일: StartupHub, 다른 글은 날짜가 다름]. 숫자는 인용하지 않는다.
- **이 강의가 다루지 않는 것**: 제품 감각·UX·디자인 품질은 직접 다루지 않는다(행사 페이지 요약 기준). 오너가 원한 '프로덕트를 진짜 잘 만드는 법'은 이 강의에서 바로 나오지 않는다. 아래 4-4는 강의의 **검증 원칙을 제품 수준으로 옮긴 팀 해석**이고, 강의 주장과 구분해 [팀 해석]으로 표시했다.

### 4-3. 앞 강연·Lauren Tan 철학과 비교

**공통점**
- **산문은 약한 층이다.** Lauren Tan은 규칙 문서를 신뢰 피라미드 거의 맨 위(덜 믿을 층)에 두었다. Hallie는 지시 문서를 '코드에서 알 수 없는 것'만 남기라고 한다. 둘 다 '실수할 때마다 문서에 한 줄 더하기'를 반대한다.
- **완료는 증거.** Tan의 '됐을 것이 아니라 증거' = Hallie의 '실제 출력을 보여 달라, 리뷰는 검사 결과를 본다'.
- **교정은 결정론적 장치로.** Tan은 린트 오류 메시지·CI, Hallie는 훅(종료 코드 2)·CI. 같은 방향이다.
- **되돌릴 수 없는 일만 사람·규칙이 막는다.** Tan(pstack 위임 원칙)과 Hallie(되돌릴 수 있는가 테스트)가 같은 말을 한다. 우리 OPERATING 7-7과도 같다.
- **신뢰가 쌓인 만큼 사람 손을 뗀다.** Tan의 '신뢰 먼저, 병렬 나중' = Hallie의 '세션 한두 개 승인 → 수십 개 몇 시간'.

**차이**
- **어디를 고치나**: Tan은 **코드베이스 자체**(아키텍처·범주 금지·주석 금지)를 고친다. Hallie는 **작업 환경**(권한·샌드박스·클라우드 기계·훅·CI·리뷰 흐름)을 고친다. Tan은 '정원', Hallie는 '울타리와 관문'에 가깝다.
- **모델을 얼마나 믿나**: Hallie는 모델이 좋아졌으니 예전 보호 장치를 걷어 내라고 한다(덜 쓰기). Tan은 모델이 좋아도 판단이 필요한 곳은 결국 슬롭이 된다며 범주째 막는다(더 막기). 충돌은 아니다. Hallie가 걷어 내라는 것은 **산문 경고**이고, Tan이 더하라는 것은 **기계 검사**다.
- **검증 연산**: Tan은 토큰 대부분을 검증에 쓰고 형식 검증까지 간다. Hallie는 형식 검증을 말하지 않고 테스트·빌드·스크린샷·CI 수준에 머문다.

**새로 더해지는 것**
1. **'그럴듯한 오답'을 가르는 검사**: 검사가 있느냐가 아니라, 그 검사가 그럴듯하지만 틀린 구현을 떨어뜨리느냐를 묻는다. 앞 강연에는 이 기준이 명시되지 않았다.
2. **보안 경계**: 권한과 샌드박스의 차이, 의존성 공급망 위험, 클라우드의 비밀 처리.
3. **훅 종료 코드 2**라는 구체 장치.
4. **위험 비례 리뷰 등급**과 '리뷰 지적을 다른 에이전트가 확인'.
5. **모델이 바뀔 때마다 지시문 감사**(덜어내기를 지시문에도 적용).
6. **코디네이터는 코드를 쓰지 않는다**는 역할 분리, 그리고 '큰 과제 하나로 사람이 필요한 지점 찾기'.

### 4-4. 몽망이 팀에 적용할 것

현재 상황(근거, 저장소 관찰 11-20):

#### 적용안 10 — 기능마다 '그럴듯한 오답'을 적고, 그것을 떨어뜨리는 검사를 만든다 (최우선) [팀 해석]
- 원칙: 검사는 의도한 동작과 그럴듯한 오답을 갈라야 한다(4-2의 7).
- 지금과의 차이: 우리 완료 기준은 '화면이 나온다·테스트가 통과한다'다. 그런데 세 기둥 기능은 **그럴듯한 오답이 특히 많다**. 겉으로는 동작하지만 기둥은 실패하는 구현이 쉽게 나온다. 블라인드 '같은 몽망이 찾기'(D2)는 외부 테스트라 12-05에야 결과가 나온다.
- 바꿀 것: feature-map.md에 `그럴듯한 오답 / 판별 검사` 두 열을 둔다. 초안:

| 기능(기둥) | 그럴듯한 오답 | 판별 검사 |
|---|---|---|
| 타고남+먹(①) | 씨앗은 다르지만 나란히 놓으면 비슷해 보인다 | 시드 100개를 렌더해 썸네일 크기에서 가장 비슷한 쌍의 차이가 기준 이상(블라인드 테스트 전 자동 대리 지표) |
| 결 이름(①) | 키우는 방식이 달라도 같은 결 이름이 몰린다 | 시간 가속 시뮬레이션에서 서로 다른 습관 프로필 N개 → 결 이름 분포가 한쪽에 쏠리지 않음 |
| 공유 카드·OG(②) | 이미지는 나오지만 피드 썸네일 크기에서 몽망이가 안 보인다 | OG를 SNS 썸네일 크기로 줄인 캡처를 증거로 첨부 |
| 반김·손 기억(③) | 반기긴 하지만 모든 몽망이가 똑같이 반긴다 | 서로 다른 세이브 두 개에서 반김이 다름 |
| 머뭇거림(③) | 서운함 표현이 죄책감으로 읽힌다 | 카피·모션을 새 맥락 리뷰어가 '찔렸다' 기준으로 판정(D-20 통과선의 사전 점검) |
| 맡겨 두기·기기 이동(③) | 동기화는 되지만 이전 기기의 최근 하루가 사라진다 | 첫 검사 = '기존 몽망이가 그대로인가'(강의의 로그인 예와 같은 구조) |
- 기대 효과: 외부 테스트 전에 기둥 실패를 싸게 잡는다. '기둥 한 줄 답'(0-2절)이 실제로 검사 가능한 문장이 된다. 기능 지도(적용안 3)와 한 표로 합쳐져 문서가 늘지 않는다.

#### 적용안 11 — 리뷰를 위험에 비례시키고, 기둥 체감은 사람이 받는다 [강의 + 팀 해석]
- 원칙: 위험 비례 리뷰, 새 맥락 리뷰, 리뷰 지적은 다른 에이전트가 확인(4-2의 9). 사람은 '언제 받아들일지'를 정한다(4-2의 1).
- 지금과의 차이: 모든 작업이 같은 리뷰 관문을 지난다. 오타 수정과 세이브 마이그레이션의 무게가 같다. 사람 리뷰어는 오너 한 명이라 강의의 '사람 2명'은 그대로 못 한다. 리뷰 지적이 맞는지 재현 확인 단계가 없다.
- 바꿀 것:
  - 리뷰 등급표(낮음 / 보통 / 높음 / 기둥 체감)를 리뷰 문서 양식 머리에 둔다(6절 제안 9).
  - '사람 2명' 대신 **독립 에이전트 리뷰 2 + 오너가 증거(녹화·캡처) 확인**으로 바꾼다.
  - **기둥 체감 등급**(UX·아트·카피 톤·첫 30초)은 검사가 아무리 초록이어도 크리에이티브 디렉터와 오너가 녹화를 보고 받는다. 이것이 '제품 감각'이 사람에게 남는 자리다.
  - **새 맥락 첫인상 리뷰**: 기획 문서를 주지 않은 리뷰 에이전트에게 녹화만 보여 주고 '처음 30초에 무엇을 느끼나, 다른 게임에서 본 것 같은가'(0-1·2절 질문)에 답하게 한다. 문서를 읽은 작성자 시선에 물들지 않은 대리 첫 사용자다. [팀 해석 — 실제 사용자 관찰(적용안 8)을 대신하지 않는다]
- 기대 효과: 사소한 작업의 리뷰 비용이 줄어 D-22 속도를 유지한다. 그 시간을 세이브·기둥 체감에 몰아 쓴다. 리뷰 오탐으로 멀쩡한 코드를 고치는 일이 줄어든다.

#### 적용안 12 — 완료 검사를 프로젝트 훅으로 강제한다(종료 코드 2)
- 원칙: 훅으로 lint·테스트를 강제하고, 막아야 할 실패는 종료 코드 2(4-2의 8).
- 지금과의 차이: 검사 훅이 오너 PC 전역 설정에만 있다. 같은 저장소를 다른 기기·클라우드 세션에서 열면 검사가 없다. lint 훅은 없다(모바일 ESLint도 아직 없음, A6).
- 바꿀 것: A6에서 ESLint를 켤 때 프로젝트 `.claude/settings.json`에 훅을 같이 둔다. 편집 뒤 해당 패키지 lint, 작업 완료 때 관련 테스트, 세션 끝에 `pnpm -r typecheck && pnpm -r test`. 완료를 막을 실패는 종료 코드 2로 돌려준다. 정확한 훅 이벤트 이름(특히 '작업 완료' 이벤트)은 Claude Code 문서로 확인한다 [확인 필요]. **설정 변경이므로 오너 승인 후** 적용한다.
- 기대 효과: 적용안 1('검사로 승격')이 실제로 매 세션 돌게 된다. 밤샘 작업에서 '테스트 실패인데 완료로 보고'가 구조적으로 막힌다.

#### 적용안 13 — '되돌릴 수 있는가'로 deny 규칙을 정한다
- 원칙: 되돌릴 수 없는 것만 하드 규칙, 나머지는 모델 판단. 권한과 샌드박스는 다르다(4-2의 4·5).
- 지금과의 차이: OPERATING 7-7이 같은 원칙을 말하지만 **글로만** 있다. 앞으로 생길 되돌릴 수 없는 일이 많다: Supabase·GCP 비밀(B1·B6), EAS 운영 채널 OTA(C10), 스토어 제출(A5·D7), 원격 DB 마이그레이션.
- 바꿀 것: 프로젝트 deny 규칙 후보(오너 승인 후, 적용안 12와 같은 파일).
  - 비밀 읽기: `.env`, `.env.*`(단 `.env.example` 허용), 서명 키·서비스 계정 JSON
  - 강제 푸시·히스토리 재작성
  - 스토어 제출·운영 채널 OTA 배포(`eas submit`, 운영 채널 `eas update`)
  - 원격 DB 초기화·운영 마이그레이션 직접 실행
  - 의존성이 많은 테스트 실행은 샌드박스 사용을 검토한다(셸 명령만 덮는다는 한계 포함).
  - 규칙 문법(패턴 표기)은 문서로 확인 후 쓴다 [확인 필요].
- 기대 효과: 서버·스토어가 붙는 12월에 사고 한 번이 소프트런칭 판정 데이터를 오염시키는 위험을 미리 막는다. 산문 원칙(7-7)을 구조로 옮기는 것이라 7절 1항과도 맞는다.

#### 적용안 14 — 지시문 감사: 코드에서 알 수 없는 것만 남긴다
- 원칙: 지시 문서는 발견할 수 없는 지식만. 강조 반복은 해롭다. 모델이 바뀌면 감사(4-2의 2).
- 지금과의 차이: OPERATING은 82줄로 아직 짧지만 절마다 오너 방향이 쌓이고 있다. 서브에이전트 지시문에 '반드시·절대' 같은 강조가 자주 들어간다. 모델 교체 때 지시문을 다시 보는 절차는 없다.
- 바꿀 것: 모델이 바뀌거나 한 달에 한 번, OPERATING·스킬·서브에이전트 프롬프트 템플릿을 감사한다(`/doctor prompt-audit` 등). 남길 것: 오너 방향·세 기둥·도메인 용어(먹·결·정·이레)·법무·연령 결정·정본 지도. 지울 것: 코드나 package.json을 보면 아는 스택·경로 설명, 같은 말의 강조 반복.
- 기대 효과: 에이전트가 지시문을 과하게 따르다 생기는 헛도는 도구 호출이 줄고, 정말 중요한 오너 방향이 묻히지 않는다.

#### 적용안 15 — 큰 과제 하나로 '사람이 필요한 지점'을 잰다
- 원칙: 평소보다 훨씬 큰 과제 하나를 맡기고 어디서 사람이 다시 필요했는지 적는다. 코디네이터는 코드를 쓰지 않는다(4-2의 10·11).
- 지금과의 차이: D-22로 체크리스트를 쉬지 않고 돌리지만, '어디서 사람이 필요했나'를 체계적으로 기록하지 않는다. PM 역할과 구현 역할이 한 세션에 섞이는 경우가 있다.
- 바꿀 것: B1(서버 골격) 또는 C13(기기 이동 자동 테스트) 하나를 코디네이터 + 작업 스레드로 돌린다. 코디네이터(PM)는 나누기·추적·돌려보내기만 하고 코드를 쓰지 않는다. 끝나면 '사람이 필요했던 지점' 목록을 progress.md에 남긴다. 그 목록이 적용안 5(자율 단계)의 근거 데이터가 된다.
- 기대 효과: 어느 영역을 2·3단계 자율로 올릴지 감이 아니라 기록으로 정한다.

#### 보류(맞지 않는 것과 그 이유)
- **클라우드 세션으로 전면 이전**: 보류. 우리 완료 증거의 상당수가 로컬 렌더·캡처(Skia·Reanimated 화면, 폭·글자 크기 조합)와 오너 실기기에 묶여 있다. 클라우드 기계에서 같은 캡처가 되는지 [확인 필요]. 계정·네트워크·비밀 설정도 오너 일이다. 적용안 15의 시범이 서버(B1)처럼 화면이 없는 과제일 때만 클라우드로 해 본다.
- **자동 머지**: 보류. 앱은 머지 = 배포가 아니다(스토어 심사·OTA 채널). 문서·카피 오타 등급만 '검사 통과 + 에이전트 리뷰'로 가볍게 한다(적용안 11).
- **'사람 리뷰 2명'**: 그대로 불가(사람은 오너 1명). 독립 에이전트 2 + 오너 증거 확인으로 바꾼다.
- **오래된 보호 장치 일괄 제거**: 부분 보류. 강의는 산문 경고를 걷어 내라는 것이지 검사를 걷어 내라는 것이 아니다. 우리는 아직 기계 검사가 적은 단계라(모바일 CI 없음) 지시문만 감사하고, 검사는 오히려 늘린다(7절과 같은 방향).
- **코디네이터·스레드 모델 지정**: 결정하지 않는다. 모델 선택은 비용이 걸려 있어 오너 결정이다.
- **규모 지표(하루 변경 수)**: 쓰지 않는다. 앞 강연과 같은 이유로 숫자는 목표가 아니다.
