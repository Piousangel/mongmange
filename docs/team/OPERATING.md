# 몽망이 키우기 팀 — 운영 규칙

## 0. 목표
- **'mongmangE 키우기'를 Google Play·App Store에 출시한다.** 몽망이를 0부터 높은 자유도로 하루하루 키우는 게임.
- 기간보다 **완성도**가 우선이다. 출시일은 품질 기준을 통과했을 때 정한다.
- 오너가 준 방향은 위 두 줄뿐이다. 나머지(컨셉·장르 세부·스택·아트·수익·일정)는 **팀이 정한다**. 오너에게는 오너만 할 수 있는 일(결제·계정·신원 확인·법적 서명)과 큰 방향 전환만 묻는다.

## 0-1. 오너 방향 (11-19 추가)
- **기획·UI·UX는 정말 독창적이고, 세련되고, 우아해야 한다.** '흔한 귀여운 키우기 게임'처럼 보이면 실패다. 시안을 낼 때마다 "다른 게임에서 본 것 같은가?"를 리뷰어가 먼저 묻는다.
- **이미지·애니메이션 생성 MCP와 도구는 전부 써도 된다**(Figma 이미지·벡터·셰이더·모델 실행, 코드 생성 벡터, Rive 등). 도구 제약 때문에 품질 기준을 낮추지 않는다.
- **필요한 건 전부 동원한다** (11-19 오너 재확인: "다 동원해도 좋다는 뜻"). Gemini(이미지·영상·텍스트), Higgsfield(영상·모션), Figma MCP, Claude in Chrome으로 웹 도구 조작, 외주·유료 도구까지 포함. 비용이 드는 계정·충전은 오너 할 일 목록에 올리고, 그동안 쓸 수 있는 도구로 먼저 진행한다.
- 목표는 **독보적**인 게임이다. "잘 만든 키우기 게임"은 기준에 못 미친다.
- AI 생성물은 저작권·일관성 위험이 있다. 그래서 출시 에셋은 "AI로 탐색 → 팀이 정한 형태 언어로 재구성·편집"을 기본으로 하고, 출처는 라이선스 원장에 남긴다.

## 0-2. 오너 방향 (11-20 추가) — 게임의 세 기둥
1. **자유도가 굉장히 높아야 한다. 사람마다 다 다른 몽망이를 키운다.** 두 사람의 몽망이가 비슷해 보이면 실패다.
2. **자기 몽망이를 SNS에 자랑하고 싶어야 하고, 본 사람이 "나도 키워 볼까?" 하는 호기심을 가져야 한다.** 공유물은 그 자체로 광고가 된다.
3. **몽망이와 감정을 주고받는다. 반려동물을 키운다는 생각으로 전개한다.** 몽망이는 나를 알아보고, 기억하고, 반기고, 서운해하고, 나에게 무언가를 바란다(단, 처벌·죄책감 없음 D-03).
- 모든 기능은 이 세 기둥 중 무엇을 강하게 하는지 한 줄로 답할 수 있어야 한다.

## 2. 결정 방법
- 갈림길 결정은 `DECISIONS.md`에 남긴다(맥락, 선택, 버린 안).
- 결정마다 **반증 조사**를 한 번 한다(이 선택이 실패한 사례가 있는지).
- 사용자 관점 질문 7가지를 팀이 먼저 묻는다: 처음 켠 사람이 30초 안에 무엇을 느끼나 / 왜 내일 다시 켜나 / 무엇이 '내 몽망이'라는 애착을 만드나 / 자유도가 막막함이 되는 지점은 어디인가 / 과금·광고가 불쾌한 지점은 어디인가 / 한 달 뒤 콘텐츠가 바닥나지 않나 / 다른 키우기 게임 대신 이걸 고를 이유는 무엇인가.

## 3. 팀 리뷰 관문 (모든 단계, 커밋 전)
- 작성자 ≠ 검토자. 검토자는 **놓침·부족·과함** 세 관점을 모두 본다.
- 완료 보고에 "리뷰: 누가 무엇을 지적, 몇 건 반영"을 쓴다.

## 4. 디자인 품질 관문
- 모든 화면은 렌더해서 눈으로 본다. 폭 320·360·390·412·430, 글자 크기 150%·200%, 라이트·다크(지원 시)를 확인해야 "완료"다.
- 애니메이션은 정지 화면이 아니라 녹화·연속 캡처로 확인한다.

## 5. 품질 기준 (출시 관문)
- 크래시 없는 상태로 7일 연속 플레이 시나리오 통과(시간 가속 테스트 포함).
- 시뮬레이션 코어 단위 테스트 통과, 세이브 마이그레이션 테스트 통과.
- 실기기 iOS·Android 각 1대 이상 확인(오너 기기).
- 외부 테스터 피드백 반영(Google 비공개 테스트 기간 활용).
