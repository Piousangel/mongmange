## 1. 잘못 지우기 위험 — 경로 열거

인증 경로를 컨트롤러마다 직접 열거했다(`grep @Controller·@UseGuards`):

| 컨트롤러 | 인증 | 활동 |
|---|---|---|
| `account.controller.ts`(bootstrap·recovery-code·recover·DELETE me) | 클래스 `@UseGuards(AuthGuard)` | 가드 touch. bootstrap 신규는 INSERT 때 이달(`account.service.ts:72`), recover는 tx 안에서 이달(`:130`) — 새 기기 sub는 아직 링크가 없어 가드가 못 쓰므로 서비스가 직접 씀 |
| `cloud-saves.controller.ts`(meta·GET·PUT·conflicts·versions·restore) | 클래스 가드 | 가드 touch |
| `page.controller.ts`(GET/PATCH creature, PUT page, commit, DELETE page) | 클래스 가드 | 가드 touch |
| `saves.controller.ts` validate, `metrics` ping, `ota`, `m.controller`, `deletion` web·영수증, `health`, `_local-storage`, `cron` | 인증 없음(사용자 JWT를 읽는 곳 없음 — `authorization` grep 0) | 활동 아님 — 처리방침 188행 '계정으로 한 요청'과 일치 |

- **세이브 없이 링크만 쓰는 사람**: `/creature`·링크 API가 가드를 지나므로 잡힌다(시험 ① 6개 probe + 변이 4).
- **되찾기 직후·기기 이동**: 새 기기는 recover tx에서 이달로 씀, 옛 기기 sub는 410(활동 아님 — 맞음, 같은 사용자를 새 기기가 갱신).
- **UTC 월 경계·off-by-one**: 대상 = 활동 달 M < (이달 − 24) ⇔ 이달 ≥ M+25. M의 말일 활동이라도 2년 + 1일 뒤에야 대상 → 2년 전에는 절대 지우지 않음. 시험이 2026-10-31T23:59:59Z / 11-01T00:00:00Z로 고정. KST 사용자의 11-01 08:59 활동은 10월로 기록되지만 지우는 시각도 UTC 기준이라 여전히 2년 + 약 1일 이상.
- **시간대**: adapter-pg가 Date를 UTC 문자열(`YYYY-MM-DD HH:mm:ss`, 오프셋 없음)로 보내 `::date` 캐스트가 세션 TimeZone에 좌우되지 않음을 소스(`@prisma/adapter-pg` `formatDateTime`)로 확인. `created_at AT TIME ZONE 'UTC'` → timestamp → `date_trunc`도 세션 TZ 무관. JS `activeMonthOf`와 SQL 정의 일치.
- **값 없는 옛 계정 = 만든 달**: 만든 달 ≤ 실제 마지막 활동이므로 보수적이지 않은(더 일찍 지우는) 쪽이다. 다만 운영 배포 전(B6 대기)이라 NULL 행이 생길 길이 없고(bootstrap이 늘 씀), 서비스 시작 뒤 2년 안에는 대상이 없어 실제 위험 0.
- **경합(잠금 재확인)**: 후보 선택과 삭제 사이 활동 → 삭제 tx의 `FOR UPDATE` 뒤 재확인으로 건너뜀(변이 2로 확인). 삭제 tx가 잠금을 쥔 동안 들어온 touch는 커밋 뒤 0행 → 그 요청은 이미 지워진 사용자로 진행(04:30 KST 그 순간 돌아온 2년 미사용자 — 수용 가능, 기록만).

## 발견 사항

### M1 (중간) '추가 읽기 0' 주장이 사실과 다름 — 모든 인증 요청에 SELECT 1개 추가
- `apps/server/src/auth/auth.guard.ts:50-53`. Prisma 7.10(relationJoins 미사용)은 관계 select를 **별도 쿼리**로 낸다. 실측 로그: `SELECT … FROM app.user_auth WHERE sub=$1` 다음에 `SELECT id, last_active_month FROM app.users WHERE id=$1`. 즉 V25 전보다 인증 요청마다 왕복 1회(풀러 경유 ~1ms대)가 는다. 두 SELECT는 트랜잭션 밖이라 원자적이지도 않다(여기서는 무해).
- DECISIONS 495행 '추가 읽기 0', activity.ts 머리말, architecture.md 5-5의 '같은 조회로 읽고'가 틀린 증거가 된다.
- 권고: `$queryRaw`로 `user_auth JOIN users` 한 문장(또는 `relationLoadStrategy: 'join'` + previewFeatures `relationJoins`)으로 바꾸고, 쿼리 수를 세는 시험(쿼리 이벤트 1개)을 추가. 못 고치면 문서 문구를 '요청마다 PK 조회 1회 추가'로 정정.

### M2 (중간) 대량 오삭제 차단기 없음 — 상한 200은 속도 제한일 뿐 멈추지 않음
- `apps/server/src/deletion/inactive-sweep.ts:20·50-70`. 상한은 하루 200명이지만 **다음 날 또 200명**이다. 시나리오: ① 인스턴스 시계가 미래로 튐(2년+) → 그날 전원이 후보 ② 활동 갱신이 조용히 실패(`activity.ts:28-30`은 warn만 남기고 삼킴 — 권한·스키마 변경·풀러 문제) → 2년 뒤부터 매일 200명씩 활동 중인 사람이 지워짐. 소프트런칭 규모(수천 명)면 몇 주 안에 전원.
- 시계가 늦게 돌아와도 미래 값은 되돌려지지 않아(조건부 UPDATE) 사후 피해는 그날 몫뿐이지만, ①·② 모두 되돌릴 수 없다(복원 재적용이 오히려 다시 지움).
- 권고(되돌릴 수 없는 작업의 최소 안전장치): 실행 전에 후보 수를 세어 **절대 수(예: 500) 또는 전체 사용자 대비 비율(예: 5%)을 넘으면 0명 지우고 error 코드 `inactive_sweep_tripped` + 500**(운영자가 확인 뒤 수동 `inactive-sweep`에 해제 인자). 함께 `activity_touch_failed`를 알림(B6 로그 알림 목록)에 건다. 차단기 시험 1개(201명이 전체의 대부분인 상황에서 0명 삭제).

### M3 (중간) 실행 시간 상한 없음 + 500 재시도가 상한을 곱함
- `inactive-sweep.ts:50-70`은 시간 예산이 없다. 사용자 하나마다 `deleteUser` → 요청 안에서 `drainDeletion`(세 버킷 list·remove + Auth admin 삭제, Auth 타임아웃 3초) → 200명 직렬이면 실제 Supabase 왕복으로 수십~수백 초. 앞에서 `gc.runDue()`도 먼저 돈다. Cloud Scheduler HTTP 기본 attemptDeadline 180초·Cloud Run 기본 요청 300초 — **어디에도(B6 체크 포함) 값이 정해져 있지 않다**(grep 0).
- 마감을 넘기면 Scheduler는 실패로 기록하지만 Cloud Run은 계속 처리(또는 300초에 끊김 — 사용자 단위 tx라 데이터는 안전, drain 잔여는 대기열이 재시도).
- `cron.controller.ts:82-97`: 한쪽 실패 → 500. B6에서 Scheduler 재시도를 켜면 **재시도마다 정리가 다시 200명**(하루 상한이 (1+재시도) × 200). Storage 장애로 gc가 며칠 계속 실패하면 매 재시도가 정리를 더 돌린다. 재시도가 앞 실행과 겹치면 같은 후보를 두고 경합(잠금으로 안전, 다만 L1처럼 failed로 셀 수 있음 — 실제로는 404 분기로 skipped).
- 권고: ① `run()`에 시간 예산(예: 120초 — 넘으면 `more=true`로 멈춤) ② 정리 결과가 이미 오늘 돌았으면(같은 UTC 날 deletion_log kind=inactive 합이 상한) 재실행은 0명 — 또는 정리 실패만 500의 근거로 삼고 gc 실패는 별도 알림 ③ B6 체크에 `storage-gc` attemptDeadline(≥ 예산 + gc)·재시도 횟수·Cloud Run timeout 명시.

### L1 (낮음) 동시 삭제 404 → skipped 분기 미검증 — `inactive-sweep.ts:64`
변이 5 생존. 재시도 겹침·수동 실행과 겹칠 때만 의미. 두 `run()`을 `Promise.all`로 돌려 `failed: 0` 단언 1개 권장.

### L2 (낮음) recover의 활동 달 쓰기 미검증·무조건 쓰기 — `account.service.ts:130`
변이 7 생존. 문서(5-5)는 'bootstrap·recover는 서비스가 직접 쓴다'고 하지만 시험이 없다. 앱이 되찾기 직후 다른 인증 요청을 내므로 실제 영향은 작다. 또 이 UPDATE는 조건 없이 `= 이달`이라 시계가 늦은 인스턴스는 값을 한 달 되돌릴 수 있다(activity.ts가 막은 것과 같은 종류, 영향 1개월·보수적이지 않은 방향). `GREATEST(last_active_month, 이달)` 또는 같은 조건식 + 시험 1개 권장.

### L3 (낮음) 실패 신호가 흐림
- 사용자 단위 실패(`failed>0`)는 200 응답 — Scheduler상 성공. warn 코드 `inactive_sweep_incomplete`가 정상 적체(`more`)와 실패를 함께 덮는다(`inactive-sweep.ts:72`). `failed>0`은 별도 error 코드로.
- 같은 200명이 늘 실패하면 커서가 매번 0부터라 뒤 후보가 영영 처리되지 않는다(굶주림). 위 error 코드 알림이면 충분.
- 500 응답 본문에 부분 결과가 사라짐(로그에만) — 수동 실행 때 불편, 기록만.

### L4 (낮음) `touch`의 `IS NULL` 분기 미검증 — `activity.ts:26`
변이 6 생존. NULL 행이 운영에 생길 길이 없어 영향 0에 가깝다. 시험 ①에 `setMonth(null)` probe 하나 추가면 됨.

### L5 (낮음) 문서 정합
- DECISIONS 498행 '12개' → 실제 15개.
- DECISIONS 495행·architecture 5-5 '같은 조회로'(M1과 함께 정정).
- `deletion_log.channel = app`은 사용자가 낸 경로가 아닌데 'app'으로 남는다. enum에 `system`이 없어 고르기 어렵다는 점은 이해하나, 감사 해석용으로 DECISIONS에 'inactive는 channel=app이 시스템 실행을 뜻함' 한 줄.
- 처리방침 K20(33행)·PIA R13은 아직 '미구현' — DECISIONS 499행대로 정본 담당 갱신 필요(이 리뷰 범위 밖, 대조 결과는 아래 5절).

## 4. 활동 갱신 성능
- 쓰기: 같은 달이면 0(xmin 시험), 달마다 사용자당 최대 1 UPDATE(조건부라 동시 요청은 같은 값 또는 0행). 경합 문제 없음.
- 읽기: **+1 SELECT/요청**(M1).
- 세이브 tx 안의 UPDATE 4곳 제거로 세이브 tx의 users 행 잠금이 사라진 것은 오히려 개선.

## 6. 시험 품질
그럴듯한 오답을 잘 고른 시험이다(링크만 쓰는 사람, 경계 1초, xmin, 늦은 시계, 전 표 전문 검색, 실제 HTTP cron). 변이 4/7 잡힘, 생존 3개는 L1·L2·L4. M2·M3에 해당하는 시험(차단기·시간 예산·쿼리 수)이 없다.

## 조건(배포 B6 전)
1. M1 — 한 문장 조인 + 쿼리 수 시험(또는 문서 정정)
