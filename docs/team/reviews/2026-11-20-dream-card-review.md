## ① 시각

### 1-1 공유하고 싶은가 (05a 대비)
- 05a는 종이 전체를 채우는 섬유질 먹결 + 가는 금선이다. v1은 **평평한 회색 띠 + 날카로운 계단 가장자리**다. 층이 두껍고 균일해 "판화"보다 "지형도·나무 단면"에 가깝다. 우아함보다 장치의 인상이 먼저 온다.
- 인화 영역이 종이의 약 45~55%뿐이고 위·아래가 크게 빈다. 4:5는 균형이 괜찮지만, 05a의 압도감은 없다. 스크린샷 한 장으로 SNS에서 멈추게 하는 힘은 약하다. 산(9:16)이 가장 낫다(실루엣이 곧 이야기).
- 잔물결(c, 재빠름)·바다·이불의 가로 끌림은 **글리치(찢긴 종이·깨진 디스플레이)로 읽힌다**. rain_b 왼쪽(약 x260,y510)에는 흰·금 조각이 튀는 **명백한 아티팩트**가 있다(빗질 접힘 구간). 보고서는 "찢긴 종이처럼 보일 수 있음" 정도로만 적었다.
- 금박: 가는 선이 약간 보이나 05a처럼 "반짝이는 한 줄"이 아니라 띠 경계의 노란 테로만 읽힌다.

### 1-2 눈동자·과녁 읽힘 (심각)
- 몽망이가 맑은 원 안에 있고 그 둘레가 동심 고리 → **눈(홍채)·과녁**. 찻잔 a/b/c, 찻잔 둘, 별·비 c, 달 c, 이불에서 공통. teacup_b는 손잡이 고리까지 붙어 "과녁 + 옆 눈"이다. art-bible 13절(05a 평가)이 정확히 이 위험("소용돌이 속 눈동자")을 경고했고 "몽망이 2배"로 막으려 했지만, 맑은 원(빈 자리)이 몽망이 몸보다 훨씬 커서 **원이 눈, 몽망이가 동공**이 된다. 14절 6의 "눈동자 넣는 쪽으로 끌려감"이 카드 구성에서 반대 방향으로 재발한 꼴이다.
- 해법 방향(다음 단계에서 고를 것): (a) 맑은 원을 몽망이 몸 바로 둘레로 줄이고 가장자리를 비대칭으로(바닥 쪽만 비움) (b) 고리 중심을 몽망이에서 어긋나게(산·바다처럼 몽망이가 수면·능선 "위"에 앉는 구성을 전 모티프로 확대) (c) 첫 고리(가장 안쪽 짙은 테)를 끊어 완전한 원을 피함. 바다 코드 주석에 "가운데 두면 눈동자로 읽힘"이라고 이미 적혀 있다 — 같은 원칙을 나머지에도 적용하라.
- 몽망이 몸: 좌상단·우하단의 **회색 호(획 층)가 게 집게·헤드폰·다리처럼** 보이고, 몸 밑에 평평한 그림자 띠가 있다. 이는 render-03 문법 영역이지만 카드에서 가장 눈에 띄는 약점이다. 금지표(1-4)의 "귀·뿔·후드" 항목과 대조 필요. 보고서 "획 재해석 층이 거의 안 보임"과도 모순된다(오히려 몸에 붙은 호가 눈에 띔).

### 1-3 10개 구별
- 실루엣으로 구별: 산, 바다(납작), 달(상단 원), 창가의 손(방울 4개), 별(점). 인정.
- 약함: **비**(도넛 + 우하단 구멍; 비로 읽을 단서가 없음, 보고서 인정), 이불(원형 + 격자 띠는 있으나 도넛), 찻잔 vs 찻잔 둘(손잡이 방울 하나 차이), 바다 vs 손잡고 본 바다.
- 글자(아침 문장)를 가리면 10개 중 변별 가능한 것은 6개 정도로 본다. 라벨 의존 카드는 공유 시 "무슨 꿈인지"가 약하다.

### 1-4 레이아웃
- 9:16: 종이가 위아래 남색 여백에 둥둥 떠 있고 인화가 작다(보고서 지적 동의, 0.38→0.45는 타당). **산의 오른쪽 날개가 종이 오른쪽 가장자리(약 x1020)에서 잘린다** — 페이드로 부드럽게 끊기긴 했으나 종이 밖으로 번진 인상. 9:16에서 세로쓰기 이름 아래에 산 오른쪽 봉우리가 접근한다(겹침은 없음).

## ② 코드

### 2-1 결정성 테스트가 의미 있나 (약함)
- 1번 테스트: 같은 순수 함수를 두 번 불러 JSON 비교. 순수 TS이므로 **거의 항상 참**인 동어반복이다. 의미 있게 만들려면 (a) 고정 입력의 **스냅샷(해시 상수)** 로 시드·op 열을 고정(리팩터가 장면을 바꾸면 실패) (b) 입력 객체 키 순서·획 기록 복제본(deep clone)에도 같은 결과를 확인.
- 시드 변화 테스트는 유용하나 `flow`, `flowSeed`, `composition`, `strokeRef`, 획 한 점 이동 같은 **나머지 필드** 민감도를 안 본다. 보고서의 "카드 필드 + 획 점열·부착" 시드라는 주장에 비해 검증이 부분적이다.
- 상한 테스트: `toBeLessThanOrEqual` 은 **쪼개 버리는(splice) 코드가 있어 항상 참**이다(`while (pre.length > LIMIT) pre.splice(0,1)`). 상한 초과를 감지하려면 자르기 **전** 길이를 노출/검사해야 한다. 더 심각하게, 자를 때 **앞쪽(= 가장 바깥 고리 방울)** 이 사라진다. 이는 시각을 조용히 바꾼다. 어떤 입력에서 자르기가 발동하는지 테스트가 말해 주지 않는다(자르기 도달 여부 미확인).
- 모티프 구별: `sigs.size >= 9` 는 op 종류(`k`) 문자열만 비교한다. 파라미터가 달라도 같은 문자열이면 같은 것으로 본다. 10개 중 1개 겹침도 허용. **실제 구별(이미지)은 테스트하지 못한다** — 그 한계는 인정하되 이름을 "모티프 구성 상이"로 정확히 쓸 것.
- "같은 입력 PNG 바이트 동일"(보고서 1절·5절 "결정성 true")은 **테스트로 보호되지 않는다**. 실제로는 플랫폼마다 달라질 수 있다(GPU 부동소수·`Math.sin/cos` V8 vs Hermes·글꼴). 주장을 "같은 기기·같은 빌드에서 장면(op)은 동일"로 낮출 것.
- 4:5 aspect는 상한 루프에서 안 돌린다(9:16만). 획이 0개일 때(strokes 빈 배열), `nseg=0` 경로 테스트 없음.

### 2-2 셰이더 uniform
- 배열 합: pre 40×2 + post 28×2 + seg 40×2 = **216 vec4**, 거기에 스칼라·vec(origin, unit, shift, npre, npost, nseg, inkC, goldC, aa, grain, fade, yLim, poolFill)가 더해지고 GLSL의 패킹 규칙상 최대 +10~14 vec4다. **약 226~230 vec4**. 보고서의 "상한 256"은 하나의 기준일 뿐이고, 주석 "256 안쪽"도 스칼라를 안 센다.
- 실제 `GL_MAX_FRAGMENT_UNIFORM_VECTORS`: Adreno 3xx 계열 약 221~224, Mali-T6xx/T7xx·Adreno 4xx+는 대체로 224 이상~1000+, 구형·저가 기기에는 이보다 작은 값이 있다. 즉 **저가 Android 일부에서 컴파일·링크 실패 가능**. Skia 런타임 셰이더 컴파일 실패는 `RuntimeEffect.Make`가 null → 모듈 로드 시 `throw new Error('marble shader compile failed')` 이다. 이 throw는 **모듈 최상위**에서 실행되므로 카드 화면이 아니라 이 모듈을 import하는 화면/앱 번들이 크래시할 수 있다(App.tsx 라우트가 정적 import라면 앱 전체). 필수 수정: lazy 생성 + 실패 시 정적 폴백(사전 렌더 PNG 또는 단색 카드).
- 성능: 픽셀당 최대 (post 28 + seg 40(+40 두 번) + pre 40) 연산 × aa 4샘플(내보내기) × 1080×1350 ≈ 1.46M 픽셀. 화면(aa 2)도 상시 렌더하면 부담. REPORT도 인정("실기기 비용 미측정"). 화면 카드는 Picture/Image 캐시가 필수(이미 목록에 있음). 호출 쪽이 한 번만 만들게 `useMemo`는 있으나 캔버스 재그리기 주기 확인 필요.
- `for` 루프의 경계가 상수이고 uniform으로 `break`하는 방식은 ES2 호환이라 규칙 위반은 아니다. 다만 `postA[27 - i]` 같은 **루프 인덱스 역방향 인덱싱**은 일부 드라이버에서 느리다. 배열을 역순으로 미리 넣어 두면 단순해진다.

### 2-3 웹/네이티브 분기
- 분기 구조(`renderImage.tsx` / `.web.tsx` + 같은 `DreamCardArt`)는 깔끔하다. 그림은 공유, 글만 분리 — 올바른 선택.
- 네이티브: `fontFamilies: ['Noto Serif KR','AppleMyungjo','serif']` — Noto Serif KR이 Skia 글꼴 관리자에 **등록되는지 코드에서 확인 못 함**. 미등록이면 Android에서 시스템 serif(한글 글리프 대체) 로 떨어져 카드 글이 기기마다 다르게 나온다. 이탤릭 영문도 Cormorant 미지정(`Cormorant` 계열이 목록에 없음) — **네이티브 카드 글꼴은 art-bible 6절(본명조·Cormorant Garamond)과 다르다**.
- 네이티브 세로쓰기 y 보정(`size*(1 + i*1.32)`)과 웹(`0.95 + ...`)이 달라 **두 플랫폼의 글 위치가 다르다**(손 보정값). 네이티브는 한 번도 안 돌려 봤다고 보고서가 인정 — **네이티브 출력은 검증되지 않은 상태**다.
- 네이티브는 PNG를 base64 문자열로 반환: 1080×1350 PNG는 수 MB, 이후 expo-file-system 저장·공유 연결에서 메모리 부담 주의. 파일 URI 반환이 낫다.
- 화면용 글(RN Text)과 공유 이미지 글(Paragraph/Canvas fillText)이 **서로 다른 렌더 경로**라서 "화면에서 본 카드 = 공유되는 카드"가 보장되지 않는다. 접근성상 RN Text 선택은 합리적이나, 비교 스냅샷 하나는 필요.

## ③ 커밋 전 필수 vs 다음 단계

### 커밋 전 필수 (코드·정직성)
1. **`marbleFx` 모듈 최상위 throw 제거** — lazy + 폴백. (높음, 앱 전체 크래시 가능)
2. **uniform 총량을 코드로 고정**: 스칼라 포함 vec4 수를 계산하는 테스트(또는 주석 정정). 상한을 낮추는 쪽(예: pre 32/post 24/seg 32 → 약 176 + 스칼라) 검토. 근거 없는 "256 안쪽" 문구는 수정. (중간)
3. **결정성 테스트 보강**: 고정 입력의 시드/op 해시 스냅샷, 자르기 발동 감지(자르기 전 길이 ≤ 상한을 검사하거나 자르기 발생 시 실패). (중간)
