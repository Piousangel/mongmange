# 앱 v1.2 독립 리뷰 (2026-11-20, 리뷰어 = 작성 비참여)

대상: 미커밋 변경 전체(카드 통합·앨범·대체 획 입력·글꼴 서브셋·SLIDE_DRIFT_W). 직접 실행: `pnpm typecheck` 통과(core·mobile), `cd packages/core && npx vitest run --testTimeout=200000` 13파일 131테스트 통과. 직접 고치지 않았다. 캡처 01·04·05·09·10 확인.

## 필수 수정(커밋 전)
1. **[높음] `apps/mobile/src/game/storage.ts` — 범위 밖 변경이 섞여 있다.** MMKV 로드가 실패하면 조용히 메모리 저장으로 대체한다(앱 종료 시 세이브 소실, D-13 위반 소지). 이 리뷰 시작 때는 `git status`에 없었고 중간에 나타났다(다른 세션이 수정 중). 이번 v1.2 커밋에 넣지 말고, 넣으려면 개발 빌드 한정(`__DEV__`)으로 막고 운영에서는 throw 또는 오류 노출. 현재 코드는 운영 빌드에서도 무음 폴백이다.
2. **[중간] 서브셋 누락 글자 검사 수단이 없다.** 지금은 맞다(소스 한글 누락 0, 비ASCII 중 누락은 ↗↘↙↖뿐이며 Pretendard 쓰는 패널 화살표라 영향 없음 — 내가 소스 전수 비교로 확인). 그러나 글자 목록은 `subset.mjs`를 돌릴 때만 갱신되고, 이후 소스에 KS X 1001 밖 글자(예: 희귀 한글·한자)가 들어가도 아무것도 실패하지 않는다. 대응: vitest 1건 추가(소스 문자열 스캔 vs `.subset.chars.txt`) 또는 `pnpm check:font`를 typecheck에 묶기. 근거 문서(원장·DECISIONS)에 이 검사 방법 한 줄.
3. **[중간] 진행·결정 기록 누락.** 글꼴 서브셋(8.4MB→1.4MB, 용량 결정)·카드 통합·대체 획 패널이 DECISIONS.md에는 D-12 변경 이력 1줄(SLIDE_DRIFT_W)뿐이다. D-08(접근성)에 "대체 입력 = 자리·방향·길이·휨 고르기(스크린리더), 두 점 고르기는 보이는 사용자용" 한 줄이 필요하다. `.claude/progress.md`에는 "assist-stroke 테스트 1건 실패 중"이 남아 있는데 지금은 통과이므로 갱신.

## ① 카드 통합 성능
- 썸네일 캐시 48장: 폭 약 108pt × PixelRatio≤2 → 216×270×4B ≈ 0.23MB/장, 48장 ≈ 11MB. 문제 없음. 단, 축출한 SkImage를 `dispose()`하지 않는다(네이티브 메모리는 GC·finalizer 의존). 앨범 열고 닫기를 반복하는 긴 세션이면 `cache.delete` 시 dispose가 안전하다(화면에 표시 중인 이미지는 키가 다시 잡히므로 주의).
- 실패(`null`)는 캐시되지 않고 재시도도 없다 → 썸네일이 영구 빈 네이비 상자. 낮음: 앨범 재열기에서 다시 시도되므로 허용 가능.
- 줄 세우기 큐는 직렬이라 카드 수십 장이면 마지막 썸네일까지 첫 열기에 수 초(카드당 셰이더 2~3개). 화면 밖 카드는 찍지 않는 지연(보이는 행만)이나 첫 6장 우선이 낫다. 현재 `items` 전체를 즉시 큐에 넣는다. 카드가 며칠 쌓이면(7일 = 7장, 이후 30장+) 의미 있다. 낮음.
- **아침 연출 중 셰이더 비용(주의)**: `developed`가 서자마자 라이브 `DreamCard`(Canvas, 마블링 셰이더 2~3개, `makeDreamArt` 표본 2)가 마운트된다. 이때가 물 빠짐 1.6초(NightWater 셰이더 캔버스 애니메이션) 구간과 겹쳐 첫 프레임 셰이더 컴파일·JS 쪽 `makeDreamArt` 계산이 연출 프레임을 잡을 수 있다. 카드는 opacity 0 상태로 이미 그려지므로 컴파일 비용은 물 빠짐 시작 시점에 몰린다. 중급 Android 실기기 확인 필요(웹 캡처로는 안 보임). 완화: 물 빠짐 전에 `thumbImage`와 같은 방식으로 이미지로 미리 찍어 두고 연출 중에는 `SkiaImage`만 움직이게(카드 크기 한 장이라 저렴), 연출 후 라이브로 교체하거나 그대로 이미지 사용. `Animated.View`의 opacity+scale은 매 프레임 오프스크린 합성이라 이 구조에서는 이미지 쪽이 안전하다.
- 카드 위 글과 아래 큰 글이 같은 문장을 두 번 보여 준다(09 캡처). 의도(카드는 공유용 작은 글, 아래는 읽는 글)로 주석에 있다. 디자인 판단 사안이며 중복으로 읽힌다 — 오너 확인 대상.
- 카드 아래 글·보내기·"낮으로" 사이 여백은 캡처에서 충분하나 글꼴 크기 확대(fontScale)에서는 `cardText`가 절대 위치라 하단 버튼과 겹칠 수 있다(확인 못 함).

## ② 대체 획이 정본 제한·부착 규칙을 지키는가
- 960 조합 테스트가 점 ≤512, 6초 이하, 시간 단조, 최소 길이, 부착값 유한을 검증한다. 정본 제한 준수는 맞다. 시작 간격 0.12W·길이 0.35/0.6/0.9W·점 41개는 `STROKE` 한도 안.
- 그러나 **테스트가 부착 결과의 질은 보지 않는다.** 내가 960 조합 × 핵 크기 0·6으로 `attachStroke`→`strokeSpine`을 돌려 보았다. 라벨은 wrap 770·base 190(약 20%가 바닥 띠 받침). 최대 돌출 0.33(L2 상한 0.33W와 같음, 초과 없음). 갈고리형(휨 ±2 + 긴 길이)과 바닥선 아래 처짐: 임의 기준(핵 바닥 +0.3W)으로 핵 크기 0에서 33건, 6에서 14건이 바닥 쪽에 내려간다. 받침(base) 규칙상 의도된 띠인지 처짐인지는 나(코드 읽기)만으로는 구분 못 한다 — 아트 판정 필요. 작성자가 남긴 위험은 실재하되 규칙 위반(돌출·금지 자리) 수준은 아니다. 권장: 테스트에 "base 라벨 비율 ≤ 25%", "돌출 ≤ 0.33W" 두 단언을 추가해 회귀를 막는다.
- 기본값 `place 2, dir 4, len 0, bend 1`은 캡처(01)에서 옆구리에 붙는 그림이 나온다. 휨 부호는 코드(긋는 방향 오른쪽 = 화면 시계 90°)와 라벨이 일치한다. 아래로 긋는 획에서 "오른쪽으로 휨"은 화면 왼쪽(몸 쪽) — 화면 기준 직관과 반대일 수 있다. 라벨 "긋는 방향 기준"을 패널에 한 줄 적는 것이 안전. 낮음.
- 접근성: 줄마다 `adjustable`+increment/decrement, ◀▶는 접근성 트리에서 숨김, 두 번 탭 문제 회피 등 D-08·C10-③ 취지에 부합한다. 거절(하루 한 획) 시 패널을 닫아 버려 스크린리더 사용자가 이유 문구를 못 들을 수 있다 — `announceForAccessibility` 없이 `info` 텍스트에만 의존하면 안 되므로 확인 필요(`setInfo`가 live region인지 미확인).
- 아침 카드: `cardK=0`(opacity 0)일 때도 접근성 요소로 노출된다. 낭독은 `DRAIN_MS+CARD_MS` 뒤 한 번 더 알린다 → 이중 낭독 가능. 낮음.

## ③ 글꼴 서브셋·OFL
- 2,694자 = 소스 글자 + KS X 1001 한글 2,350 + ASCII·Latin-1·부호·호환 자모. 소스 한글 누락 0건 확인(내 스크립트로 `apps/mobile/src`, 전수). 8.4MB → 1.4MB. 도구는 결정적.
- OFL: 저작권 줄에 Reserved Font Name 선언 없음(OFL 사본 1줄 확인) → 이름 유지 가능. OFL 원문을 `assets/fonts/OFL-GowunBatang.txt`에 둠(2항). 파일명에 `.subset` 표기. 주의: OFL 5항·고지는 앱에서 사용자가 볼 수 있는 "오픈소스 라이선스" 화면 또는 스토어 설명에 글꼴 이름·저작권 고지를 두는 것이 안전하다(번들 폴더에 파일만 있으면 앱 안에서는 안 보임). 원장에 이 할 일이 없다. 낮음~중간(출시 전).
- `@expo-google-fonts/gowun-batang`을 devDependency로 옮긴 것은 맞다(원본은 서브셋 입력용). `pnpm-lock.yaml` 변경 포함 확인 필요.
- 한국어 전용 앱이라 현재는 충분. 영어판 때 라틴 글리프가 Gowun에 없으면 다른 글꼴로 대체됨.

## ④ SLIDE_DRIFT_W와 snapshot
- 변경 범위가 새 획으로 한정(slidCase = 앵커나 손 무게 중심이 금지 자리)이고 저장된 attach는 건드리지 않는다. `attachVersion` 유지가 D-13 방침(빗 변경 시와 같은 선례)과 일치한다. 정당.
- 스냅숏: `quilt916`만 바뀜(moon·empty 불변). 원인은 `day7ClumsyRecords`의 6번째 획(앞 위 지그재그) 자리 변화 — 이 획이 바로 고치려던 사례이므로 정당. 다만 해시만 바꾸지 말고 "6번 획이 이전엔 어디였고 지금 어디"라는 수치 단언이 `attach-slide.test.ts`의 110° 미만 단언으로 있어 보완된다. 확인함.
- 한계: 새 획의 부착 결과가 같은 raw에 대해 빌드마다 다르다. 세이브에 attach가 저장되므로 안전하나, `pose.ts`의 데모 레코드(day7ClumsyRecords)는 매번 재계산이라 이후 카드 REPORT 캡처가 달라진다. 이미 반영.
- `slideOf`의 slid 임계 6°와 문서의 "금지 자리 15% 초과" 설명이 별개의 기준이다. 문서에 구분 한 줄 권장. 낮음.
