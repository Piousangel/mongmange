## 지적

### M1 (중간) 8-1절 대조표의 '첫 화면' 전제가 이 앱에서 틀렸다 — 네이티브 복구 범위가 거의 없다
- 근거: expo-updates의 '첫 화면' = RN 마커 `CONTENT_APPEARED`(Android `ErrorRecovery.kt:79-83`) / `RCTContentDidAppear`(iOS `ErrorRecovery.swift:292·306-308`). 이 순간 `markSuccessfulLaunchForLaunchedUpdate()`가 불려 그 판은 '성공 실행 1'이 된다(`ErrorRecoveryHandler.kt:76-82`).
- 우리 `apps/mobile/index.ts:31`의 Boot는 **App을 require하기 전에** 한지색 `View`를 그린다 → 콘텐츠가 즉시 '나타남'. 따라서 App 모듈 로드·첫 화면 렌더·초기 store 처리에서 나는 치명 오류는 모두 '첫 화면 뒤(성공 판)'로 분류된다. 네이티브가 이전 판·내장판으로 되돌리는 경우는 **번들 평가 중 오류(`index.ts` 모듈 평가·import 체인)뿐**이다.
- `ota-self-host.md:151` 표 1행은 일반론으로는 맞지만, 독자(PM)는 '새 판이 화면 뜨기 전에 죽으면 네이티브가 알아서 되돌린다'로 읽는다. 실제 V12a·V10 같은 화면 코드 OTA 결함은 거의 전부 2행(앱 JS + 서버)으로 간다.
- `ota-self-host.md:156` ERROR_RECOVERY_ONLY 효과 서술도 부정확: 첫 화면 뒤에는 파이프라인이 `WAIT_FOR_REMOTE_UPDATE, CRASH`만 남기므로(`ErrorRecoveryHandler.kt:79`) 받은 판을 **띄우지 않고** 그대로 크래시한다. 다만 받은 판은 DB에 남아 **다음 콜드 스타트**에 실행된다. 즉 효과는 '첫 화면 뒤 10초 창 안의 치명 오류에서 네이티브가 최대 5초 새 판을 받아 둔다'(`ErrorRecovery.kt:69-76`, `REMOTE_LOAD_TIMEOUT_MS = 5000`)이다.
- 요구: 8-1 표에 'Boot 빈 화면 때문에 1행은 번들 평가 오류에만 해당' 한 줄, 156줄 서술 정정.

### M2 (중간, 기존 코드지만 D-22 주장과 직결) App 로드 실패는 크래시가 아니라 '영구 빈 화면' — 크래시 루프 판정·네이티브 복구 모두 못 본다
- `apps/mobile/index.ts:15-18`의 `require('./App')`는 `.then` 안이라 던지면 `ready`가 거부되고, `index.ts:24`의 `void ready.then(...)`은 거부를 처리하지 않는다. RN 릴리스에서 미처리 약속 거부는 치명 오류가 아니므로 앱은 **한지 빈 화면에 멈춘 채 살아 있다**.
- 사용자는 홈으로 나가거나 앱을 내린다 → `background` → `open=0, crash=0`(깨끗한 끝). `CRASH_LOOP_AT` 경로가 절대 켜지지 않는다. 구제는 '다음 날 첫 열기의 하루 1회 확인 → 그다음 콜드 스타트'뿐(최대 1일 이상).
- 권고(작성자 판단): `ready.catch`에서 오류를 다시 던져 전역 치명 처리로 보내거나(→ 네이티브 10초 창 + 크래시 루프 판정이 본다), 최소한 OTA 체커에 '빈 화면 실패' 표시를 넘겨 하루 제한을 건너뛰게. 시험으로 고정할 것.

### L1 (낮음, 실기기 확인 필요) iOS 앱 전환기에서 내리면 '크래시'로 세어 하루 1회가 무력해질 수 있다
- `checker.ts:176`은 `background`만 깨끗한 끝으로 본다. iOS에서 앱 전환기를 열면 AppState는 `inactive`이고, 거기서 카드를 쓸어 올려 종료하면 `background` 이벤트 없이 끝나는 경우가 있다.
- 이 습관을 가진 사용자는 2회 뒤부터 **매 실행이 크래시 루프 판정**(`checker.ts:168-169`) → 매 콜드 스타트마다 확인 요청. 정확성 문제는 아니지만 'D-22·PM ⑤ 하루 1회'와 서버 부하 가정이 깨진다. 문서 155줄 ⓒ의 '한 번 더 건너뛰는 것뿐'은 이 경우 과소 서술.
- 권고: `inactive`도 `open=0`으로(다시 `active`면 1로 돌아오므로 손해 없음) 하거나, 리허설 항목(8-1 대조표 5)에 'iOS 전환기 종료 2회 → 다음 실행 요청 수' 추가.

### L2 (낮음, 영향은 치명) 진입점 방어가 없다 — 내장 번들에서 OTA 코드 예외 = 복구 불가 크래시
- `apps/mobile/index.ts:6`의 정적 import는 끌어올려져 `registerRootComponent`보다 **먼저** `src/ota/index.ts → src/game/storage.ts`를 평가한다(MMKV 생성, 운영에서 실패 시 throw — `storage.ts:17-18`). `startOta()`(`ota/index.ts:17-29`)도 try 없이 `Platform.OS`·`createOtaChecker`·`AppState.addEventListener`를 부른다.
- 현재 코드에서 실제로 던질 경로는 사실상 없다(`optionalModule`·`readRecord`·`writeRecord`·`run`이 모두 잡음, `void checker.start()`는 거부되지 않음 — 변이 1로 확인). 동기 등록 규칙(11-20 S25)도 지켜진다(모두 동기).
- 그러나 빌드 2 **내장 번들**에서 여기서 던지면 번들 평가 오류 → 되돌아갈 이전 판이 없음 → 매 실행 크래시, OTA로도 못 고침(받는 코드 자신이 죽으므로). MMKV 실패는 이전에도 App 로드에서 (빈 화면으로) 실패했으므로 새 위험은 '순서'뿐이다.
- 권고: `startOta` 본문 전체 try/catch, `kv`는 `startOta` 안에서 지연 require(실패 시 OTA만 끔). 변이 8·9가 생존하므로 정적 시험 1개(진입점에 `registerRootComponent(` 뒤 `startOta();`가 있고, `startOta` 본문이 try로 감싸져 있음) 추가.

### L3 (낮음) 시험 공백 — '시도를 먼저 기록' 미고정
- 변이 5 생존. 문서·주석이 강조하는 '확인 도중 죽어도 그날 1회'(`checker.ts:146-149`)를 잡는 시험이 없다. 'hang 상태에서 checker를 버리고(죽음) 같은 날 새 launch → later' 시험 1개면 잡힌다. 다만 이 경우 크래시 1회는 crash 세기로도 이어지므로 의도대로인지 함께 적을 것.
- 8-1 대조표 165줄 '변이 11 잡힘'은 근거 위치(어떤 변이였는지)가 없다. 이 리뷰의 표로 대체하거나 출처를 적을 것.

### 정보(문제 없음 확인)
- **적용 시점(①)**: `fetchUpdateAsync`가 받은 판은 DB에 들어가고 다음 실행의 런처 선택 정책(같은 런타임 중 최신)이 고른다. `fallbackToCacheTimeout: 0`·`NEVER`라 시작 시 네트워크 대기 없음. `rollBackToEmbedded` 지시도 받기만 하면 다음 실행에 내장판. `reloadAsync` 금지는 정적 시험·호출 수 시험 둘 다로 고정(변이 2). **작성자 결정 ① 승인.** 대가(오래 사는 세션의 지연)는 문서에 정직하게 적혀 있다.
- **시간 초과 의미**: JS `withTimeout`은 경쟁만 끊고 네이티브 요청은 계속된다. 늦게 끝난 받기도 DB에 남아 다음 실행에 적용 — 무해. 같은 날 재확인은 `last`로 막힘.
- **오류 의미**: 개발 모드·`isUsingDeveloperTool`이면 JS가 `ERR_UPDATES_DISABLED`를 던짐(`src/Updates.ts:244-253, 331-340`) — 우리는 `__DEV__`면 모듈을 부르지도 않고, `isEnabled`(`Updates.ts:26`, 상수)로 한 번 더 막는다.
- **하루 1회(3)**: `localDay`는 현지 날짜 문자열 비교라 시계를 되돌리거나 시간대를 바꾸면 날짜가 '다르다'로 보아 최대 1회 더 묻고 `last`를 새 값으로 덮는다. 영구 잠김 없음(미래 시각 `last`도 다음 판정에서 풀림). 시험은 없지만 위험 낮음.
- **첫 실행 판정**: `mong.ota` 없음 = 첫 세션. 깨진 값은 첫 실행 아님(시험 있음). 빌드 1 → 빌드 2 업데이트 사용자는 첫 세션 1회를 쉬고 다음부터 확인 — 의도와 맞음. (MMKV `getString`이 늘 던지면 매번 첫 세션 → 영원히 확인 안 함. 운영 MMKV에서는 현실성 낮음.)
- **MMKV 쓰기와 크래시**: MMKV는 mmap 기반이라 JS 치명 오류·프로세스 kill 뒤에도 쓴 값이 남는다(커널 패닉·전원 차단 제외). `open=1`을 `start()` 첫 동기 구간에서 쓰므로 직후 크래시도 세어진다.
- **웹 분기**: Metro는 `./src/ota` 디렉터리를 `index.web.ts`로 해석 → 웹 번들에 expo-updates·MMKV 경로 없음. `index.web.ts` no-op.
- **Skia 순서**: `startOta()`는 `skiaReady`·App require와 무관하게 동기 실행, 첫 렌더 전. 네이티브 `skiaReady`는 즉시 해결이라 경합 없음.
- **개인정보(5)**: 저장 = 숫자 5칸(`v·first·last·open·crash`, 시험 고정). 요청 헤더는 expo-updates 네이티브가 만들며 가드 플러그인의 상수 덮기(`EAS-Client-ID` 0 UUID·`Expo-Fatal-Error: -`·빈 `Expo-Recent-Failed-Update-IDs`)가 그대로 적용 — `ota-config.test.ts` 통과로 덮기 순서 유지 확인. Extra-Params 미사용. 식별자 0 확인.

**③ 득실**
- 득: M1 때문에 이 앱의 실제 결함은 대부분 '첫 화면 뒤'다. ERROR_RECOVERY_ONLY면 시작 후 ~10초 안의 치명 오류에서 네이티브가 최대 5초 새 판을 받아 둔다 → **문서 '남은 한계 ⓐ'(확인·받기 전에 죽는 루프)를 정확히 메운다.** JS가 죽어도 동작하고, 하루 제한·첫 세션 규칙과 무관. 첫 화면 전 오류에서는 고친 판을 바로 띄운다.
- 실: 요청은 **치명 오류 때만** 하나 더(`UpdatesUtils.kt:210` — 시작 시 자동 확인은 여전히 false). 헤더는 같은 상수 덮기(V21 유지). 첫 세션 크래시면 '첫 실행 요청 0' 리허설 항목에 예외가 생김(문서에 적을 것).
- fingerprint: `checkAutomatically`는 `fingerprint.config.js`의 제외 4칸(`requestHeaders`·`codeSigningCertificate`·`codeSigningMetadata`·`enabled`)에 없으므로 **런타임 해시가 바뀐다**. 모든 채널에 같은 값이라 채널 간 일치(ota-config '채널 env 셋에서 런타임이 같다')는 유지되고, 빌드 2가 어차피 새 런타임이므로 동결 전이면 비용 0. 동결 뒤 바꾸면 기존 바이너리와 OTA가 갈라진다 → **12-19 전 결정 필수.**
- 가드 관계: `enabled=false`(ready false·인증서 없음)면 복구 경로도 꺼진다 — fail-closed와 일치.
