## 1. 시각

### 1-1. PM 판단에 대한 의견
- **7일차: 동의하고, 심각도는 PM이 본 것보다 높다(치명).** `day7.png`를 직접 보면 검은 덩어리 + 흰 점 둘 + 오른쪽 위 가는 털 뭉치 + 아래쪽 울퉁불퉁한 가장자리다. 이건 "우아하지 않다"에서 끝나지 않는다. 아트 1-1이 "가장 큰 위험"으로 적은 **검댕(susuwatari)** 실루엣이고, 1-4 금지표의 "털·톱니 가장자리"에 정면으로 걸린다. OPERATING 0-1의 "다른 게임에서 본 것 같은가?"에 "예(지브리 검댕)"라고 답하게 된다. REPORT 7절은 이 항목을 "획이 몸을 감싸는가: 미통과"로만 적었는데, 금지표 판정(9절)에서 "털 가장자리: 7일차 획 끝은 여지"로 낮춰 적은 건 과소평가다.
- **0일차: 대체로 동의, 단 '좋음'은 형태까지만.** 비율·바닥·눈 둘·빈자리는 맞다. 하지만 빗은 REPORT 스스로 미통과(털 뭉치·불꽃)다. 0일차 빗이 이미 불꽃처럼 보이면, 7일차에 빗이 0.3W로 자라고 주변 획 끝이 겹치면서 털 뭉치가 커진다. 7일차 문제의 씨앗이 0일차에 있다.
- **밤: 부분 반박.** 대비·감은 호·무섭지 않음은 통과가 맞다. 그런데 밤 몸은 7일차와 같은 실루엣이고, 오른쪽에 가는 가닥 셋이 지느러미·털처럼 삐져 있다. 밤이 괜찮아 보이는 이유는 은회색 몸 + 밝은 테가 대비를 낮춰 들쭉날쭉한 윤곽을 덜 드러내기 때문이다. **밤 통과를 "단일 coverage 방식이 된다"는 독립 근거로 쓰면 안 된다.** 7일차를 고치면 밤도 다시 캡처해야 한다.

### 1-2. 7일차가 한 덩어리 얼룩이 되는 원인(중요한 순서)
1. **정본끼리 부딪친다(원인의 뿌리).** 아트 4절 팔레트는 `body` = "핵 + 새 획, 한 coverage", 1-3은 "0~7 = 짙은 먹"이다. D-13은 몸 전체를 마스크 하나로 합쳐 **한 번만** 칠한다. 이 셋을 지키면 7일차의 획 7개는 정의상 **실루엣 굴곡으로만** 보일 수밖에 없다. 그런데 비교 기준 `02a` 가운데는 획이 몸과 다른 농도(회색 담묵)·비백·몸과의 틈으로 따로 읽힌다. 정본 텍스트와 기준 이미지가 서로 다르다. 구현 버그가 아니라 정본 충돌이다.
2. **D-11과 다르게 구현했다(REPORT에 안 적힘).** D-11은 "획은 `Vertices`(텍스처 좌표 = 획 길이·폭)에 비백 셰이더를 입힌다"이다. 지금 구현은 획을 흰 마스크로만 그려서 uv를 버린다(`Mongmangi.tsx` mode A, `color="white"`). 비백이 없으니 획이 몸과 구별되는 단서가 하나도 남지 않는다. REPORT 2절 "구현"과 11절에 D-11 이탈을 적어야 한다.
3. **부착 비용이 틈을 없앤다.** `attach.ts` 비용은 `e = sd − 0.04`로 스파인을 표면 밖 0.04W에 두고, 리본 반폭은 0.0375W다. 그래서 리본 안쪽 가장자리가 핵 표면에 **딱 맞닿는다.** 몸과 획 사이에 종이가 한 줄도 안 보인다. 여기에 닫힘 필터(팽창 → 침식 1.5pt) + 블러 σ1.2 + 알파 램프 임계(0.4~0.6)가 사실상 메타볼처럼 오목한 자리를 메운다. 결과는 "몸을 감싼 획"이 아니라 "윤곽이 두꺼워지고 울퉁불퉁해진 몸"이다. (발견 2의 '셋째 눈' 종이 점을 없애려고 넣은 닫힘이 같은 효과를 키운다.)
4. **획 모양이 가늘고 끝이 실처럼 빠진다.** 폭 0.075W(7일차 W 80pt 기준 약 6pt)에, 끝 38% 구간이 폭 12%까지 줄어든다(mesh v2, L2 테이퍼면 6%). 가는 리본 여러 개가 같은 방향으로 실처럼 빠지면 털로 읽힌다. 특히 오른쪽 위는 빗 세 가닥(역시 테이퍼) + 앞 두름 끝이 한곳에 모여 불꽃·털 뭉치가 된다.
5. **7일차 포즈가 `02a`를 닮지 않았다.** `day7Records`는 7획 중 4획이 0.35W 이하의 짧은 호이고, 모두 반지름 0.57~0.7W에서 그었다(그때 표면 바로 바깥). 짧은 획 여러 개를 윤곽에 바짝 붙이면 너덜너덜해진다. `02a` 가운데는 크고 굵은 두름 1개 + 받침 2개다. 받침 두 획은 `y ≈ 0.445`로 바닥선 위에 놓여 아트 1-1의 "평평한 바닥"을 깨고 "받침이 바닥 굴곡처럼" 보이게 한다(REPORT도 경고로 적음).
6. **회전 + 이동만으로는 볼록한 몸을 감쌀 수 없다.** 강체 변환은 획의 곡률이 핵과 맞을 때만 몸을 따라간다. 곡률이 다르면 한 점에서 접하고 나머지는 접선으로 뻗어 갈고리·꼬리가 된다(REPORT 0절 ③). L3 `bend`는 표면 거리 d를 호 길이 비율로 줄이는 반경 압축일 뿐이라, 곡률을 둘레에 맞추는 '감기'가 아니다. 그래서 L1~L3 결과가 거의 같다.
7. **판정 지표가 이 실패를 못 본다.** "핵 면적 ≥75%"(88% 통과)는 면적만 잰다. "획이 따로 읽히는가", "윤곽 거칠기"는 재지 않는다. 88%로 통과했는데 그림은 검댕이다. 7일차용 지표를 하나 더 둬야 한다(예: 윤곽 곡률 부호 변화 횟수, 끝이 0.02W 이하로 빠지는 가닥 수 상한).

### 1-3. REPORT 10절 결정 요청 1~4에 대한 의견
1. **금지 자리 ① 상한(45° vs 빗 뿌리 73°)** — (가)가 맞는 방향이다. 다만 숫자를 손으로 75°로 바꾸지 말고 **빗 기하에서 파생**시켜라(맨 아래 가닥 뿌리 각 + 여유 6°). 빗 길이·각도가 성향(D-02)으로 바뀌면 금지 자리도 따라가야 하기 때문이다. (나) 빗 피치를 줄이면 아트 1-1의 "간격 = 굵기 × 1.2"를 깨고 털 뭉치가 더 촘촘해진다. 반대한다. (다) 빗 인접 벌점은 (가)의 보조로만 둔다. 함께 고칠 것: 지금 금지 자리 검사는 **앵커 θ 하나**만 본다(`isForbidden(a.theta)`). 획 몸통이 금지 자리를 덮는 경우가 정수리 '넷째 가닥'의 원인이다. 점 단위 비율로 판정하고 비용 가중치(지금 2)를 올려야 한다.
2. **L단계 차이가 작음** — 동의. 이 상태로 D-12 외부 테스트(5명 × L1~L3)를 돌리면 세 단계가 같은 자극물이라 결과가 의미 없다. 숫자만 조정(상한 낮추기, 휨 30% → 더 크게)하지 말고 **L3을 진짜 감기로 바꿔라**: 획을 (앵커에서 잰 호 길이 s, 법선 거리 n) 좌표로 바꾼 뒤 핵 윤곽을 따라 다시 놓는 매핑에, 휨 비율을 섞는다. L2 상한도 7일 이하에서 0.5W는 너무 크다(빗이 0.3W인데 유저 획이 그보다 더 나간다). 0.3~0.35W를 제안한다. 비교 자극물은 BRIEF·D-12대로 실제 손가락 획 20개로 만든다(지금은 3개).
3. **"감싼다"가 약함** — 가장 중요한 결정이고, 아트 판단만으로 끝낼 일이 아니다. 아트 4절·1-3(새 획 = 몸 색, 한 coverage)과 D-13(한 번만 칠한다)을 **함께 고쳐야 하는 정본 개정**이다. 제안:
   - **가장자리(블러·테·번짐)는 단일 coverage로 유지한다.** 이음매 문제는 이미 풀렸고 되돌릴 이유가 없다.
   - **안쪽 농도·비백만 획별로 다르게 칠한다.** 같은 레이어 안에서 마스크 알파 = coverage, 다른 채널 = 획 톤(핵 0, 새 획 0.15~0.25 담묵)으로 그리고 칠 셰이더가 그 채널을 읽는다. 또는 마스크로 칠한 뒤 획 리본을 같은 마스크로 클립해 담묵·비백을 덧칠한다. 겹친 자리 농도 띠가 안 생기도록 톤은 max로 합친다.
   - **앵커 근처 말고는 몸과 0.02~0.04W 틈을 허용한다.** `02a`가 "감싼다"로 읽히는 건 획과 몸 사이 종이 한 줄 덕분이다. 그러면 닫힘 필터는 앵커 근처에만 필요하다(또는 틈 폭이 닫힘 반경보다 크게).
   - 획 기본 폭을 0.12~0.16W로 키우고 끝 최소 폭을 30% 이상으로 둔다(실처럼 빠지는 끝 금지).
   - 결정 전에 위 조합으로 **정지 캡처 2~3안을 반나절 안에** 뽑아 `02a`와 나란히 보고 고른다. "획 끝 비백만" 또는 "톤 1단계만" 하나로는 부족하다고 본다. 비백은 끝만 바꾸고, 톤만으로는 틈이 없어 여전히 한 덩어리다.
4. **0일차 빗이 털 뭉치·불꽃** — 동의. 빗 끝을 실 테이퍼 대신 붓을 뗀 둥근 끝 + 짧은 비백으로, 굵기를 0.06W 이상으로 시작하고, 위 가닥은 수평에 더 가깝게(±15° 안에서 0~5°). 0일차 빗이 '털'이 아니라 '세 번 그은 붓'으로 읽혀야 7일차도 산다.

## 2. 코드

### 2-1. core 순수성 — 통과

### 2-2. worklet TDZ 위험 — 중간(지금은 안전, 다시 깨질 수 있음)
- Reanimated/worklets 플러그인은 `function f() { 'worklet' }` 선언을 `const f = ...` 꼴로 바꾸고 클로저를 정의 시점에 잡는다. 그래서 **함수 호이스팅이 사라진다.** 모듈 최상위에서 아래에 선언된 worklet을 부르거나 참조하면 TDZ가 난다(REPORT 10-6의 그 한 번).
- 지금 순서를 확인했다: core.ts(`CORE = coreParams()`는 coreParams 아래), eyes.ts(`SHAPES`는 eyeShape 아래), simplify/attach/ribbon/pose 모두 쓰는 함수가 위에 있다. **지금은 안전하다.**
- 문제는 막아 주는 장치가 없다는 것이다. Vitest는 플러그인 없이 돌아서 이 오류를 못 잡는다. 누가 함수 순서를 바꾸면 웹·네이티브에서만 터진다. 고칠 방법(둘 중 하나): ESLint `no-use-before-define`(functions: true)를 core에 켠다, 또는 core 각 파일을 worklets 바벨 플러그인으로 변환해 import해 보는 테스트 1건을 둔다.

### 2-3. 세이브 봉투·마이그레이션 테스트 — 일부는 동어반복
- **① 결정성**: 같은 프로세스에서 같은 함수를 두 번 불러 같다는 부분은 JS에서 당연하다(동어반복). 의미 있는 건 직렬화 왕복 뒤 메시가 같다는 뒷부분뿐이다. 진짜 위험은 엔진 차이(Hermes UI 런타임 vs Node V8의 `Math.sin/pow` 끝자리)다. 부착 결과는 저장하니 괜찮지만, 메시는 로드할 때마다 다시 만든다. 기기 간 공유가 없으니 MVP에선 낮음.
- **② 마이그레이션 "끝점 차이 < 0.03W"는 구조상 항상 0에 가깝다(동어반복).** `dejitter`는 끝점을 고정하고, RDP는 첫·끝 점을 늘 남기고, Catmull-Rom 재표본은 첫·끝 제어점을 지난다. 그리고 두 버전에 같은 `attach`를 준다. 그러니 v1·v2 설정을 무엇으로 바꿔도 끝점은 같다. 이 테스트는 "메시를 고쳐도 몸 자리가 안 바뀐다"를 증명하지 못한다. 고칠 방법: (a) 앵커(`attach.ax, ay`)에 가장 가까운 v2 스파인 점이 핵 표면 0.02W 안에 있는지(= v2에서도 획이 몸에서 안 뜨는지), (b) v1·v2 스파인 사이 하우스도르프 거리 상한, (c) 앵커가 끝점이 아닌 획(가운데가 몸에 닿는 획)으로 검사한다. 지금 테스트 ④도 시작점 = 앵커인 획만 쓴다.
- schema v1 → v2 마이그레이션 자체(숫자 배열 → base64, taper 채우기)는 실제 변환을 한 번 거치므로 의미가 있다. 다만 v1 "구형" 봉투를 지금 코드의 `attachStroke`로 만들어서, 실제로 존재한 적 없는 형식이다. 스파이크 01 세이브가 없었으니 받아들일 수 있다.
- 빠진 것(중간): 미래 버전(`schemaVersion: 3`) 거부 테스트, 깨진 base64·홀수 바이트 입력, 모르는 `meshVersion`일 때 조용히 현재 버전으로 떨어지는 동작(`SIMPLIFY_VERSIONS[v] ?? 현재`, 새 앱 세이브를 옛 앱이 읽으면 모양이 몰래 바뀐다) 중 하나는 있어야 한다.
- **③ 크기 테스트**는 의미가 있지만 압력 채널을 넣은 최악에 가까운 경우다(RNGH v3에는 압력이 없다). 24획 43KB면 여유가 있다. 통과.
- int16 양자화 범위 ±8W: 화면 세로가 0일차 W로 약 12W이고 핵이 화면 60% 높이에 있어 위쪽 끝이 약 7.4W다. 지금은 들어가지만 여유가 작다. 화면 끝에서 그은 획은 잘린다(`clamp16`). 낮음, 주석으로 남길 것.

### 2-4. 테스트가 구현을 베끼는가
- `금지 자리 미끄러짐` 테스트: `attachStroke`가 `nearestAllowed`로 θ를 고르니 `isForbidden(a.theta) === false`는 정의상 참이다. 획 몸통이 금지 자리를 덮는지는 안 본다. 실제 결함(정수리 넷째 가닥)을 놓친다. → 점 단위 판정으로 바꾼다.
- `E 빗` 테스트의 `expect(deg).toBeLessThan(75)`는 **알려진 정본 위반(빗 뿌리가 금지 자리 ① 밖)을 통과로 굳힌다.** 정본(아트 1-1 "빗 자리는 금지 자리")과 다르면 테스트가 빨개져야 한다. `it.fails` 또는 `it.todo` + REPORT 연결로 바꾸고, 결정 1이 나면 정상 테스트로 되돌린다. (높음, 커밋 전)
- `coreRadius1(0) > 0.3`은 아무것도 지키지 않는다(낮음, 지울 것).
- 몸 수치 테스트(비율·현·정수리·눈·빗 길이비)와 L1 거리 보존, L2 축소는 의미 있다.

### 2-5. 성능(UI 스레드) — 중간, 실기기 전에 손볼 것
- **긋는 중 배열 복사가 O(n²).** `onUpdate`마다 `live.value = [...pts, 새 점]`이고, 매 프레임 `buildRibbon`이 손획 전체(단순화 없이, 상한 없이)를 다시 만든다. S25 터치는 120Hz 안팎이라 6초면 700점 이상이다. 웹 4× 감속 최대 66.7ms가 이미 신호다. → `live.modify`로 제자리 push, 리본은 끝부분만 갱신하거나 그리는 중 점을 거리 기준으로 솎는다.
- **부착 애니메이션 동안 모든 획을 매 프레임 다시 단순화한다.** `ribbons` 캐시 키에 모든 획의 `attachK`가 들어가므로, 한 획이 800ms 정착하는 동안 24획 전부가 `simplifyStroke`(dejitter → RDP → 조밀 Catmull-Rom) + 리본을 매 프레임 다시 돈다. `freshVerts`도 같은 획을 한 번 더 만든다. → 획별로 캐시한다(단순화 점열은 raw가 안 바뀌면 영구 캐시, 리본은 `(s, k)`가 바뀐 획만).
- 캐시가 맞아도 `ribbons`가 매 프레임 새 배열(`rs.slice()` + 빗)을 돌려주므로 `maskVerts`가 매 프레임 수천 개의 `{x, y}` 객체를 새로 만든다. UI 스레드 GC 부담이다.
- `strokeCache`를 읽는 `useDerivedValue` 안에서 같은 값을 쓴다. 의존성에 걸려 바뀔 때마다 한 번 더 돈다(무한 루프는 아님).
- mode A에서도 `sdfU`가 매 프레임 768칸 배열을 채운다(후보 B 전용인데 늘 돈다).
- `frame` 하나에 모든 상태를 담아 모든 derived가 매 프레임 다시 계산된다(눈 경로 생성 포함). 스파이크로는 괜찮고, 실측 뒤 나누면 된다.

### 2-6. 웹/네이티브 차이 — 중간
- 웹 60fps 수치는 REPORT 말대로 네이티브 근거가 아니다(웹 worklet = JS 스레드).
- 후보 B: `uniform float4 segs[128]` + `float2 rads[128]`는 프래그먼트 uniform 384 vec4 슬롯이다. GLES 3.0 최소 보장(224)을 넘어 일부 중급 Android GPU에서 컴파일이 실패할 수 있다. 128회 루프도 픽셀마다 돈다. A를 고를 이유가 하나 더 있다.
- 칠 필터 그래프(팽창·침식·블러 ×1 + 색 필터 ×4 + 블렌드)는 레이어 전체에 매 프레임 돈다. 중급 Android 비용은 S25 측정 항목에 그대로 넣는다.
- 밤 1/4 해상도 캔버스 + `transform: scale`은 Android SurfaceView에서 스케일이 안 먹을 수 있다(REPORT 10-7, 동의).
- 페인트가 `night·bleed·ink` 양자화 키로 `runOnJS(setKey)` → React 재렌더 → 필터 그래프를 다시 만든다. 낮 → 밤 2400ms 전환 동안 최대 20번 JS 재렌더가 난다. 전환 중 끊김 후보다.

### 2-7. 그 밖의 정확성
- 손획 리본(`liveV`)은 `base` 변환만 받고 `anim`(기울기·숨·눌림)은 안 받는다. 숨쉬는 몸 위에서 손획이 미세하게 어긋난다(낮음).
- 새 획을 앞 획 성장 애니메이션(정착 뒤 600~1400ms) 중에 그으면 정규화는 `coreScale(n0)`로 하는데 화면의 몸은 아직 작다. 그은 자리와 붙는 자리가 조금 어긋난다(낮음).
- `globalThis.__strokes` 디버그 누적은 출시 경로에서 빼야 한다(낮음, 표시만).

## 3. 과함 — 버리거나 줄일 것
- **후보 B(SDF 셰이더) 전체**: PSNR 37.8dB로 A와 같은 결과가 나왔고, A가 싸고, B는 Android uniform 한도 위험이 있다. 비교는 끝났다. `bodySdfFx`·`sdfU`·`?body=B`를 지우거나 최소한 A 경로에서 계산이 안 돌게 한다. 비교 결과는 REPORT에 남아 있으니 충분하다.
- **모션 webm 14개 + 시트 14개**: 360·390 두 벌을 모두 저장소에 넣을 이유가 약하다. 판정은 한 해상도로 충분하다. 큰 바이너리는 저장소 무게만 늘린다. 390 한 벌 + 시트만 커밋하고 나머지는 지우거나 Git 밖에 둔다(용량 확인 후 결정).
- **표정 4종 보간·시선·기쁨 튐·빗 튕김·조수 전환·안심 문구**: 스파이크 질문("06c 수준에 닿는가", "몽망이로 보이면서 내가 그었다")에 비해 모션 쪽 완성도에 시간이 많이 갔다. 정작 질문 ②는 "절반"이다. 다음 반복은 정지 화면 7일차 하나에 집중하는 게 맞다.
- metrics-*.json 5개는 남겨도 되지만 REPORT 표와 중복이다(낮음).
