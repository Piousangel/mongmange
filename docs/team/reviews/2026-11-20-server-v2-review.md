## 치명 (D-21 확정 전에 고칠 것)

### C1. 신고 중복 판정이 '한 사람이 남의 링크를 숨기는 일'을 막지 못한다 (3-1·3-8·7절 L5)

`reporter_key = HMAC(오늘의 소금, IP ‖ UA)`와 '30일 안에 서로 다른 키 3개'를 함께 쓰면 구멍이 넷 생긴다. 하나만 있어도 한 사람이 자동 숨김을 일으킬 수 있다.

1. **소금이 날마다 바뀐다 ↔ 판정 창은 30일이다.** 같은 사람이 사흘 동안 하루에 한 번씩 신고하면 키가 셋이 되어 3건으로 센다. 게다가 `reporter_key`는 48시간 뒤 NULL이 된다. 그러면 `UNIQUE(report_id, reporter_key)`가 NULL끼리는 중복을 허용하므로, 30일 창의 '서로 다른 키 수'는 계산할 수 없다. 창과 소금 주기가 서로 맞지 않는다.
2. **UA가 키에 들어 있다.** 같은 IP에서 UA만 바꿔도 다른 사람으로 센다. curl 세 줄이면 숨길 수 있다.
3. **IPv6.** 집과 모바일 회선 대부분이 사용자 한 명에게 /64를 준다. 주소를 바꾸는 데 비용이 0이므로 IP당 레이트 리밋도 함께 무력해진다.
4. **어느 IP를 믿을지 정하지 않았다.** 요청은 Firebase Hosting rewrite를 거쳐 Cloud Run에 닿는다. 그래서 Nest가 보는 `req.ip`는 클라이언트 IP가 아니다. `X-Forwarded-For`의 맨 왼쪽 값은 클라이언트가 마음대로 넣을 수 있다. 이 값을 쓰면 신고 판정과 모든 IP 레이트 리밋을 헤더 하나로 우회한다. 반대로 프록시 IP를 쓰면 모든 사용자가 한 IP로 묶여 레이트 리밋이 전체를 막는다.

- 고칠 방향(제안): ① 키는 **IP만** 쓴다(UA 제외). IPv4는 /32, IPv6는 /64(또는 /56)로 접어서 넣는다. ② 소금을 날마다 바꾸지 말고 **대상(열린 `reports` 행)마다 소금 하나**를 둔다. 그 신고가 닫히거나 창(예: 7일)이 끝나면 소금을 지운다. 그러면 창 안에서는 계속 중복을 가려내고, 대상끼리 연결할 수도 없다. ③ B6 첫날 실제 요청으로 **XFF에서 몇 번째 값이 Google 프런트엔드가 붙인 클라이언트 IP인지** 확인하고, Fastify `trustProxy`를 그 개수에 맞춰 고정한다. Firebase를 거친 경로와 `*.run.app` 직접 경로를 둘 다 본다. ④ L5에 'UA만 바꿔 3회', '하루 간격 3회', 'IPv6 /64 안에서 주소 3개', '가짜 XFF' 시나리오를 넣는다. 지금의 L5 '같은 IP 신고로 숨김 0건'은 이 넷 가운데 아무것도 시험하지 않는다.
- 덧붙임: 소금이 같은 DB에 있는 48시간 동안에는 IPv4 2^32개를 전수 대입해 IP를 되짚을 수 있다. '되짚을 수 없다'는 소금을 지운 뒤에만 참이다. 처리방침에는 '48시간 보관하는 가명 정보'로 적는다. 3-1 공식과 6-4 비밀값 `REPORT_HMAC_KEY`('소금과 별도의 고정 키')가 서로 다르므로 하나로 맞춘다.

### C2. 서버가 검증한 공개 스냅숏과 실제로 공개되는 `snap.json`이 다른 파일일 수 있다 (3-2·3-5)

`PUT /creature/page`는 요청 본문의 `snapshot`을 `parsePublicSnapshot`으로 검증한다(모르는 키가 있으면 422). 그런데 공개되는 `snap.json`은 **앱이 서명 URL로 직접 PUT하는 별도 파일**이다. 앱에 버그가 있거나 클라이언트를 조작하면, 검증된 본문과 다른 파일(`relation.hour` 등이 든 파일)을 올릴 수 있다. 그러면 '서버가 키 화이트리스트로 막는다'는 개인정보 보장(5-1 ④, 3-5)이 성립하지 않는다.
- 고칠 방향: `snap.json`은 **서버가 검증한 본을 직접 Storage에 쓴다.** 크기는 32KB 이하라 서버 부담이 없다. 업로드 URL 발급 목록에서 `snap`을 뺀다. `meta`도 서버가 만든다(지금도 그렇게 읽힌다).
- 같은 계열의 위험: 포스터·OG·루프는 서버가 다시 그리지 않으므로 조작된 클라이언트가 **아무 이미지나** `mongmang.ink/m/…`의 OG로 걸 수 있다. 이름 금칙어도 OG 픽셀에는 적용되지 않는다. 막을 수는 없다. 대신 ① `commit`에서 파일 시그니처(JPEG·MP4 매직 바이트)와 해상도를 확인하고 ② 이 위험을 '신고 → 격리'로 감수한다는 문장을 10절 반증에 넣는다.

### C3. 집계 핑으로는 이름 A/B 주지표가 실제로 계산되지 않을 수 있다 (3-6, 기획 10-1)

1. **`nt`의 '-'가 분모와 분자를 다른 칸에 나눈다.** 군 값은 '플래그 꺼짐·배정 전'이면 `-`다. 첫 실행 핑(dayN=0)은 원격 플래그를 받기 **전에** 나갈 수 있다. 바이너리 기본값이 꺼짐이거나 플래그 캐시가 비어 있을 때다. 그러면 `open(day_n=0)`은 `-` 칸에, 나중의 `name_set`은 `A` 칸에 쌓인다. `nt`별 `sum(name_set)/sum(open, day_n=0)`은 분모가 비어 있거나 부풀려진다.
   - 고칠 방향: 군은 **설치 순간 로컬 난수로 확정하고 플래그와 무관하게 늘 보낸다**(`A`·`B`만). 플래그는 '군을 실제로 적용하느냐'만 정한다. 판정 SQL은 `nameTiming`이 켜진 날 이후의 코호트로 거른다.
2. **`wg`·`moon`은 날마다 바뀌는 값이다.** 3-6은 '위젯(참고) = `wg`별 `day_n` 비율'을 계산하려 한다. 그런데 같은 기기도 dayN=0에는 `wg=0`이고 dayN=3에는 `wg=1`일 수 있다. 그래서 `wg=1` 칸의 D_n 분자에 대응하는 dayN=0 분모가 없다. 이 비율은 정의되지 않는다. `moon`도 같다(그날의 값). 기획이 '참고'로 둔 값이니, 계산식을 '`wg=1` 칸 open 수의 일별 추이'처럼 정의 가능한 것으로 바꾸거나 '판정에 쓰지 않음'으로 못박는다. D1·D7은 `wg`·`moon`을 **합산한 뒤** 계산해야 한다는 점을 SQL 스니펫 규칙으로 적는다.
3. **분모가 오염되는 경로가 셋이다.** ① 빌드 1(11-29) 비공개 테스트 설치자는 핑이 없던 때 dayN=0을 지났다. 이들이 빌드 2로 업데이트하면 분자만 들어온다. → 판정 SQL은 `cohort_day ≥ 핑이 들어간 빌드의 배포일`로 거른다. ② 지표를 나중에 끄면 분모에는 남고 분자에서만 빠져 리텐션이 낮게 나온다. ③ 첫 실행이 오프라인일 때 `open`도 아웃박스로 미뤄지는지 문서에 없다. 이벤트만 아웃박스라고 적혀 있다.
4. **Cloud Run의 기본 CPU 할당(요청 처리 중에만)에서는 10초 `setInterval` flush가 요청 사이에 돌지 않는다**(리뷰어 기억, 확인 필요). 마지막 요청 뒤의 칸은 다음 요청이나 SIGTERM까지 메모리에 머문다. 인스턴스가 비정상 종료되면 '최대 10초분'이 아니라 '마지막 flush 뒤 전부'를 잃는다. → flush를 **요청 처리 안에서** 한다(요청이 올 때 10초가 지났으면 그 요청이 flush). SIGTERM flush는 유지한다. L3의 '합계 오차 0'은 이 구조로 시험한다.
5. **D30은 판정 기간에 사실상 '미판정'이다.** 핑이 12-22에 시작하면 30일이 지난 코호트는 01-21~01-26에 첫 4~5일치뿐이다. 수백 설치 규모라면 n≥300은 불가능하다. 기획 10-1의 대체 규칙(D14)이 사실상 주규칙이 된다. 이 점을 9-2나 10절에 한 줄 적어 판정 날 놀라지 않게 한다.
6. **`/ping`은 인증이 없어 지표를 오염시킬 수 있다.** 군마다 n≈160인 판정에서는 스크립트 하나로 B군 `name_set`을 수십 건 넣을 수 있다. 최소 장치를 둔다. ① 값 범위 검증(dayN 0~400, 날짜 ±2일, 화이트리스트) ② 판정 SQL에 `sum(open, day_n=0)` ≤ 같은 날 스토어 설치 수 × 1.2 대조를 넣는다.

## 중요

### I1. 계정 삭제 뒤 데이터가 되살아난다 (3-8 삭제 절차)
`DELETE /me` 뒤에도 앱이 가진 Supabase 액세스 토큰은 만료 전까지(기본 1시간) 서명 검증을 통과한다. 아웃박스의 `PUT /saves`나 재시도된 `bootstrap`이 오면 Nest는 같은 `sub`로 `users` 행을 **다시 만든다**. 그러면 삭제를 요청한 데이터가 서버에 다시 생긴다(Play 계정 삭제 정책 위반 소지).
- 고칠 방향: ① 앱은 삭제 성공 시 세션·아웃박스·`EXPO_PUBLIC` 캐시를 비운다. ② 서버는 삭제한 `sub`를 토큰 최대 수명(+여유) 동안 거부 목록에 둔다. 또는 `bootstrap` 외의 모든 API에서 `users` 행이 없으면 401을 낸다. `bootstrap`은 `auth.users` 존재를 Admin API로 확인한다. ③ e2e '삭제 직후 옛 토큰으로 PUT → 거부'.

### I2. OS 백업이 세션 토큰까지 복원해 두 기기가 같은 refresh token을 쓴다 (3-3 ④, D-06)
D-06은 세이브가 iCloud·Android Auto Backup에 들어가길 원한다. 3-3은 세션을 MMKV에 저장한다. 같은 MMKV 인스턴스면 새 폰 복원 때 세션도 따라온다. 옛 폰이 살아 있으면 두 기기가 같은 refresh token을 돌리게 된다. 그러면 Supabase의 refresh token 재사용 감지가 세션 묶음을 폐기해 **두 기기 모두 '맡겨 두기 끊김'**이 된다(리뷰어 기억, 확인 필요). 되찾기 글귀가 없으면 클라우드 사본에 다시 닿지 못한다.
- 고칠 방향: 세션은 **백업에서 제외한 별도 MMKV 인스턴스**(iOS `isExcludedFromBackup`, Android `dataExtractionRules` 제외)에 둔다. 복원된 기기는 되찾기 흐름으로 들어간다. Q9 테스트에 'OS 백업 복원 + 옛 기기 계속 사용'을 넣는다.

### I3. 국외 이전·처리위탁 표(5-4)가 실제 데이터 흐름과 다르다
- "CDN은 공개 콘텐츠뿐"은 **틀렸다.** 앱의 `/api/**`(세이브 본문 전체·되찾기 글귀·JWT)도 `mongmang.ink` → Firebase Hosting rewrite를 지난다(2-1 그림). 사용자 가까운 Google 엣지에서 TLS가 끝난다. 소프트런칭 사용자는 캐나다·뉴질랜드·필리핀에 있으므로(D-18·D-23) 그 엣지는 국외다. 대안은 앱의 API 기본 주소를 `*.run.app`(서울) 직접으로 두고 `/m/**`만 Firebase를 거치게 하는 것이다. 이렇게 하면 이전 경로도, 서울 rewrite 의존도 함께 줄어든다.
- Cloud Logging `_Default` 버킷은 기본 위치가 global이고 보존이 30일이다(리뷰어 기억, 확인 필요). 5-2의 'IP 7일'은 설정하지 않으면 거짓이 된다. 기존 프로젝트의 `_Default`는 위치를 바꿀 수 없다. 그래서 B6에서 **서울 로그 버킷을 새로 만들고 `_Default` 싱크를 옮기는 작업**을 체크 항목으로 넣는다.
- 요청 로그에는 IP와 함께 `/api/v1/m/{code}/seen`·`/m/{code}/get` **URL이 남는다.** 그래서 '어느 IP가 어느 몽망이 링크를 봤나'가 7일 동안 기록된다. 3-6의 '쿠키·식별자 없음'과 별개로 처리방침 '웹 페이지' 절에 적는다.
- 개인정보보호법 제28조의8에 따라 처리방침으로 고지한다면 항목이 모자란다. 지금 표에 없는 것: **이전 일시·방법, 받는 자 연락처, 보유·이용 기간**[법률 검토].
- 소프트런칭 국가 사용자의 데이터가 한국·미국으로 옮겨진다. 이 표는 한국법 시각만 다룬다. 캐나다(특히 퀘벡 Law 25의 국외 이전 전 평가, 14세 미만 동의), 필리핀 DPA를 **오너 12-05 법률 검토 범위에 넣는다**[법률 검토].

### I4. 14세 확인이 '덮는 범위'와 '방식'에 빈틈이 있다 (3-3 ③·5-3)
- 범위: 확인은 계정이 생길 때만 한다. 그런데 **EAS Update의 설치 id(`EAS-Client-ID`류)는 설치 직후 모든 사용자(14세 미만 포함)에게서 미국으로 간다**[확인 필요]. IP·설치 id가 개인정보로 판단되면 '서버에 `under14`가 없다'는 말만으로는 제22조의2 회피 논리가 완결되지 않는다[법률 검토 — 오너 12-05 질문에 이 항목을 명시].
- 방식: "만 14세 이상인가요? 예/아니요"는 정답을 알려 주는 유도형이다. Google Families가 요구하는 **중립적 연령 확인**(출생 연도 입력 등)에 미치지 못한다. 연도는 기기에서 판정하고 서버에는 지금처럼 `ok`만 보낸다.
- 스토어 설정: Google Play 타깃 연령대는 '13~15세' 같은 묶음이라 '14세 이상'만 고를 수 없다(리뷰어 기억, 확인 필요). D-06(13+)·D-23(14+)·store-listing의 선언을 한 줄로 맞춘다.

### I5. 공개 웹 삭제 경로를 다른 사람이 악용할 수 있다 (3-8 ② 웹 삭제)
"되찾기 글귀가 없으면 링크 끄기만"이라고 했다. 그런데 인장 코드는 **링크 URL에 공개된 값**이다. 그래서 아무나 남의 코드를 메일로 보내 링크를 끌 수 있다. 링크만 켜고 맡겨 두기를 안 켠 사용자는 글귀가 아예 없으므로, 이 경로로는 본인 확인이 불가능하다.
- 고칠 방향: 글귀가 없는 웹 요청은 **처리하지 않는다**. 앱 안 삭제 안내와 장기 미사용 규칙으로 갈음하고, 그 이유를 `/delete`에 적는다. 링크 켜기 때 '삭제용 글귀'를 함께 보여 주는 것도 대안이다. 또 처리를 마친 메일(글귀 평문 포함)은 지운다는 규칙을 런북에 넣는다.

### I6. 격리된 링크를 주인이 '다시 만들기'로 되살릴 수 있다 (3-2·3-8·3-9)
상태 표에 `quarantined`가 있다. 그런데 `PUT /creature/page`·`commit`이 `quarantined` 상태나 `creatures.hidden`일 때 거부한다는 규칙이 없다. 그러면 주인이 '다시 만들기'를 누를 때 새 판이 `live`가 된다. 주인 앱에 '잠시 가려졌어요'가 뜨면 오히려 다시 만들기를 유도할 수도 있다.
- 상태 전이표를 한 장 만든다: `quarantined`에서는 PUT·commit이 409이고, 주인의 DELETE(링크 끄기)는 허용하되 격리본은 운영 판단까지 둔다. 운영자가 7일 SLA를 놓쳐 30일이 지나면 기본값(복원 또는 확정)도 정한다.

### I7. 서명 업로드의 크기·형식 상한이 실제로 강제되지 않고, 버려진 업로드가 영구히 남는다 (3-2·3-5·3-8)
- Supabase 서명 업로드 URL은 파일별 크기·형식을 강제하지 않는다. 강제는 **버킷 단위** `file_size_limit`·`allowed_mime_types`로 한다(리뷰어 기억, 확인 필요). 3-8의 '파일은 3-5 상한'은 `commit`에서 사후로 확인하는 것뿐이다. 버킷 상한을 600KB로 두고 그 위에 `commit` 검사를 얹는다.
- 업로드만 하고 `commit`하지 않은 판은 **공개 버킷에 남는다.** 4-1은 '다음 시도 때 치운다'라고만 했다. 다시 시도하지 않는 사용자의 파일은 영원히 남고, 공개 버킷이 무료 파일 호스팅으로 쓰일 여지도 생긴다. `storage_gc`에 '발급 뒤 N시간 안에 commit 없음' 항목을 발급 때 미리 넣는다.
- 공개 경로에 `creatureId`(내부 UUID)가 그대로 드러난다. 판이 바뀌어도 같은 값이라 경로끼리 연결된다. 경로 앞부분은 불투명 난수로 둔다.

### I8. 관리 도구의 `localhost` 프록시는 CSRF에 열려 있다 (3-12)
`gcloud run services proxy`는 오너의 자격 증명을 `localhost:8080`에 붙여 준다. 오너가 그 시간에 연 아무 웹페이지가 `localhost:8080/…`으로 POST를 보낼 수 있고, 그 요청이 '확정 숨김·삭제'로 실행된다. '로그인 코드 0줄'이라 막을 장치가 없다.
- 최소 장치: 상태를 바꾸는 요청은 `Origin`/`Host`가 `localhost:8080`인지 검사(DNS 리바인딩 대비)하고, 폼마다 CSRF 토큰을 넣는다. 0.1일이면 된다. 또 `ADMIN_MODE`가 아닌 `mong-api`에서 관리 라우트가 404인지 배포 스모크에 넣는다(같은 이미지라 환경 변수가 빠지는 사고에 대비).

### I9. `creatures UNIQUE(user_id)`를 '앱 규칙으로만' 두면 `bootstrap` 멱등이 깨진다 (3-1·3-2)
재시도나 두 요청이 동시에 오면 몽망이 두 마리와 코드 두 개가 생긴다. 1.0 동안은 DB 제약으로 두고, 여러 마리를 키울 때 마이그레이션으로 푼다(확장 → 배포 → 축소 원칙과도 맞다).

### I10. iOS '꺼진 채 들어온 코드를 플래그로 켠다'는 App Store 2.3.1(숨긴 기능)과 부딪칠 수 있다 (3-11)
소프트런칭 중 iOS는 TestFlight 외부 테스트다. 외부 테스트도 베타 심사를 받는다. 심사 때 꺼져 있던 맡겨 두기·링크를 심사 뒤에 원격으로 켜는 것은 2.3.1이 금지하는 '숨겨진·휴면 기능'에 해당할 소지가 있다. 정식 1.0 제출 때는 **심사 시점에 기능이 켜져 있거나 심사 노트에 적혀 있어야** 한다. 플래그는 '끄는 손잡이'와 A/B로만 쓴다는 규칙을 3-11에 적는다. Android는 JS 번들 OTA가 허용 범위다.

### I11. EAS Update 이탈 경로가 바이너리에 묶여 있다 (3-11·8·10 #19)
'비용이 크면 자체 업데이트 서버(약 2일)'라고 했다. 그런데 `updates.url`은 **네이티브 설정**이라 바꾸려면 스토어 업데이트가 필요하다. 런타임 URL 덮어쓰기 API는 SDK 버전·제약을 확인해야 한다[확인 필요]. 그러니 EAS 요금(Production 요금제의 MAU 단가)을 **빌드 2(12-10) 전에** 확정해야 한다. 오너 할 일 12-01과 날짜는 맞다. 다만 '나중에 바꾸면 된다'는 대응은 빼야 한다. 10만 설치에서 '월 0~200달러'라는 범위도 근거가 없다. 요금표를 확인한 뒤 숫자를 다시 넣는다.

### I12. 링크 조회 기록(`link_daily`)이 사용자별 데이터인데 보관 기간이 없다 (3-1·5-5)
PK에 `code`가 있어 '이 사람의 링크가 하루 몇 번 보였나'가 계정에 묶인 값으로 무기한 남는다. 5-5 표에도 없다. 퍼널 판정에는 코드별 값이 필요 없다. ① 30일 뒤 코드를 지우고 합계로 말아 두거나 ② 처음부터 코드 없이 센다. 삭제 절차(3-8)의 CASCADE 대상에도 넣는다.

### I13. 일정 산수와 오너 의존 (9-1·9-3)
- 합계를 두 번 셌다. B1~B7 + 운영 전환 0.5를 더하면 **15.0**인데(운영 0.5 포함), 표는 '15.0 + 운영 0.5 = 15.5'로 적었다. 실제로는 15.0이다. 0절과 질문 9의 숫자도 같이 고친다.
- 빠진 공수가 있다. B3(11-28 시작)는 core의 `toPublicSnapshot`·`parsePublicSnapshot`을 전제로 한다. B4는 `parseMotif`를, 3-6은 달 위상을 전제로 한다. 이 core 작업은 'core 담당 PR'로 넘겼지만, 앱 레인은 이미 41 대 40.75로 꽉 차 있다(3-11). **어느 레인에도 일수가 없다.** 약 1.0~1.5일로 추정되며 서버 레인으로 옮기는 편이 현실적이다.
- B3는 2.5일인데 할 일이 12가지다(bootstrap·touch·PUT·commit·DELETE·서명 업로드·검증·금칙어·HTML 템플릿·`/get`·비콘·gc). B5는 2.5일 안에 관리 도구 1.0이 들어 있다. 둘 다 빠듯하다.
- 오너 의존: 11-23(월)에 계정이 없으면 B6만 밀리는 것이 아니다. B0의 `.well-known`이 12-05 EAS 리허설 전에 운영 도메인에 떠 있어야 하는데, 그 사슬이 끊긴다. ① 오너에게 **11-21~22 주말 처리**를 요청하고 ② 늦어지면 B3를 로컬(Supabase CLI)에서 먼저 진행하는 순서 교체안을 9-1에 적어 둔다. 법률 검토(12-05) → 처리방침 게시(12-08)는 3일뿐이다. 검토 결과가 '동의 필요'로 나오면 B8과 빌드 2 라벨을 다시 써야 한다. **법률 검토 질문을 지금 확정해 이번 주에 보내는 것**을 권한다.

## 사소

- S1. **이력 솎기를 날마다 하면 행이 쌓인다**(3-4). `overwritten`은 PUT마다 생긴다(최대 60/시간). 날마다 솎으면 하루 수백 행·수십 MB가 쌓였다 지워져 TOAST가 부풀고 WAL이 늘어난다. Micro 컴퓨트의 IO 예산에서 불리하다. '최근 3벌'은 PUT 트랜잭션 안에서 바로 지우고, `pg_cron`은 주·30일 규칙만 맡긴다.
- S2. **`weekly`를 언제 표시하나**가 없다(3-4). `overwritten`을 3벌로 솎은 뒤에는 그 주의 첫 본이 이미 없다. 'PUT 때 이번 ISO 주에 `weekly`가 없으면 덮이는 본을 `weekly`로 저장'처럼 쓰는 순간을 정한다.
- S3. **`/recover` 뒤 글귀 회전과 옛 기기 처리**(3-3 ⑤). 회전하지 않으면 글귀를 한 번 본 사람이 언제든 몽망이를 다시 가져갈 수 있다. 되찾으면 새 글귀를 발급하고, 옛 기기에는 '다른 기기로 옮겨졌어요' 상태(서버 410 등)를 둔다. `recovery_hash`가 `users`에 있는데 몽망이는 새 사용자로 옮겨진다. 해시를 `creatures`로 옮기는 편이 자연스럽다.
- S4. **pepper를 잃으면 글귀가 전부 무효가 된다.** `RECOVERY_PEPPER`는 Secret Manager 버전 관리와 오프라인 사본을 런북에 둔다. 회전에 대비해 `recovery_pepper_v` 열을 둔다.
- S5. **로그 가림 규칙이 없다.** Nest 요청 로그·예외 로그에 `/recover` 본문(글귀), `Authorization`, 세이브 본문이 남지 않도록 가림 목록을 6-4에 적는다.
- S6. **JWT 검증 항목**을 명시한다: `iss`·`aud`·`exp`·`role = authenticated`·`sub` 존재. 비대칭 키만 받고 HS256은 거부한다(레거시 anon 키 토큰 차단). Supabase가 새 API 키(`sb_secret_…`)로 옮겨 가는 중이라 `SERVICE_ROLE_KEY` 이름·수명도 B6에서 확인한다[확인 필요].
- S7. **레이트 리밋은 인스턴스 메모리라** min 0에서 콜드 스타트마다 초기화되고, 최대 3배까지 새어 나간다. 소프트런칭에서는 감수하되 L5를 인스턴스 1개 기준으로 본다는 점을 적는다.
- S8. **'공유 직후 데우기'는 그 사용자 근처 엣지만 데운다**(3-5). 카카오 크롤러(국내)는 한국 사용자 공유에 효과가 있다. X·iMessage 크롤러는 미국 엣지라 놓친다. L2의 기대치를 그만큼 낮춘다.
- S9. **`BUNDLE_SEQ`는 바이너리와 OTA를 통틀어 하나의 증가 값**이어야 한다(3-7). 위젯 스토어 업데이트로 fingerprint가 갈리면 런타임마다 OTA를 따로 게시해야 한다. 그때 새 바이너리의 내장 SEQ가 앞선 OTA보다 작으면 기능이 꺼진다.
- S10. **비용 '상한 장치'의 이름이 과하다**(3-8·8). GCP 예산은 알림일 뿐 지출을 멈추지 않는다. Firebase 전송에는 상한이 없다. Supabase Spend cap을 켜면 한도 초과 때 서비스가 제한되어(가입·전송) 입소문이 난 순간에 링크 이미지가 끊길 수 있다(리뷰어 기억, 확인 필요). '알림'과 '상한'을 나눠 적는다.
- S11. **복원 리허설로 운영 데이터를 스테이징에 넣지 않는다**(3-8 백업). 스테이징은 Free이고 접근 범위가 넓다. 지운 사용자도 함께 되살아난다. 리허설은 시드 데이터로 하거나, 운영 백업을 새 임시 프로젝트에 복원한 뒤 바로 지운다.
- S12. **링크 코드는 '평생 하나'다.** 특정 상대에게 보낸 링크를 끊고 싶은 주인이 끈 뒤 다시 켜면, 같은 URL이 다시 살아난다. '새 주소로 다시 만들기'(코드 회전)를 1.0.x 후보로 적어 둔다. 인장 무늬는 `sealSeed`라 영향이 없다. 그 밖에 `DIRECT_URL`이 Supabase 직접 연결(IPv6 전용)을 가리키면 GitHub 호스티드 러너에서 마이그레이션이 실패한다. 세션 풀러(5432)를 쓴다는 점을 비밀값 이름에도 드러낸다.

## 리뷰 질문 13개에 대한 답

1. **신고자 48시간 해시**: 해시 없이 '3건'을 지킬 방법은 없다(가입 없는 웹 신고이므로). **기획 6-5 문구를 고친다**: "신고자를 식별하는 정보는 저장하지 않으며, 같은 사람의 중복 신고를 가려내려고 IP에서 만든 일회성 가명 값을 최대 N일 보관 후 파기". 다만 지금 설계로는 그 목적도 달성하지 못한다(C1). 대상별 소금, IP만(/64 접기), XFF 신뢰 위치 고정으로 고친 뒤에 확정한다.
2. **격리 이동 = Q12 '삭제로 즉시'**: 공개 경로에서 즉시 사라진다는 뜻으로 읽어도 된다. 기획의 의도는 '공개에서 안 보임'이다. 30일 격리 보관은 목적(운영자 확인·복원·재발 판단)과 기간을 처리방침 '신고' 절에 적으면 무리가 없다[법률 검토 대상은 아님]. 단 I6(다시 만들기로 우회)을 막아야 '즉시 안 보임'이 유지된다. 스테이징(Free)에는 Smart CDN이 없을 수 있으니 Q12 검증은 운영 설정에서 한다.
3. **Q12 문구 보강**: 맞다. '외부 서비스가 이미 만든 미리보기 카드와 이미 내려받은 브라우저 캐시는 범위 밖, 카카오는 런북으로 초기화'를 덧붙인다. 또 Smart CDN 약 60초를 고려해 '즉시'를 '약 1분 안'으로 쓰는 것이 정직하다.
4. **밤물 = 세 번째 계정 생성 순간**: 논리상 필요하다(맡김을 올리고 삭제·막기를 하려면 주체가 있어야 한다). 그런데 D-23([확정])이 '계정은 첫 링크 공유·맡겨 두기 때만'이라고 적었다. 그래서 리뷰로 끝낼 일이 아니라 **D-23 개정(새 결정)**이 필요하다. 1.0 직후 릴리스 전에 DECISIONS에 올린다. 14세 확인을 같은 자리에 두는 것은 원칙과 맞다.
5. **지표 차원 3개**: 식별 가능성 처리는 충분하다(식별자 없음 + 작은 칸 합치기). 단 요청 로그의 IP는 본문과 묶이지 않으므로 별개다. '평생 한 번' 이벤트로 '개수 비율 = 사람 비율'을 만드는 가정은 이름 A/B에 맞다. 그러나 `nt`의 '-' 처리와 분모 오염 때문에 **지금 그대로면 계산이 틀어진다**(C3). `wg`·`moon`별 리텐션 식은 정의되지 않는다. `wg` 함수가 앱 레인에 전달됐다는 근거는 문서 안에 없다. 앱 레인 투두(빌드 2 네이티브 묶음)에 항목으로 넣었는지 PM이 확인한다.
6. **조회 비콘**: 처리방침 '웹 페이지' 절에 적는다. 비콘 자체보다 **요청 로그의 IP + 링크 코드 URL 7일**이 적을 대상이다(I3). 크롤러 제외는 충분하다. 다만 수치는 '고유 방문자'가 아닌 '페이지 로드 수'라고 대시보드에 표기한다.
7. **EAS Update 설치 id**: 사실이면(그럴 가능성이 높다) ① 'Usage Data Not Linked'는 유지된다(핑과 묶이지 않음). 그러나 Data safety·App Privacy에 **기기 또는 기타 ID**(Expo가 처리)를 선언해야 할 수 있다. ② P9 '설치만 한 사람은 서버가 모른다'는 '**우리** 서버는 모른다'로 고친다. ③ 14세 논리에 영향을 준다(I4). 자체 업데이트 서버를 1.0에 둘지는 **법률 검토 결과와 EAS 요금**에 달렸다. 둘 다 빌드 2 전에 정해야 한다(바이너리 설정, I11). 기본 권고는 고지하고 EAS를 쓰는 것이다.
8. **관리 도구 접근**: 1인 운영·7일 SLA에는 충분하다. 휴대폰을 못 쓰는 것은 SLA 위험이 아니다. 급할 때는 Cloud Shell 웹 미리보기로 휴대폰에서도 열 수 있다(확인 필요). 위험은 접근성이 아니라 **localhost CSRF**다(I8). 소프트런칭에는 Studio로 되돌려도 된다(과설계 표).
9. **공수**: 합계부터 고친다(15.5 → 15.0, I13). 대신 core 함수 1.0~1.5일이 어느 레인에도 없다. 흡수안은 ① 관리 도구를 정식 출시 전으로 미뤄 −1.0 ② L1·L3를 1월 재실행에 합쳐 −0.5. 이렇게 하면 core 몫을 서버 레인이 가져가도 기획 4-1의 14.0 근처로 돌아온다. 웹 +1.0은 정적 → live 폴백·Playwright이므로 타당하다.
10. **장기 미사용 고지**: 처리방침 사전 고지 + 앱 안 표시로 갈음하는 것은 개정법(2023, 유효기간제 폐지) 아래에서 자율 규칙이라 가능성이 높다[법률 검토]. 단 '30일 전 앱 안 표시'는 앱을 열면 곧 활동이 되어 시계가 다시 돌아가는 구조다. 그래서 그 표시는 사실상 아무에게도 보이지 않는다. 문구를 '앱을 2년 동안 열지 않으면 정리'로 단순화하는 편이 정직하다.
11. **기획과 다르게 정한 곳**: 넷 다 기획 의도를 해치지 않는다. 모티프를 Firebase 정적에 두는 것이 더 낫다(PR 리뷰·CI). 웹 언어를 클라이언트가 고르게 한 것은 캐시 키가 하나라서 옳다. 링크 기본 꺼짐은 정정이다. TTL 1시간도 문제없다. 기획 6-1·6-2 표의 'Storage 자산'·'6시간'을 고치는 일은 PM 몫으로 8절 목록에 넣는다.
12. **wasm R2 이전**: 소프트런칭(`webLive` 01-05)에는 알림을 보고 옮겨도 된다. **정식 출시(02월) 전에는 미리 옮긴다.** Firebase 전송에는 상한이 없다. 예산 알림은 몇 시간 늦게 오고, 입소문 링크는 그보다 빠르다(S10). 0.5일이므로 01월 출시 준비 주에 넣는다. 옮길 때 CORS와 `application/wasm` 압축 전송을 확인한다.
13. **이력 4주와 Q9**: 충분하다. 분실의 주원인은 이력 길이가 아니다. ① 되찾기 글귀를 잃는 것 ② 세션 소실·재사용 감지(I2) ③ 삭제 직후 부활(I1)이다. 이력 4주는 '잘못 고른 충돌'을 되돌리는 용도이고, 충돌본 30일이면 된다. Q9 시나리오에 'OS 백업 복원 + 옛 기기 계속 사용', '되찾은 뒤 옛 기기 업로드'를 더한다.
