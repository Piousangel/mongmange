## 2. 지적

### 중간

**M1. `verify --only` 오타·빈 값이 '0단계 통과'(exit 0)로 끝난다** — `scripts/verify.mjs:12-13, 59, 88`
- `--only lnt`나 값 없는 `--only`는 단계 이름과 하나도 맞지 않는다. 그래서 아무것도 안 돌리고 "verify 통과: 0단계"를 찍은 뒤 0으로 끝난다(직접 실행해 확인). 에이전트가 이 줄을 근거로 완료를 주장하면 OPERATING 8이 말하는 그럴듯한 오답이 된다. `--only=lint` 꼴은 조용히 무시되고 전체가 돈다.
- 고칠 것: 모르는 이름이 있거나 집합이 비면 단계 이름 목록을 찍고 exit 2. 결과가 0단계면 실패로 본다. `--only=` 꼴도 받는다.

**M2. `mong/effect-needs-cleanup`이 effect 안 비동기의 가장 흔한 꼴을 못 잡는다** — `tools/eslint/mong-plugin.mjs:75, 105`
- 탐침 결과(모두 통과 = 미탐):
  - `useEffect(() => { const run = async () => { const v = await load(); setX(v); }; run(); }, [])` — 안쪽 함수는 건너뛰고, `run()` 호출은 트리거로 보지 않는다. React 문서가 권하는 꼴이라 앞으로 가장 많이 나올 모양이다.
  - `useEffect(() => { void loadAndSet(); }, [])` — 시험이 `void ping.flush(ctx)`를 정상으로 고정해 두었다. 그래서 state를 건드리는 비동기 함수도 `void`만 붙이면 통과한다.
  - `return null;`·`return () => {};` — '그 뒤에 값이 있는 return'만 보므로 정리 아닌 return도 통과한다.
  - `load().catch(() => setErr(1))` — `.catch`·`.finally`는 트리거가 아니다.
- lint-rules.md 6절의 한계에는 "alive 확인 여부는 리뷰 몫"만 적혀 있다. 위 꼴이 빠져 있으니 문서를 믿는 사람은 이 규칙이 비동기 경합을 막는다고 오해한다.
- 고칠 것(최소): ① effect 본문에서 선언한 안쪽 함수를 호출하면 그 함수 안의 트리거를 트리거로 친다 ② `.catch`·`.finally`를 추가한다 ③ return 인자가 함수 식이나 식별자일 때만 정리로 본다. `void f()`는 정적으로 판정할 수 없으니 6절 한계에 명시한다. RuleTester 무효 사례에 ①·③을 넣는다.

**M3. 인라인 설정 주석으로 '이유 강제'(`mong/disable-needs-reason`)를 우회한다** — `tools/eslint/mong-plugin.mjs:164`, `eslint.config.mjs:26`
- `/* eslint mong/no-floating-timer: "off" */`는 `eslint-disable`이 아니어서 `DIRECTIVE` 정규식에 걸리지 않는다. 이 주석이 있으면 그 파일 전체에서 규칙이 꺼지고, 오류는 0건이다(탐침 확인). `reportUnusedDisableDirectives`도 이 꼴은 보지 않는다. 파일 전체 `/* eslint-disable */`(규칙 이름 없음)도 스스로를 꺼서 잡히지 않는다(6절에 적혀 있음). 이유 칸에 `-- .`처럼 한 글자만 적어도 통과한다(막을 수 없으니 리뷰 몫).
- 고칠 것: `DIRECTIVE`를 `^\s*eslint(?:-disable(?:-next-line|-line)?|-enable)?\s` 꼴로 넓혀 인라인 설정 주석은 이유가 있어도 오류로 낸다. 또는 `linterOptions.noInlineConfig`의 영향을 따져 본다. 단 그렇게 하면 줄 단위 disable도 꺼진다. 파일 전체 disable은 verify에 grep 단계 하나(생성 코드 `apps/server/src/generated/**` 제외)로 막으면 6절 한계가 사라진다.

**M4. 승격 근거 표 1·2번의 인용 절반이 실제 지적 내용과 다르다** — `docs/team/lint-rules.md:49-50`
- 리뷰 원문을 대조한 결과:
  - build1 L-6은 '백그라운드로 가면 평점 창이 0회가 될 수 있다'는 **정책** 문제다. 핸들 정리 문제가 아니다.
  - app-flow C9는 오히려 "해제는 onEnd/8초 타이머로 되어 있어 **누수는 없다**"고 적었다.
  - server-v2 4는 Cloud Run CPU 할당 때문에 `setInterval` flush가 **돌지 않는** 문제다. 핸들을 버리는 문제가 아니고, 이 규칙으로 막히지도 않는다.
  - build1 M-4와 app-flow C8은 연타·호출 순서 경합이다. 같은 문서 '승격하지 않은 것' 표가 스스로 "정적 판정 불가"라고 분류한 지적이다. 그런데 2번 근거로 다시 쓰였다.
- 규칙 자체는 쓸모 있다. A6 첫 실행에서 실제 위반 7건(타이머 6, effect 1)을 잡았고, mentors.md 1절-5의 타이머 복제 지적과도 맞는다. 문제는 "리뷰에서 두 번 나온 지적을 승격했다"는 주장이 문서상 사실과 다르다는 점이다. 이렇게 두면 다음 사람이 이 표를 근거 삼아 약한 승격을 따라 한다.
- 고칠 것: 1·2번 근거를 사실대로 바꾼다. 'mentors.md 1절-5 + A6 첫 실행 위반 7건(파일:줄)'로 적고, L-6·C9·server-v2 4·M-4·C8은 빼거나 '관련(이 규칙으로 막히지 않음)'으로 낮춘다.
