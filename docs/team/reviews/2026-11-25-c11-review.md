## 1. 지적 사항

### H1 [높음·`cloud`를 켜기 전에 필수] 원격 층 때문에 세션 백업 제외가 없는 바이너리에서도 `cloud`가 켜질 수 있다

- 무엇: C11에서 `features.ts`에 원격 층이 생겼다. 그래서 서명된 config 하나로 `cloud`를 켤 수 있다. 하지만 원격 config의 하한은 둘뿐이다. `minAppBuild`는 문서 전체에 걸리고, `minBundle`은 JS 판(BUNDLE_SEQ)을 본다. **키마다 바이너리 하한을 거는 방법이 없다.** 그런데 세션 MMKV의 OS 백업 제외는 빌드 2 네이티브 묶음 몫이다(`sessionStore.ts` 주석, architecture 4-2).
- 지금 깨지는 것: **지금은 아무것도 깨지지 않는다.** 플래그가 꺼져 있고 Supabase 환경값이 비어 있어 로그인 포트가 걸리지 않는다. 켜는 순간 아래 일이 생긴다.
  1. 처리방침 10절의 "서버 접속 정보(로그인 세션)는 백업에서 뺍니다"가 거짓이 된다.
  2. 새 폰을 백업에서 복원하면 접근 토큰·갱신 토큰이 같이 온다. 그러면 두 기기가 같은 익명 계정을 쓴다. architecture 3-3 ④는 '새 폰 = 세션 없음 → 되찾기 글귀로 이어 주기'를 전제했는데, 이 흐름을 건너뛴다. C12의 410 moved·되찾기 판정도 '기기 하나 = 세션 하나'를 전제했는데 이 전제가 깨진다.
  3. Supabase 갱신 토큰 회전이 켜져 있으면, 한 기기가 토큰을 갱신하는 순간 다른 기기가 가진 토큰은 폐기된 토큰이 된다. 그 기기가 재사용 간격 밖에서 이 토큰을 쓰면 재사용으로 감지된다(공식 `refresh_token_already_used`). 그러면 그 토큰의 하위 토큰이 모두 폐기되어 **두 기기가 모두 끊길 수 있다.**
  4. 기기 백업이 유출되면 계정을 가져갈 수 있는 경로가 된다(그 계정의 몽망이·공개 페이지 조작).
- 고침 제안: 앱에서 `cloud`의 원격 켬은 '세션 저장소가 백업에서 빠졌다'는 네이티브 확인이 참일 때만 받는다. 예를 들어 `sessionStore.backupExcluded()`를 두고 빌드 2 모듈이 참을 돌려주게 한다. 그 전까지 원격 층의 `cloud`는 `false` 쪽으로만 받는다. 시험은 '백업 제외 미확인 바이너리 + 원격 cloud 켬 → isOn("cloud") 거짓'이다. DECISIONS C11 절의 '남은 것'에 이 조건을 적는다.

### M1 [중간·통계 연결 전] 보내는 도중 통계를 꺼도 남은 핑 덩어리가 나간다(재현함)

- `sendAll`은 동의를 시작할 때 한 번만 본다(`flush` → `enabled()`). 그 뒤에는 미리 만든 핑 목록(32개씩 묶음)을 끝까지 보낸다.
- 재현: 사건 40개 → 핑 2건. 첫 요청을 보내는 동안 `setMetricsOn(kv,false)`를 부르고 동의를 거짓으로 바꿨다. 그래도 **두 번째 요청이 나갔다**(요청 2건). 요청 하나의 제한 시간이 10초이므로 끈 뒤 수십 초 동안 나갈 수 있다.
- 처리방침 3-1은 "끄면 그때부터 보내지 않고"라고 쓴다. 이 문장이 지켜지지 않는다. 연결 실패가 나면 `failedOnce()`가 끈 뒤에 `mong.net.retry`를 다시 쓰는 문제도 있다(해는 없지만 '지운다'는 약속과 어긋난다).
- 고침: 루프에서 요청마다 `if (!enabled()) break;`를 넣는다. `failedOnce`도 `enabled()`일 때만 쓴다. 시험은 '첫 요청 중 끔 → 요청 1건'이다.

### M2 [중간·로그인 연결 전] `signIn()`이 남아 있는 세션을 덮어써 기존 익명 계정이 고아가 된다(재현함)

- 어댑터의 `signIn`은 세션이 있어도 `/auth/v1/signup`을 불러 새 사용자를 만들고 저장소를 덮어쓴다. 재현에서 두 번째 `signIn` 뒤 세션이 A2/R2로 바뀌었다.
- C12 `tasks.signIn`은 `token()`이 null일 때만 `signIn`을 부른다. 그런데 `token()`이 null이 되는 경우가 하나 더 있다. **접근 토큰이 만료됐고 갱신이 timeout·5xx·429로 실패했을 때**다. 이때는 세션(갱신 토큰)이 그대로 있다. 바로 뒤 signup이 성공하면 몽망이가 걸린 원래 익명 사용자에게 다시 닿을 길이 없다. 되찾기 글귀를 받아 두지 않았다면 영구히 잃는다.
- 고침: 어댑터에서 `read()`가 세션을 돌려주면 `signIn`은 새 사용자를 만들지 않는다. 대신 `refresh()`를 시도하고 그 결과를 실패로 돌려준다(offline·unavailable). 시험은 '세션 있음 + 갱신 503 → signIn이 signup을 부르지 않음, 세션 유지'다.

### M3 [중간·로그인 연결 전] 갱신 응답이 400·401이면 무조건 세션을 지운다 — 401은 '토큰 무효'가 아니다

- GoTrue가 갱신 토큰이 무효라고 할 때는 응답 본문의 `error_code`로 알린다. 공식 오류 코드 문서의 `refresh_token_not_found`·`refresh_token_already_used`·`session_not_found`·`session_expired`다. 공식 문서는 이 코드와 HTTP 상태의 짝을 정하지 않는다. 한편 **401은 공개 키(apikey)가 틀렸거나 교체·폐기됐을 때 API 게이트웨이가 주는 응답**이기도 하다. 키 교체 사고나 잘못 넣은 환경값 하나로 갱신을 시도한 **모든 사용자의 세션이 지워진다.** 익명 계정이라 다시 로그인할 수단이 없고, 그때부터는 되찾기 글귀로만 이어 줄 수 있다.
- 갱신 요청이 timeout으로 끝났는데 서버는 회전을 마친 경우도 있다. 그러면 기기에는 옛 토큰이 남고, 재사용 간격(기본 10초) 밖에서 이 토큰을 쓰면 끊긴다. 이것은 회전 정책의 성질이라 코드만으로 다 막을 수 없다. 대신 DECISIONS에 위험으로 적고 Supabase 대시보드에서 재사용 간격을 확인해야 한다.
- 고침: 본문 `error_code`가 위 네 개 중 하나일 때만 `clear()`한다. 그 밖의 400·401은 남긴다. `token()`은 null을 주되 세션은 지우지 않는다. 시험은 '401 `{"message":"Invalid API key"}` → 세션 유지, 400 `refresh_token_already_used` → 비움'이다.
- 확인한 것: 세 REST 경로는 맞다. 익명 signup은 이메일·전화 없이 `POST /auth/v1/signup` 본문 `{data}`다(supabase-js `signInAnonymously`와 같은 경로이고, 캡차를 켜면 `gotrue_meta_security.captcha_token`이 필요하다). 갱신은 `POST /auth/v1/token?grant_type=refresh_token` 본문 `{refresh_token}`이고, 이것은 Supabase Auth README에 있다. 로그아웃은 `POST /auth/v1/logout?scope=local`에 Bearer를 싣는다(supabase-js와 같음). 출처는 supabase/auth README와 Supabase 'Auth error codes' 문서다. **캡차를 켜면 지금 본문으로는 signup이 실패하므로**, 운영 Auth 설정에서 캡차를 쓰지 않는다는 것을 DECISIONS에 고정해야 한다.
- 토큰 로그: `src/net`·새 화면 어디에도 `console`·로그 호출이 없다(grep 0건). 오류 경로도 본문을 밖으로 내지 않는다. 맞다.

### M4 [중간] 딥링크 'HTML = 계약'을 정적 고정물로만 지킨다 — 서버 틀이 바뀌어도 앱 시험은 통과한다

- `test/fixtures/m-page/*.html`은 렌더러 출력을 **손으로 떠 둔 사본**이다. 어느 시험도 `renderLivePage`·`renderGonePage`를 불러 지금 출력과 대조하지 않는다(grep으로 `m-page`를 쓰는 곳은 net-link 시험 하나뿐). 소스에서 정규식으로 읽는 것은 `APP_NAME` 하나다.
- 파서는 틀에 민감하다. `<section class="live-msg"><h1>`이 바로 붙어 있어야 하고, `</h1>`과 `<p>` 사이에는 공백만 와야 한다. `<main id="m" data-state=`의 속성 순서도 고정이다. 서버에서 클래스를 하나 더하거나, 속성 순서를 바꾸거나, `<h1>`에 `lang`을 넣기만 해도 앱 시트는 '보여 드릴 수 없어요'가 된다. 그리고 시험은 초록으로 남는다.
- 고침: 서버 시험에 '렌더러 출력 = `apps/mobile/test/fixtures/m-page/*.html`'(바이트 비교) 한 건을 둔다. 또는 앱 시험이 서버 렌더러를 직접 불러 고정물을 그 자리에서 만든다. 둘 중 하나로 고정물이 낡지 않게 한다. 장기적으로는 `data-` 속성(`data-title`, `data-aux-ko` 등)을 계약 칸으로 두는 것도 검토한다. 그러면 화면 마크업과 계약이 떨어진다.
- 주소 검증은 맞다. 호스트를 그대로 비교하고(소문자), 사용자 정보·포트·http·하위 경로·다른 호스트·`mongmang.ink.evil` 꼴을 거부한다. `%` 인코딩은 풀린 뒤 `normalizeCreatureCode`가 정규 8자만 통과시킨다. 서버로 보낼 때는 정규 코드를 `encodeURIComponent`로 다시 싸므로 경로 주입이 없다. B7a H1과 같은 오픈 리디렉트 종류의 문제는 없다. 앱은 받은 주소로 이동하지 않고 코드만 꺼낸다.
- 신고 본문은 `reportRequestSchema.parse({reason})`의 결과 하나뿐이다. 요청 스냅숏 시험이 `{"reason":"personal"}`와 머리글 전체를 고정한다. 맞다.

### M5 [중간] 시험 빈틈 — 변이 12개 중 3개가 살아남았다(6절)

- `due()`의 '시계가 되돌아감 → 다시 받기'(`age < 0`) 줄을 지워도 시험이 통과한다. 이 줄이 없으면 시계를 앞으로 돌린 뒤 되돌린 기기가 max-age·TTL 판정에서 '아직 신선함'에 갇힌다. 그동안 새 킬 스위치를 받지 못한다(만료 14일이 상한).
- ETag를 '지금 쓸 수 있는 캐시'일 때만 싣는 조건(`&& current()`)을 지워도 통과한다. 이 조건이 없으면 만료된 캐시에 대해 304를 받고 신선하다고 표시한 채 번들 기본값으로 남는다. 다만 `current()`가 만료를 다시 보므로 원격 값이 되살아나지는 않는다. 손해는 다시 받기가 늦어지는 것이다.
- `Cache-Control: no-store/no-cache → 0`을 지워도 통과한다.
- 고침: 세 줄에 시험을 하나씩 둔다.

## 2. 낮음

- **L1 연령 판이 바뀌거나 미달로 다시 판정된 뒤에도 켠 표시·아웃박스가 남는다.** `metricsConsent`가 거짓이 되므로 나가지는 않는다. 하지만 같은 사람이 나중에 다시 통과하면 **다시 켜지 않았는데도** 통계가 다시 나가고, 그 전에 모아 둔 아웃박스(7일 안)도 함께 나간다. 연령 판을 올리는 까닭은 대개 고지나 확인 방식이 바뀐 것이므로 다시 동의를 받는 편이 맞다. 제안: `ageStatus`가 passed가 아닐 때 켠 표시·아웃박스·재시도 대기를 지운다(`metricsSetting`을 읽을 때나 `recordAge` 뒤에). 처음 켤 때도 아웃박스·재시도 대기를 비운다. B0 opt-out 시절 기기에 남은 칸이 동의 뒤에 나가지 않게 하기 위해서다.
- **L2 켜기 전에 일어난 사건을 켠 뒤에 보낸다.** `syncOnce`는 세이브 상태에서 7일 안의 평생 한 번 사건(첫 탭·이름 짓기 등)을 뽑는다. 그래서 켜기 이틀 전에 지은 이름도 켜는 날 핑에 실린다. 식별자는 없지만 3-1의 "직접 켠 경우에만 보냅니다"를 '켠 뒤에 일어난 것만'으로 읽는 사람이 있을 수 있다. 방침에 한 줄 더하거나(아래 5절 문구 ③) 코드에서 켠 날 dayN 이상만 받는다. QA-3 의견은 방침에 적는 쪽이다(D1 리텐션 측정 목적과 맞음).
- **L3 탈출 기록이 있는데 실행을 시작할 때 활성 원격이 없으면(캐시 만료·쓰기 실패) 같은 v를 다시 받았을 때 그 실행 동안 탈출이 풀린다(재현함).** `startRun`은 `active()`가 null이면 탈출 기록을 읽지 않는다. 그 뒤 `applied()`는 `escape.kind === 'normal'`이라 같은 v3를 그대로 적용한다. 다음 실행에서는 탈출이 되살아나므로 손해는 크래시 한 번이다. 고침: `startRun`이 active 여부와 상관없이 저장된 탈출을 메모리에 올린다. `applied()`는 그 v와 비교한다.
- **L4 고정 User-Agent는 핑·로그인에만 쓴다.** 맡겨 두기 API(`cloud/api.ts`)·`/m` 조회·신고는 기본 UA로 나간다. 처리방침 3-1의 "User-Agent(앱 이름과 판, 운영체제 종류가 드러날 수 있음)"는 거짓이 아니다. 다만 B4 P9의 '고정된 앱 이름만'으로 문구를 좁히려면 `http.request` 기본 머리글로 올려야 한다. RN에서 iOS NSURLSession·Android OkHttp가 덮어쓴 `user-agent`를 그대로 보내는지는 **실기기에서 확인해야 한다**(12-12 리허설).
- **L5 포스터 주소는 https인지만 본다.** 서버 렌더러가 `publicOrigin`으로 거르지만, 앱도 허용 호스트(공개 스토리지 출처)로 한 번 더 좁히는 편이 낫다(두 겹 방어).
- **L6 팩 sha가 틀려도 무한 루프는 아니다.** 한 refresh에 2회로 끝나고, 시험이 '세 번째 요청 없음'을 고정한다. 그러나 `refresh`는 매니페스트를 다시 받을 때가 아니어도(`skipped`) `wanted` 전체를 다시 훑는다. 그래서 깨진 팩 하나가 **포그라운드마다 2회씩** 계속 요청된다. 틀린 sha를 `(sha, 매니페스트 seq)`로 기억해 같은 매니페스트에서는 다시 묻지 않게 한다.
- **L7 `LinkReceiver`는 플래그 `link`와 무관하게 늘 걸려 있다.** 원격으로 끌 손잡이가 없다. 링크를 받는 쪽은 계정 없이 웹 방문과 같으므로 허용할 수 있다. 그래도 신고 POST까지 앱에서 나가므로 `link`(또는 새 키)로 끌 수 있게 할지 PM이 결정해야 한다.
- **L8 처음 켤 때 `mong.net.once`를 비우지 않는다.** B0 빌드에서 '보냄' 표시만 남은 사건은 동의 뒤에도 다시 나가지 않는다. 통계가 적게 잡힐 뿐이고 개인정보 문제는 아니다.

### 2. 새 지적

#### N1 [높음·로그인 연결 전 필수] 일시적인 토큰 실패가 C12 `runTask`의 '예전 계정' 가드를 밟아 세션과 기록을 지운다 — M2·M3의 보호가 무력해진다(재현함)

- 경로: C11 어댑터의 `token()`은 접근 토큰이 만료됐고 갱신이 오프라인·timeout·5xx·429·키 오류로 실패하면 **세션을 둔 채 null**을 돌려준다(M3 고침대로). 그런데 main의 `cloud/tasks.ts` `runTask` 첫 줄은 다음과 같다.
  `if (NEEDS_LOGIN.has(task.t) && readRecord(d.kv)?.state === 'on' && !(await d.auth.token()...)) return await orphan(d);`
  이 줄은 '토큰 null = 로그인 없음(백업 복원 폰)'으로 읽는다. 그래서 `orphan()`이 '예전 계정' 표시를 `abandoned: true`로 남기고, 기록을 비우고, **`signOut()`을 부른다.** 실제 어댑터에서 signOut은 세션을 지운다.
- 재현: fake 서버로 enable → `enabled`. 그 뒤 토큰 null(만료 + 오프라인을 흉내) 상태에서 `sync`를 돌렸다. 결과는 `{"r":"orphaned"}`, 기록 `null`, 미확인 지움 표시 `{reason:"orphan", abandoned:true}`, signOut 1회였다. 따로 어댑터를 시험해 '만료 + 오프라인 → token() null, 세션 남음'도 확인했다.
- 현실 시나리오: 접근 토큰 수명은 기본 1시간이다. 1시간 넘게 앱을 안 연 사용자가 지하철처럼 오프라인에서 앱을 열면, 맡기기(sync)가 돌 때 **맡겨 두기가 끊기고 로그인을 잃는다.** 되찾기 글귀가 없으면 영구 손실이다. 리뷰 M2·M3이 막으려던 바로 그 결과다.
- C12 시험이 이것을 못 잡은 까닭: `fakeServer.authFor().token()`은 오프라인이어도 토큰을 돌려준다. 즉 '세션은 있는데 지금 토큰을 못 받음' 상태가 시험에 없다.
- 고침 제안(C11·C12 공동): `CloudAuth`에 `hasSession(): boolean`(동기, 저장소만 봄)을 더하거나, `token()`이 `{kind:'none'} | {kind:'unavailable', failure} | {kind:'ok', token}`을 돌려주게 한다. `runTask` 가드는 '세션 없음'일 때만 orphan으로 보내고, 'unavailable'이면 `fail(failure)`로 끝낸다(기록·세션 유지). `currentSub`도 같은 구분을 써서 일시 실패를 '다른 로그인'으로 읽지 않게 한다(`loginGone`이 'ended' 대신 orphan으로 가는 갈래). 시험은 '세션 있음 + 갱신 offline → sync = failed offline, 기록·세션 유지'를 fake auth에도 넣는다.

#### N2 [낮음] 시험 빈틈 2건(변이 생존)

### 1. N1 — 풀림

- `TokenState = ok | none | unavailable`로 나뉜다. 어댑터는 세션이 없으면 none을, 만료 + 갱신 실패이면 **세션이 남았을 때만** unavailable을 돌려준다. Auth가 '끝남'이라 해서 세션을 비운 뒤에는 none이다. 갱신이 성공했는데 세션을 다시 읽지 못하면 unavailable(device)이다.
- C12 쪽에서 none은 '예전 계정'(orphan)으로만 간다. unavailable은 다음 세 곳에서 모두 `fail(failure)`로 미루고 기록·세션·표시를 건드리지 않는다.
  - `runTask` 가드
  - `loginGone`(no_account 뒤 지금 로그인을 확인하지 못한 경우)
  - 켜기의 `signIn`(새 사용자를 만들지 않음)
- `readToken`은 포트가 던지면 unavailable(offline)로 읽는다.
- 재리뷰 때 재현한 경로(enable → 만료 + 오프라인 → sync)는 cloud 시험 '[C11 재리뷰 N1 재현]'이 그대로 고정한다. sync·fetch·reissue·deleteCheck 모두 `failed offline`이 되고, 기록은 같고, 미확인 지움 표시는 없고, 세션은 남는다. 연결이 돌아오면 같은 sub로 이어진다. 가짜 서버도 '만료 + 오프라인 → unavailable'을 흉내 낸다. 이 흉내 줄을 지우면(B5) 시험이 빨개진다.

### 2. none과 unavailable의 기준 ↔ Supabase GoTrue

- none이 되는 경우는 둘뿐이다. 기기에 세션이 없거나, 갱신 거절 본문이 `refreshEnded`에 걸린 경우다. `refreshEnded`는 C11 M3의 `TERMINAL_REFRESH_CODES`(refresh_token_not_found·refresh_token_already_used·session_not_found·session_expired·user_not_found·user_banned)와 옛 GoTrue `invalid_grant` + 'Invalid Refresh Token'으로 판정한다. 이 기준은 **M3 목록과 같은 함수 하나에서 나온다(일관됨).** Supabase 'Auth error codes' 문서의 '세션이 끝나 새 로그인이 필요한' 코드들과 맞는다.
- 그 밖의 거절은 모두 unavailable이다. 연결 실패(offline), 시간 초과, 5xx(unavailable), 429(rateLimited), 401 `Invalid API key`·모르는 400(server)이 여기에 든다. net-auth 시험이 offline·503·401 키 오류·`refresh_token_not_found` 네 갈래를 표로 고정한다.
- 남는 위험(낮음): GoTrue가 앞으로 '끝남'을 뜻하는 새 `error_code`를 더하면, 그 사용자는 none이 아니라 unavailable(server)에 머문다. 데이터를 잃지는 않고 아래 3절의 '영원히 못 받음'이 된다. 코드 목록을 GoTrue 판 올림 때 확인하는 항목으로 B6 점검표에 두기를 권한다.

### 3. unavailable이 영원히 이어질 때 사용자에게 보이는 것 — **N3 [중간·자동 맡기기 연결 전]**

- 지금: 맡기기는 아직 사용자가 시트에서 직접 누를 때만 돈다(`model.ts`의 sync는 사용자 사건, `useCloud.runTask`). 누를 때마다 `failed` 화면이 까닭별 문구를 보인다('서버 쪽 문제로 지금은 하지 못했어요' + '이 기기의 몽망이는 그대로예요'). 시트에는 '마지막으로 맡긴 때'(`cloud-last`)가 보인다. 그래서 **조용히 멈추지는 않는다.**
- 그러나 상태가 쌓이지 않는다. 키 사고나 계속되는 갱신 거절로 며칠·몇 주째 못 받아도, 공방 노트 행(`cloudRowState`)은 계속 'on'('맡겨 둠')이다. 몇 번을 실패해도 다음 길(되찾기 글귀로 이어 주기, 문의)을 안내하지 않는다. 자동 맡기기가 연결되면 실패가 화면 밖에서 일어나므로 이 문제는 '조용히 영영 안 됨'이 된다.
- 고침 제안(자동 맡기기 연결과 같은 작업에서):
  1. 기록에 `lastFailAt`·`failSince`(unavailable 또는 실패가 처음 시작된 때)를 둔다.
  2. `syncedAt`이 N일(예: 3일)보다 오래됐고 그동안 실패만 있었으면 행을 'paused'(또는 'attention')로 바꾸고, 시트 첫 줄에 '한동안 맡기지 못했어요 — 이 기기의 몽망이는 그대로예요. 계속되면 되찾기 글귀를 확인해 두세요'를 보인다.
  3. 같은 까닭(server)이 연달아 오면 운영 경보가 서버 쪽에서 먼저 울린다(갱신 401은 우리 서버 로그에 남지 않으므로 Supabase 대시보드 경보 B6).
  시험은 '실패 N일 → 행 paused + 안내 문구'다.
