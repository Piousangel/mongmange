## 치명

### C1. 소프트런칭 판정 기준 대부분이 통계적으로 판정 불가다 (2-16·4-4·10·10-1)
- 소프트런칭은 Google 전용·캐나다·뉴질랜드·필리핀·광고비 0원(D-18)이다. 5주 동안 설치가 수백 건이면 많은 편이다 [팀 추정].
- **이름 시점 A/B**의 기준 "A가 D1을 −2%p 이내로 지킴": D1이 약 35%일 때 2%p 차이를 검정력 80%로 보려면 한 군에 약 9천 명이 필요하다(정규 근사). 군마다 수백 명이면 신뢰구간이 ±6~8%p라서 어떤 결과가 나와도 '통과'로 읽힐 수 있다.
- **설계 결함이 하나 더 있다**: A안은 이름 시점과 **알림 권한 시점(하루 늦춤)을 함께 바꾼다**(2-16). D1에 차이가 나도 어느 변수 때문인지 가를 수 없다(교란).
- **D30 6%**: 02-16 판정 시점에 D30이 나오는 코호트는 01-12~01-17 설치자뿐이다. 그 표본에서 6%는 몇 명 수준이다.
- **Q9 '분실 문의 0건'**: 유저가 적고 iOS가 빠지면(I6) 0건은 안전하다는 증거가 못 된다.
- **고칠 것**
  1. 판정 규칙을 미리 고정한다. 지표마다 **최소 표본**을 정하고, 미달이면 '미판정 → 정해 둔 기본값'으로 간다. 이름 시점은 업계 기준선인 A를 기본값으로 둘지 C 2-2 근거대로 B를 둘지 지금 정해 둔다.
  2. A/B의 주지표는 **효과가 큰 '7일 안 이름 지은 비율'**로 하고, D1은 신뢰구간을 적은 가드레일 참고값으로만 쓴다.
  3. 알림 권한 시점은 두 군에서 같게 둔다. 바꾸려면 따로 실험한다.
  4. D30 관문은 "D30 ≥ 6%"가 아니라 "**D30 신뢰구간 하한이 X% 이상** 또는 표본 미달이면 D7·D14 추세로 대체"로 다시 쓴다(서버 아키텍처 9절 #9와 같은 경고).
  5. Q9에는 **내부 기기 이동·충돌 시나리오 자동 테스트**(iOS·Android 각 20회 이상, 두 기기 번갈아 쓰기 포함)를 주 근거로 둔다.

### C2. 6절 서버 명세가 서버 아키텍처 v1과 개인정보에서 세 곳 충돌한다

'Not Linked to You' 주장이 약해지고 14세 미만 데이터가 동의 없이 쌓인다. 이 id가 없어도 D1·D7·D30·A/B를 잴 수 있다 | 아키텍처의 집계 핑을 채택한다. 실험 배정(`nameTiming`)·위젯 사용 여부·보름 창은 **집계 칸의 차원**으로 넣는다. 6-5 이벤트 11종을 아키텍처 화이트리스트와 하나로 합친다 |

### C3. 일정 논리(4-4)가 D-22 이전 전제이고, 진짜 임계 경로를 놓쳤다
- 4-4는 '6주 연기'를 주장한다. D-22는 이미 "03-16은 상한, 관문 통과 즉시, 매주 당긴다"로 바꿨다. 문서가 낡았다.
- 더 중요한 점: 출시일을 정하는 것은 개발 36일이 아니라 **측정 시계**다. ① Google 개인 계정의 비공개 테스트 14일(11-29 → 12-13) ② 프로덕션 접근 신청·심사 [확인 필요: 소요일] ③ 소프트런칭 첫 코호트의 D30(시작 + 30일 이상). v2 일정은 소프트런칭을 01-12로 **늦췄다**(기존 12-29). 그래서 D30 판독이 02-11 이후로 밀렸고, 그게 03-16의 실제 원인이다.
- **가장 빠른 현실적 순서**는 5절에 적었다. 요지: 지표 핑·원격 플래그·네이티브 설정을 빌드 2에 먼저 넣고, 소프트런칭을 Google이 허용하는 가장 이른 날(12-22 전후 목표 [확인 필요])에 시작한다. 서버 기능은 소프트런칭 중에 **OTA(expo-updates)와 플래그로** 차례로 켠다. 그러면 D30 첫 판독이 01-21 전후로 당겨지고, 관문을 통과하면 **02월 초 출시가 다시 가능하다**. 03-16은 상한으로만 남긴다.

## 중요

### I1. (과제 1) 1위 기준선 대비 — 빠진 것·과한 것
- **보름밤은 '05에 더한 것'이 아니다.** 05 0절 2번·G2가 직접 권한 항목이다("D-21 ④ 원격 플래그로 켜고 끔, 첫 회는 출시 직후 보름"). 0-1 표 X3 행과 11절 8번의 "05 권고에 발자국·보름밤을 더했다"는 사실과 다르다. 보름밤의 1.0 편입은 **타당하다**. 다만 아래를 고친다.
  - 보름 표는 **서버가 필요 없다.** 달 위상 계산은 `packages/core`의 순수 함수(수십 줄)로 끝나고 **현지 날짜 기준**으로 계산해야 맞다. `MoonCalendar.date(UTC)` 1년치 표는 한국·미주에서 보름 창이 하루 어긋날 수 있다. 서버 몫은 보름 모티프 팩뿐이다(첫 3개월분은 번들).
  - **'둥근 전체 수' 문장은 1.0에서 뺀다.** ① P4('숫자 없음')와 스스로 모순이다. ② 소프트런칭·출시 초 규모에서는 "약 0명/1천 명"처럼 초라하거나 부풀려 보인다. ③ '어젯밤'의 집계 시점이 시간대마다 달라 한국 아침 7시(UTC 전날 22시)에는 집계가 끝나 있지 않다. DAU가 임계값(예: 1만)을 넘은 뒤 플래그로 켠다. 그러면 S6의 서버 공수는 거의 0이 된다.
- **S3 발자국은 과하다. 1.0 관문에서 빼고 1.0 직후 첫 묶음으로 옮길 것을 권한다.** 05 4-2는 '링크 손님 프리셋 반응'을 **1.x의 친구 그래프 없는 소셜 2순위**로 두었다. 이득은 링크를 공유한 소수에게만 돌아간다. 비용은 무인증 공개 POST(봇·IP 순환 남용), IP 소금 해시 30일 보관, 공유자 계정 필수, 앱·웹·서버 세 레인 작업이다. 기획 스스로도 자르는 순서 1번으로 두었다. D-22는 '리뷰 반영분 예외'를 허용한다. 남긴다면 **플래그 꺼짐으로 출시하고 관문(Q)에서 뺀다.** `visitorKey` 원본 보관은 30일 → 48시간으로 줄인다(3단계 묘사만 필요).
- **S2 '살아 있는 웹'은 05 범위('링크 웹 보기') 안이지만 구현 방식이 과하다**(I2).
- **S1 Apple·Google 연결**: 05·아키텍처 모두 1.0 밖이다. 되찾기 글귀 + OS 백업으로 기준선(B10 '잃지 않음')을 채운다. 1.0.x로 옮긴다(−1.5일, 새 네이티브 모듈 2개 회피).
- **빠진 것**
  - 05 B10 '안정성': 서버 장애·버전 불일치 런북은 있다. 그런데 **iOS 실사용 검증 경로가 없다**(I6).
  - 05 G6 '서버가 꺼져도 100% 동작'은 Q5로 들어갔다. 다만 **서버가 느린 경우**(300ms~5s 타임아웃 경계, 반쯤 성공한 업로드)를 테스트 항목으로 명시한다.
  - 05 4-2 '운영: 신고·숨기기 + 서버에서 내리기'의 1인 운영 SLA가 기획은 48시간(Q12), 아키텍처는 '주 1회 메일 확인·7일'이다. 하나로 정하고, 오너가 감당할 수 있는 값으로 고친다.

### I2. S2 살아 있는 웹 — 가장 큰 항목(8.5일)인데 첫인상 위험이 가장 크다
- 카카오톡·인스타 인앱 브라우저에서 CanvasKit wasm(수 MB [확인 필요])을 받는 동안 페이지는 빈 한지다. 링크 → 설치 전환에서 첫 1~2초가 가장 비싸다. 아키텍처 v1은 '템플릿 HTML 50KB 미만'을 목표로 했는데, 기획 v2는 반대 방향이다.
- 서버 쪽 **OG 렌더(Node CanvasKit) + 8초 MP4 사전 렌더**는 Cloud Run 위에 헤드리스 렌더 + 인코더 파이프라인을 두는 일이다. 서버 2.5일 안에 들어가지 않는다 [팀 추정].
- **고칠 것**: 기기가 이미 가진 것을 쓴다. ① OG 1200×630 변형은 **앱이 렌더해 업로드**한다(아키텍처 3-5와 같음). ② 8초 루프는 D-18 자체 인코더로 **앱이 만들어 업로드**한다(이레 두루마리 영상과 같은 경로, 12-05 관문 실패 시 정지 이미지). ③ 웹은 정적 HTML + 영상·이미지를 먼저 보여 주고, WebGL이 되는 브라우저에서만 첫 페인트 **뒤에** CanvasKit을 지연 로드해 탭 반응·'획 → 몸'을 붙인다. 서버 렌더 0이 되고, 웹 5.0일 중 일부와 서버 1.5일 이상이 줄어든다.

### I3. (과제 3) 위젯 — 출시 전 필수 판단은 동의, 공수와 경로가 틀렸다
- **필수 판단**: 동의한다. 05 B4·G1 기준선이고, 잠 → 아침 리듬에 가장 잘 맞는다. 다만 위젯은 소프트런칭 판정 대상이 아니라 **관문 Q14(크래시 0·죄책감 장면 0)만** 보면 된다.
- **'네이티브 모듈 없음'은 틀렸다.** 위젯은 앱 확장 타깃이고, 앱 → 위젯 데이터 전달에 네이티브 코드가 필요하다.
  - iOS 경로(Expo CNG 유지): `@bacons/apple-targets` config plugin으로 WidgetKit 확장 타깃(Swift 코드는 레포의 `targets/widget/`에 둠)과 **App Group** entitlement를 만든다. 앱은 공유 컨테이너에 PNG 3장 + 시간표 JSON을 쓰고 `WidgetCenter.shared.reloadAllTimelines()`를 불러야 한다. JS에서 이 둘을 하려면 **작은 로컬 Expo 모듈(Swift 수십 줄)**이 필요하다. `expo-file-system`의 Apple 공유 컨테이너 경로 지원 여부, Expo의 `expo-widgets`(알파) 사용 가능 여부는 [확인 필요]. EAS가 확장 타깃용 번들 id·프로비저닝을 따로 만든다(오너: Apple Developer 계정 필요, C9와 같은 의존).
  - Android 경로: `react-native-android-widget`(config plugin, JSX로 RemoteViews를 그리고 이미지 지원) 또는 Kotlin `AppWidgetProvider`. `updatePeriodMillis` 하한이 30분이라 잠·아침 전환 정확도는 **앱 이벤트 때 즉시 갱신 + 30분 주기**로 충분하다(정확한 알람은 권한 부담).
  - **D-04: 로컬 Xcode가 없다.** Swift 위젯을 EAS 빌드(회당 수십 분, Android 메모리 이력)로만 디버깅해야 한다. 3.0일(iOS 1.5) → **5~6일**로 잡는다. 네이티브 변경(위젯 타깃·App Group·`associatedDomains`·`intentFilters`·`expo-updates`)은 **한 번의 네이티브 빌드로 묶는다**(빌드 2).
- **위젯에 보일 것**(기획 3상태에 덧붙임)

### I4. (과제 4) 개인정보·연령·공개 페이지
- **연령 확인 실효성**(C2-a 뒤에도 남는 것): ① '아니요'라고 답한 기기는 답을 기록하고 같은 날 다시 묻지 않는다(바로 고쳐 답하기 방지). 서버에는 `under14`를 저장하지 않는다. 아니요면 계정이 생기지 않으니 저장할 곳도 없다. 그러면 `Account.ageScreen` 필드는 `14plus` 기록 하나로 줄어든다. ② 법정대리인 동의를 제공하지 않는다는 것과, 기기 안 게임·이미지 공유는 그대로라는 안내 문구(작가 몫). ③ 대안인 '타깃 14세 이상 상향'은 스토어 등급·마케팅에 영향이 거의 없고 법적으로 가장 단순하다. 12-05 결정 때 **기본 권고안**으로 올린다. [확인 필요: 법률 검토]
- **공개 페이지에서 드러나는 것**
  - `태어난 날짜 + 날 세기`(+ `strokesTotal`·`dayCount`가 공개 사본에 들어가면)를 주기적으로 보면 **주인이 매일 들어오는지(활동 리듬)**가 드러난다. 링크를 아는 지인(가족·연인·동급생)이 볼 수 있다. 공개 사본은 링크를 켤 때와 주인이 '다시 만들기'를 누를 때만 갱신하고, 획 수·날 세기는 그 시점 값으로 고정한다.
  - 이름은 실명 위험이 있다. 기본 비공개 + 필터는 좋다. **OG 이미지·`og:title`에도 같은 `nameVisibility`가 적용된다**고 명시한다(아키텍처 3-5는 `og:title` = 이름).
  - 파생 획(≤64점 + attach)만 공개하는 것은 적절하다.
- **보관 기간**
  - 세이브 원본(점열의 시간 t·필압 p)은 6-4에서 '생체 정보에 가깝다'고 규정했다. 그런데 이력을 8주 보관한다. 복원에 필요한 것은 최신본 + 충돌본이다. 이력은 **4주(최신 3 + 주 1개씩 4주)**로 줄이고 처리방침에 적는다.
  - 장기 미사용 계정 정리(아키텍처: 2년)가 기획 6-6에 없다. 넣는다.
  - 신고 1년은 보관 목적(재발 판단)을 적고, 신고자 키는 일일 해시로 둔다.
  - 백업 속 사본 7일 소멸 고지는 아키텍처와 맞춘다.
- **데이터 라벨**: C2-b를 반영하면 Usage Data를 'Not Linked'로 유지할 수 있다. 위젯은 서버로 아무것도 보내지 않는다는 점도 라벨 검토표에 적는다.

### I5. (과제 2) 밤물·몽망이끼리 소셜 — 우아함·독창성·위험
- **우아함·독창성: 높다.** Tamaverse식 '남의 아이가 지나감'을 물·종이 결·먹 번짐으로 번역해 글 없이 언어를 넘는다. 할 일 0, 끄면 그대로라 피로가 생길 틈이 작다. "다른 게임에서 본 것 같은가?"(OPERATING 0-1)에 대해서는 구조는 익숙하지만 표현이 새롭다고 판단한다. 1.0 직후 보조로 두는 판단에 동의한다.
- **위험과 보강**
  1. **신고 대상이 0.3배 번진 실루엣이다.** 유저는 무엇이 문제인지 잘 못 보고, 관리자는 원본을 봐야 판단한다. 관리 도구에 `encounter` → 손님 몽망이 파생 획 원형 보기를 넣는다(S5 관리 도구 범위 확장, 1.0 직후).
  2. **손님 먹이 내 먹과 같을 확률이 25%다**(같은 네 먹). 그날 선물이 무의미해진다. 같은 먹이면 조각 모양·번짐 무늬만 다르게 하거나 같은 먹 손님은 고르지 않는다.
  3. **호스트 쪽 비대칭**: 한 번도 손님이 오지 않는 아이가 생길 수 있다(풀 무작위). 문장이 없으니 D-03 충돌은 없지만, 고를 때 '최근 손님을 덜 받은 아이' 가중을 둔다.
  4. **N4 동기**: 같은 날 태어난 여섯을 고를 때 실루엣이 극단적인 아이(신고 이력·이상 형태)를 빼는 필터가 필요하다. 이레 두루마리는 공유 소재라 남의 아이가 퍼진다(실루엣이지만).
  5. **아동**: 14세 미만이 차단되므로 밤물 노출은 없다. 다만 '아니요'의 대가(맡겨 두기·밤물 없음)가 거짓 응답 동기를 만든다. 타깃 14+ 상향이 이 문제도 없앤다(I4).
  6. **악성 링크·스팸 쓰다듬기**: 웹에서 할 수 있는 것이 쓰다듬기 하나이고 먹점 상한이 3이라 피해 상한이 낮다. 남는 위험은 **불쾌한 이름 + 형태 페이지를 밈으로 퍼뜨리는 것**이다. 신고 3건 자동 숨김 + 이미지 파일 삭제 즉시 반영(C2-c)으로 충분하다.
