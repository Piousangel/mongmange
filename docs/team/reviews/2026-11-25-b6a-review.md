## 판정: 조건부 통과

드라이버 계약·DB TLS·로그 위생은 잘 되어 있다. 오류를 숨기지 않고 실패로 드러내며, DB TLS를 우회할 길은 찾지 못했다.
막는 결함은 둘이다.
- **H1**: 서명 업로드 URL이 2시간 동안 살아 있다. 그래서 계정 삭제·새 PUT·링크 끄기 **뒤에** 옛 URL로 올린 파일이 대기 행 없이 staging에 **영구히** 남는다. 직접 재현했다.
- **M1**: README의 Firebase 맞춤 역할 권한 이름은 존재하지 않는다. 실제로 필요한 권한은 사이트 전체를 배포할 수 있는 권한이다.

H1은 `STORAGE_DRIVER=supabase`를 켜기 전에 고쳐야 한다. M1은 오너 결정 전까지 `CDN_DRIVER=firebase`를 켜지 않는다. 지금 YAML은 둘 다 `none`이므로 이 상태로 커밋해도 운영 동작은 바뀌지 않는다. 바뀌는 것은 DB CA 필수뿐이다.

## 발견

### 높음

**H1. 서명 업로드 URL(2시간)이 삭제·버리기·끄기보다 오래 살아, 그 뒤 올린 파일이 staging에 영구히 남는다(삭제 완전성·처리방침 6절)**
- 위치: `deletion.service.ts` 83·106행(삭제 시 staging 행을 `now`로 당겨 처리 뒤 행 삭제), `page.service.ts` `dropPending`(`notBefore: now`), `disable`. 2시간 꼬리 행은 `commit`(283행)에만 있다.
- 경로: Supabase 서명 업로드는 되돌릴 수 없고 2시간 유효하다(소스 `getSignedUploadURL.ts`: 만료 = 서버 설정 `uploadSignedUrlExpirationTime`). 그 사이 판 폴더가 지워지면 '같은 키에 객체 없음'이 되어 x-upsert가 없어도 업로드가 성공한다. 그런데 그 접두를 다시 볼 대기 행이 없다. 계정 삭제 경로에서는 `creature_id`·`store_key` 행도 사라져 아무도 그 접두를 찾지 못한다.
- 영향: 삭제한 계정의 og.jpg가 비공개 버킷에 기한 없이 남는다. og.jpg에는 이름이 그려져 있을 수 있다(B5 'ogPoster'). 여러 기기(A에서 링크 만드는 중, B에서 계정 삭제)나 업로드 도중 삭제처럼 정상 사용에서도 생긴다. local 드라이버도 같은 구멍이 있었지만 창이 5분이었다. B6a에서 24배로 커졌고, DECISIONS B6a ②는 'commit 뒤 staging 대기 행 2시간이 늦은 업로드를 지운다'고 해 이 세 경로도 덮는 것처럼 읽힌다.
- 고칠 방향(작성자 판단): 세 경로 모두 `page-staging` 행을 하나 더 넣는다. 그 행은 `now + SIGNED_UPLOAD_MAX_LIFE_MS`에 같은 접두를 지우는 꼬리 행이다. 계정 삭제는 `store_key` 단위 꼬리 행이고, `creature_id`는 FK가 아니므로 남길 수 있다. `deletion` 처리 때 이 꼬리 행이 함께 당겨지지 않도록 reason이나 조건을 분리한다. 시험은 이 리뷰의 탐침 3경로를 그대로 쓴다.

### 중간

**M1. Firebase 맞춤 역할 권한이 존재하지 않는 이름이다. 실제 필요 권한은 사이트 전체 배포 권한이다(권한 범위)**
- `deploy/README.md` 8-3과 DECISIONS B6a는 `firebasehosting.releases.list`·`firebasehosting.releases.create`를 쓴다. Google Cloud IAM 문서의 Firebase Hosting 권한은 `firebasehosting.sites.{create,delete,get,list,update}`뿐이다(관리자 역할은 `firebasehosting.*` 와일드카드). releases·channels 단위 권한은 없다. 그대로 실행하면 `gcloud iam roles create`가 '알 수 없는 권한'으로 실패할 가능성이 높다 [확인 필요: 실제 gcloud 실행].
- 릴리스를 만들려면 `firebasehosting.sites.update`가 필요하다. 이 권한은 Hosting 권한이 프로젝트 수준이라 같은 프로젝트의 모든 사이트에 걸린다. 버전을 만들고 내는 일, 즉 `mongmang.ink` 정적 사이트 전체(처리방침 페이지·AASA·assetlinks·원격 설정 파일)를 바꾸는 일까지 포함한다. Cloud Run 인스턴스가 뚫리면 사이트 변조로 번진다. 정본 0-3 B6 체크의 'Hosting 릴리스 권한만 가진 무효화용 서비스 계정'은 이 세분성으로는 만들 수 없다. 그리고 B6a는 별도 계정이 아니라 `mong-api-run`에 붙인다.
- 오너·PM 결정 거리: ① 받아들이고 문서를 `sites.get`+`sites.update`로 고친다(위험을 적고). ② `/m`을 별도 Firebase 프로젝트의 사이트로 분리해 폭발 반경을 그 사이트로 줄인다. ③ 무효화를 하지 않고 s-maxage를 5분 바닥으로 둔다. 처리방침은 '최대 1시간'이므로 ③으로도 약속은 지켜진다.

**M2. live 재릴리스가 동시에 일어난 정적 배포를 되감을 수 있다**
- `purgeSite()`는 ① `GET channels/live`로 V1을 읽고 ② `POST releases?versionName=V1`을 보낸다. 그 사이에 web-static 배포(`firebase deploy`)가 V2를 내면, ②가 **V1을 다시 내서 사이트를 옛 판으로 되돌린다**. 조건부 릴리스(etag)는 없다. 창은 수백 ms이지만, 무효화 요청은 링크 끄기·commit·삭제·격리 때 1분 묶음으로 언제든 생긴다. 되돌아간 상태는 다음 배포 때까지 아무 알림 없이 이어진다. 처리방침 개정 게시 직후라면 옛 방침이 다시 나간다.
- 고칠 방향: 릴리스 뒤 `releases.list`(pageSize 2)로 바로 앞 릴리스의 버전을 본다. 그 버전이 우리가 낸 V1이 아니면 그 버전을 한 번 더 내고, error 로그를 남긴다. 아니면 web-static 배포 절차에 '배포 뒤 live 버전 확인'을 넣는다. 최소한 README 8-3에 이 경합과 확인 방법을 적는다.

**M3. CDN 무효화가 사용자 요청 안에서 동기로 돈다. Firebase가 느리면 최대 약 30초 늦어진다**
- `CdnPurgeQueue.request()` → `flush()` → `purgeSite()`(토큰·채널·릴리스 각 10초 제한)를 commit·링크 끄기·계정 삭제·신고 격리(신고 요청) 응답 **전에** 기다린다. `CountingInvalidator` 때는 0ms였다. Firebase 장애 동안에는 1분마다 첫 요청 하나가 최대 30초를 기다린다. 앱 쪽 시간 초과와 재시도가 겹치면 같은 판 commit이 두 번 올 수도 있다. 409로 막히지만 사용자에게는 실패로 보인다.
- 고칠 방향: 요청 경로에서는 `requested_at`만 적고 flush를 기다리지 않는다(Scheduler 1분이 낸다). 아니면 요청 안의 flush에 짧은 제한(예: 2초)을 둔다.

### 낮음

- **L1. `cdn_purge_failed` 로그에 단계·상태가 없다.** `cdn-purge.ts`는 `type: e.name`만 찍어 늘 `CdnPurgeError`로 나온다. README 8-3은 '로그 `cdn_purge_failed`의 단계 `release`'로 403을 가려낸다고 쓴다. `step`·`status`는 비밀이 아니므로 로그에 더하거나 README를 고친다.
- **L2. 가짜 Storage가 서명 업로드의 upsert를 실제와 다르게 흉내 낸다.** 실제 서버는 발급 요청의 `x-upsert`를 토큰에 묶고(`getSignedUploadURL.ts`: `upsert: request.headers['x-upsert'] === 'true'`), 업로드 때는 토큰의 값만 쓴다(`uploadSignedObject.ts`: `const { owner, upsert } = await …verifyObjectSignature(…)`). 가짜는 업로드 PUT 머리글을 본다. 그래서 변이 4(발급에 x-upsert)가 살아남는다. 반대로 '앱이 PUT에 x-upsert를 붙이면 덮어쓸 수 있다'는 잘못된 그림을 시험이 받아들인다. 가짜를 토큰에 묶고 변이 4를 잡는 시험을 하나 더한다.
- **L3. 변이 2·6이 살아남는다.** ① '지우기 200인데 실제로 안 지워짐'(경로 인코딩 불일치 같은 조용한 실패) 시험을 더하면 `removePrefix` 마지막 확인이 고정된다. ② `DATABASE_CA_FILE`이 인증서가 아닌 파일인 경우와 PEM이지만 깨진 경우를 시험한다. 덧붙여 `DATABASE_CA_FILE`은 `BEGIN CERTIFICATE` 문자열만 보고 `X509Certificate`로 파싱하지 않아 `DATABASE_CA_CERT`와 검사가 다르다. 깨진 파일이어도 연결 때 실패(닫힌 쪽)라 위험은 낮다.
- **L4. 버킷 대조가 `storage.objects` RLS 정책은 보지 않는다.** 앱 사용자는 Supabase Auth 익명 JWT를 가지므로, 누가 대시보드에서 정책을 하나 더하면 서명 없이 staging·public에 직접 쓸 수 있다. 그러면 page-staging의 JSON 허용(정본과 다름 ①)의 전제가 무너진다. B6 첫날 실측 목록(README 8-2)에 '사용자 JWT로 4개 버킷 쓰기·목록이 모두 거부되는지'와 '`storage.objects`에 anon·authenticated 정책 0'을 더하길 권한다.
- **L5. 실측 목록에 copy의 `metadata.mimetype` 반영을 더한다.** `copyMetadata:false` + `metadata.mimetype`으로 공개 파일의 Content-Type이 정해지는지 봐야 한다. 지금 목록 ④는 cacheControl만 본다.

## 요청받은 관점별 판단

1. **드라이버 계약 일치**: 맞다. 목록은 cursor 쪽 나눔에 같은 cursor면 멈추고, 1203개 시험이 있다. 하위 폴더는 list-v2 `with_delimiter:false`이고, 소스상 delimiter `undefined` = S3식 재귀로 추정한다(실측 ③은 남김). 이름이 전체 키든 상대 이름이든 처리한다. 없는 객체 삭제는 200으로 멱등이다. 덮어쓰기는 서버 `put`이 x-upsert true다. Cache-Control은 공개 버킷 `public, max-age=3600`이고 copy 때 서버가 다시 정한다. local과 다른 점 하나: `move`는 원본이 없고 대상이 있으면 성공한다(local은 ENOENT). 다시 부르기에 더 안전한 쪽이라 문제없다. list-v2가 실제로 '마지막 조각'만 이름으로 준다 해도 removePrefix는 5회 뒤 실패, quarantine_move는 not_found로 **실패로 드러난다**(조용히 성공하지 않음). 이것도 확인했다.
2. **삭제 완전성**: 네 버킷 흔적 0, 부분 실패 → 대기열 → cron이 마저 지우는 경로, 쪽 나눔은 시험과 코드 모두 맞다. H1(삭제 뒤 늦은 업로드) 하나가 빈다.
3. **정본과 다르게 한 두 가지**
   - page-staging JSON 허용: **안전(조건부)**. 서명은 경로 하나(og.jpg 등)에 묶이고 snap.json 서명은 발급하지 않는다. 경로는 JWT `url` 클레임이다. 앱이 og 자리에 `application/json`을 올리면 commit `inspect`가 유형 불일치로 422를 낸다. 시험으로도 확인했고, 공개 버킷에는 0이다. 서명 URL로 다른 키를 쓸 수는 없다. 전제는 RLS 정책 0이다(L4). 이 허용이 실제로 넓히는 것은 '비공개 staging에 600KB 이하 JSON을 최대 6시간'뿐이다.
   - 서명 업로드 URL 2시간: commit 경로는 1회(업서트 없음)·commit 재검사·꼬리 2시간 행으로 충분하다. **삭제·버리기·끄기 경로는 부족하다(H1).** 2시간이 실제 설정값과 같은지는 B6 실측(README 8-2 ②)에 남는다.
4. **DB TLS verify-full**: 우회 조합을 찾지 못했다. CA가 있으면 URL의 `sslmode`·`ssl`·`sslrootcert`·`uselibpqcompat` 등을 지우고 명시적으로 `rejectUnauthorized: true`를 건다. 이것이 `NODE_TLS_REJECT_UNAUTHORIZED=0`과 `PGSSLMODE`보다 우선한다. 퍼센트 인코딩된 키도 `URLSearchParams`가 풀어서 지운다. 운영 판별은 `NODE_ENV=production`(Dockerfile·YAML 둘 다)이고 CA가 없으면 부팅을 거부하므로, 로컬·CI 분기가 운영으로 새지 않는다. CA 형식: `DATABASE_CA_CERT`는 X509로 파싱한다. FILE은 L3. 남는 위험은 Supabase 풀러(Supavisor) 인증서의 SAN이 풀러 호스트 이름을 담는지다. 아니면 첫 배포에서 `/readyz`가 실패하는 닫힌 실패가 된다. 그때 검증을 끄지 말라는 문구는 README 8-1에 있다.
5. **CDN 무효화**: 토큰은 메타데이터 서버에서 받고 로그·오류에 남지 않는다. 다만 토큰 권한 = `mong-api-run` 전체(비밀 5개 + Hosting)이고, Hosting 권한은 M1에 적은 대로 사이트 전체 배포다. 정적 배포와의 경합은 M2(되감기)다. 실패하면 대기열로 되돌리고 바닥은 s-maxage 5분이다. 다른 사이트의 버전은 내지 않는다(시험 있음). 요청 경로 지연은 M3.
6. **로그·오류의 URL·키·식별값**: 새는 곳을 찾지 못했다. `StorageError`는 연산·분류·상태만 담는다. `CdnPurgeError`는 단계·상태만 담는다. 버킷 대조 로그는 버킷 이름·항목만 남긴다. 앱 전체 시험이 로그에 서비스 키·`/storage/v1`·`storeKey/pageKey` 모양이 없음을 확인한다. 서명 URL은 응답 본문으로만 나가고, 응답 본문은 요청 로그 화이트리스트 밖이다.
7. **테스트 품질**: 핵심 경로(쪽 나눔·옛 오류 꼴·재시도·4xx·TLS 실제 손잡기·앱 전체 삭제 연쇄)는 실제 동작으로 시험한다. 직접 넣은 변이 6개 중 3개가 살아남았다(L2·L3). 가장 큰 공백은 H1이다. 삭제 '뒤'의 업로드를 시험하지 않는다.

## 처리방침 v3.3과의 대조
- 5·6절 '끄면 즉시 삭제, 웹 캐시 최대 1시간'(K29): 공개 파일 `max-age=3600`이고 `/m`의 s-maxage는 300이라 참이다. 무효화를 켜지 않아도 참이다.
- 6절 계정 삭제 '지체 없이 파기': **H1 때문에 거짓이 될 수 있다**(삭제 뒤 늦은 업로드가 영구히 남음).
- 8절 Supabase 행: '저장은 서울'은 버킷 위치를 실측하지 않았다(B6). 공개 파일 전송망의 거점 국가는 이미 [확인 필요]로 적혀 있다. B6a가 더한 새 국외 이전은 없다. Firebase Hosting REST 호출은 운영자 서버 → Google API로, 개인정보는 싣지 않는다.

### 요청받은 확인

1. **H1 세 경로**: 위 표대로 모두 지워진다. 꼬리 행은 `creature_id`·`deletion_id` 없이 남아 삭제·끄기·새 PUT이 당기거나 지우지 않는다(R8이 고정). 처리 시점에 그 폴더가 아직 커밋 대기 판이면 지우지 않고 행만 버린다. URL은 이미 만료라 더 올라올 것이 없고, 6시간 `uncommitted` 행이나 계정 삭제가 그 폴더를 맡는다(R9가 고정). 엇갈리는 경우(꼬리 처리 때 대기 → 그 뒤 commit·버림·삭제)도 따져 봤다. 모두 commit의 +2시간 행이나 6시간 행, 삭제 연쇄가 덮는다.
2. **'흔적 0' 시험에서 꼬리 행을 빼는 방식과 처리방침**: 맞다고 판단한다. 남는 것은 `storage_gc` 한 행(버킷·`{storeKey}/{pageKey}`·시각)뿐이다. 사람·계정·코드와 잇는 행은 삭제 때 모두 사라져 DB 안에서 되짚을 수 없다. 이 행이 가리키는 파일은 삭제 **뒤에** 늦게 올라온 것뿐이고, 그것도 최대 '2시간 15분 + 5분 주기'에 지워진다. 6절 '계정을 지우면 … 함께 지움'은 삭제 시점에 있던 것을 말하고, 늦게 온 것은 짧은 정해진 시간 안에 지우므로 '지체 없이'의 뜻에 맞는다. 시험의 제외 조건(`reason='upload_tail' and creature_id is null and deletion_id is null`)은 꼬리 행만 빼며 다른 행을 가리지 않는다. 한 가지는 남겨 둔다. `storeKey/pageKey`는 공개 중이던 og:image 주소에도 있었다. 그래서 그 주소를 본 사람에게는 '가명 키'가 2시간 15분 남는 셈이다(DB 밖으로는 안 보임). 처리방침에 적을 정도는 아니고 DECISIONS B6a에 이미 적혀 있다(640행).
3. **충돌 해소(`git diff main...76891a1`)**: B7a 공통 파일(`common/shutdown-budget.ts`·`link-counter`·`metrics`·`health`·`main`·`app.factory`)은 변경 0이다. `prisma.service.ts`는 `connectionString` 한 줄만 `pgConnection` 펼침으로 바뀌었다. `query_timeout`(6초)·`statement_timeout`·`keepAlive`·`idle_in_transaction_session_timeout` 40초·`idleTimeoutMillis`·`DroppingClient`(소켓 폐기)·종료 시 `budget.settle()` + 1.5초 끊기는 그대로다. 펼침이 먼저이고 뒤의 키가 덮을 `ssl` 키는 없다. env.ts의 B7a 교차 검사(query > statement, connect < ready)도 그대로다. CDN 종료 대기는 `budget.run` + `within(…, remaining())`으로 공유 8초 마감 안에 들어갔다. deploy.sh·YAML은 B7a의 판 번호 고정(latest 금지)에 CA 비밀이 같은 형식으로 들어갔다. web-edge e2e는 운영 설정에 시험 CA만 더했고, 판정 단언은 그대로다.
4. **리뷰 변이**: 위 표. 1차 생존 3개 모두 이제 잡힌다.

### 새 발견

- **N1(중간, 잠재 — CDN을 켜기 전에): M2 되감기 복구가 사이트 전체 릴리스 목록을 본다.** `GET sites/{site}/releases?pageSize=2`는 공식 문서상 '**live 채널과 활성 preview 채널의 릴리스를 함께**' 돌려준다. 순서 보장도 문서에 없다(sites.releases.list 참조). 누가 preview 채널(`firebase hosting:channel:deploy`)을 쓰면 '바로 앞 릴리스'가 preview 버전이 된다. 그러면 복구 단계가 **preview 버전을 live로 낸다**. 지금 web-static은 preview 채널을 쓰지 않고 `CDN_DRIVER`는 check가 막아 영향은 0이다. 고칠 방향: `sites/{site}/channels/live/releases?pageSize=2`(채널 단위 목록)로 바꾸고, `releaseTime`으로 순서를 직접 확인한다. 가짜(cdn-firebase 시험)도 채널 경로를 알아야 한다. 경로만 바꾸면 지금 시험 3개가 실패하는 것을 확인했다(변이 표 밖 R12).
- **N2(낮음): `enqueue`의 `inflight = Promise.all([inflight, run])` 사슬이 결과 배열을 중첩으로 쥔다.** 요청마다 아주 작은 배열이 하나씩 쌓여 인스턴스 수명 동안 줄지 않는다. 바이트 단위라 실해는 작다. `inflight = run`(가장 최근 것)이나 Set으로 바꾸면 없어진다.
- **N3(낮음, 정보): 종료 마감에 잘린 뒤쪽 무효화는 요청이 사라질 수 있다.** `flush`가 차례를 잡는 커밋(`requested_at = NULL`)을 한 뒤 SIGKILL되면 되돌리는 UPDATE가 돌지 않는다. 그러면 다음 Scheduler가 낼 것이 없다. 바닥은 s-maxage 5분이라 약속(최대 1시간)은 지켜진다. 주석 '못 끝낸 요청은 DB에 남아 Scheduler가 낸다'는 이 경우에 참이 아니다. 문구만 고치거나 그대로 둔다.
