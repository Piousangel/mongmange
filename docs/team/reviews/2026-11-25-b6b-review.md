## 판정: 조건부 통과

rewrite 자체는 맞다. 서울 리전의 `mong-api`를 가리키고, `/m/**` 뒤·정적 rewrite 앞에 있으며, OTA 경로에 닿는 Cache-Control 헤더가 없다. 런북의 토큰 처리도 안전하다.
다만 다음 넷은 **B6 첫날 전에** 손보길 권한다.
- Hosting의 **60초 제한은 공식 문서로 확정된 사실**인데, 체크리스트는 아직 `[확인 필요]`로 두고 측정 명령이 없다(F1).
- 체크리스트 안에서 순서가 충돌한다(F2).
- B7-report의 지표·로그 알림이 빠졌다(F3).
- 빌드 검사에서 변이 3개가 살아남았고, 거짓 통과 경로가 2개 있다(F4).

## 1. Firebase Hosting → Cloud Run 재작성 제약(공식 문서 확인)

| 항목 | 공식 문서 | OTA에 미치는 영향 |
|---|---|---|
| 요청 제한 | "Firebase Hosting is subject to a **60-second request timeout**." Cloud Run 제한을 더 길게 잡아도 504가 난다(hosting/cloud-run) | **매니페스트**: 문제없음(DB 1회·30초 메모리 캐시). **에셋**: 가장 큰 파일이 번들 5.1MB(br 1.69MB)다. 60초가 백엔드 처리 시간만 세는지, 느린 클라이언트로 내려보내는 시간까지 세는지는 문서에 없다 → 느린 회선(50KB/s)에서 br은 약 34초, 압축 없이 내려가면 약 102초다. Android OkHttp는 기본으로 gzip만 청하므로 **gz 판 크기 기준**으로 재야 한다 |
| 응답 크기 | Hosting 문서에는 동적 응답 크기 제한이 없다(정적 파일 2GB만). Cloud Run 쪽 HTTP/1 비스트리밍 32MiB 제한은 스트리밍이면 풀린다(Cloud Run 블로그) | 서버가 에셋을 스트림으로 보내고 e2e에 '스트림 32MB'가 있어 직접 호출은 괜찮다. **Hosting 경유 상한은 [확인 필요]** — 지금 크기(수 MB)로는 문제가 될 가능성이 낮다 |
| 쿠키 | "Only the specially-named `__session` cookie is permitted to pass through" | OTA는 쿠키를 쓰지 않는다 → 영향 없음(오히려 식별자 통로가 줄어든다) |
| 요청 헤더 전달 | 공식 문서에 전달·제거 목록이 **없다** | `expo-*`·`accept`가 전달되는지는 실측뿐이다 → 체크리스트 T5의 '400이면 떨굼' 판정이 맞는 설계다 |
| 캐시 기본값 | "requests that are handled by backend code do **not** cache on the CDN by default", Cache-Control이 없으면 Hosting이 `private`를 붙인다. GET·HEAD만 캐시한다. 캐시 키 = 호스트·경로·질의 + `Vary`에 든 요청 헤더. 동적 응답에는 `Vary: Cookie, Authorization`을 더한다 | 매니페스트·204(`private, max-age=0`)는 캐시되지 않는다. 에셋(`public, max-age=31536000, immutable` + `vary: accept-encoding`)은 CDN에 캐시된다 → 바라는 동작이고 송신 비용도 준다 |
| **404 캐시** | "The CDN caches your service's **404** response to a nonexistent URL for **10 minutes**", 서비스가 캐시 헤더를 주면 그 값을 따른다 | OTA 컨트롤러의 404는 모두 `no-store`라 괜찮다. 그러나 `/api/v1/ota/<없는 하위 경로>`는 Nest 기본 404라 Cache-Control이 없다(전역 필터는 429만 `no-store`) → 10분 캐시된다. 실해는 작다(낮음, F9) |
| 리전 | `asia-northeast3`(서울)은 rewrite 지원 리전이지만 '같은 위치 권장' 5개 리전에는 없다 | 지연이 조금 붙는다. 이미 `/m/**`도 같은 구성이라 새 위험은 아니다 |

**대안(T5가 400이거나 60초를 넘을 때)과 B7a web-edge와의 관계**

1. **에셋만 우회**: 매니페스트는 `ota.mongmang.ink`(Firebase)에 두고, 매니페스트 안 에셋 `url`만 `*.run.app`(또는 저장소 공개 주소)으로 바꾼다. 에셋 URL은 서명된 매니페스트 안에 있어 앱 바이너리를 바꾸지 않아도 된다(게시 CLI 설정만 바뀜).
   - deploy/README 3절의 '공개 경로 30초' 권고와 부딪친다. 그 절 3항의 '에셋은 별도'를 확정해야 한다.
   - 에셋 레이트 리밋 키가 `ota` 그룹이 아니라 HOPS 1 위치가 된다.
2. **전부 run.app 직접**: app.json `updates.url`을 바꾼다. 이 값은 바이너리에 들어가므로 **빌드 2 네이티브 동결(12-19) 전**에 정해야 한다. 그래서 T5·R4 결과가 12-12 리허설 전에 나와야 한다.
   - `TRUSTED_PROXY_HOPS_OTA`를 1로 바꿔야 한다.
3. 둘 다 **처리방침이 바뀐다**: K27('업데이트 요청은 Firebase Hosting을 지나'), 테스터판 1-1·6절의 'Firebase Hosting — 업데이트 파일' 행. Supabase 공개 주소를 쓰면 수탁자도 새로 늘어난다 → 게시 방침과 Data safety를 먼저 고친다(DECISIONS 'PM 판정 — 빌드 2 Data safety').
4. **web-edge(B7a)**:
   - Firebase 경유를 유지하면, T3 실측 뒤 web-edge를 `ota` 그룹으로 넓힐 수 있다(B7a '앱 API와의 관계'). 그러면 체크리스트 B절 끝에 적힌 '`run.app` 직접 호출로 HOPS 2 위치를 위조해 매니페스트 리밋 피하기'가 닫힌다.
   - run.app 직접으로 가면 web-edge는 걸 수 없다(앱이 직접 부르므로). 그때는 HOPS 1 키 + 전역 리밋만 남는다.

## 2. 빌드 검사 확장 — 거짓 통과·거짓 실패

**탐침**(`check()`에 고친 firebase.json을 넣음)

| 경우 | 결과 | 평가 |
|---|---|---|
| 지금 firebase.json | 통과 | 맞음 |
| 앞에 `/api/v1/ota/manifest` → 정적 rewrite | 실패(가로챔 + `/m/**` 맨 앞 아님) | 맞음 |
| `/api/v1/ota/manifest*` 헤더에 Cache-Control | 실패 | 맞음 |
| OTA rewrite를 맨 뒤로 | 통과 | 맞음(뒤 순서는 무해) |
| **`redirects`에 `/api/v1/ota/:p*`** | **통과** | **거짓 통과** — Hosting은 redirects를 rewrites보다 먼저 적용하는데 검사가 redirects를 보지 않는다 |
| **헤더 `source`에 확장 glob `@(manifest\|assets){,/**}`** | **통과** | **거짓 통과** — `globRe`가 `@( )`·`{ }`를 글자로 본다(Firebase는 extglob을 지원) |
| **헤더·rewrite에 `regex` 키(`source` 대신)** | **TypeError로 빌드 중단**(`undefined.split`) | 닫힌 쪽으로 실패하지만, 맞는 설정에도 '거짓 실패'가 나고 사유가 BuildError로 나오지 않는다. 헤더 regex로 Cache-Control을 거는 것은 검사하지 못한다 |

**변이**(`build.mjs` 한 곳씩 → web-static 시험 → 되돌림, 매번 `cmp` 같음)

| # | 변이 | 결과 |
|---|---|---|
| N1 | 앞선 rewrite 가로채기 검사 끔 | 잡음 |
| N2 | `globRe`의 `*`(한 마디)를 `.*`(여러 마디)로 | **생존** — 넓게 맞는 쪽(거짓 실패)을 보는 음성 시험이 없다(예: `/api/*` 헤더는 OTA에 닿지 않아야 한다) |
| N3 | 정적 `public/api` 검사 끔 | 잡음 |
| N4 | 검사 표본에서 에셋 경로 뺌(`OTA_PATHS` = 매니페스트만) | **생존** — `/api/v1/ota/assets/**`에만 Cache-Control을 거는 시험이 없다. 거기에 `public, max-age=300`이 걸리면 에셋 503·404(`no-store`)가 덮여 **실패 응답이 5분 캐시**될 수 있다 |
| N5 | `region !== 'asia-northeast3'` 검사 끔 | **생존** — 리전을 바꾸는 시험이 없다(serviceId만 바꿈) |

## 3. 복원 런북 4단계 손 호출

- **좋은 점**
  - 역할이 가장 좁다(`roles/iam.serviceAccountOpenIdTokenCreator`, `mong-scheduler` 한 계정에만).
  - 토큰을 `sed … | curl -H @-`로 넘겨 argv·셸 기록에 남지 않는다(curl 7.55+).
  - `--include-email`로 서버의 이메일 대조에 맞췄다.
  - audience는 '경로 없는 서비스 주소'다.
  - deploy/README 5절과 글자가 같다(정본 표시도 있음).
- **보완(낮음)**
  1. **IAM 전파 지연**: 바인딩 직후 ②가 403일 수 있다(보통 수십 초~수 분). 401·403 안내에 '1~2분 뒤 다시'를 넣지 않으면 audience를 잘못 의심하게 된다.
  2. **회수 누락**: 줄 단위로 붙여 넣다가 터미널이 끊기면 ③이 빠진다. 시한부 조건 바인딩(`--condition` + `request.time < …`)이나 `trap`을 쓰는 한 줄 스크립트를 권한다. 서비스 계정 리소스가 IAM Conditions를 받는지는 [확인 필요].
  3. 이미 같은 바인딩이 있던 계정이면 ③이 그것까지 지운다. ① 전에 `get-iam-policy`로 있는지 보는 줄이 있으면 안전하다.
  4. `ME=$(gcloud config get-value account)`가 서비스 계정이면 `user:` 접두가 틀린다(사람이 돌리는 런북이라 낮음).
