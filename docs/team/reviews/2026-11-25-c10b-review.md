## 중요

**H1. 다른 규칙을 거는 플러그인이 app.json에서 우리 것보다 앞에 있으면, 세션 제외 규칙이 조용히 덮이고 prebuild는 성공한다. 표시 `extra.mongSessionBackupExcluded`는 그래도 true다.**
- 직접 실험(사본, Android prebuild):
  - 가짜 플러그인(`fullBackupContent`·`dataExtractionRules`를 다른 xml로 거는 것)을 **앞에** 두면 → `✔ Finished prebuild`. 매니페스트는 `android:fullBackupContent="@xml/other_backup" android:dataExtractionRules="@xml/other_rules"` → **세션이 백업된다**.
  - 같은 플러그인을 **뒤에** 두면 → `[withSessionBackupExclusion] android:fullBackupContent가 이미 @xml/other_backup다`로 멈춘다(의도대로).
- 까닭: Expo mod는 나중에 등록된 플러그인의 것이 먼저 돈다. 그래서 '이미 걸려 있으면 멈춤' 가드는 **뒤에 등록된** 플러그인과 내장 mod만 본다. 앞에 등록된 플러그인의 mod는 우리 mod 뒤에 돌아 값을 덮는다.
- 표시가 문제를 키운다: `extra` 값은 플러그인 본문(설정 평가 시점)에서 쓰므로 mod 결과와 무관하게 true다. C11은 이 값만 믿고 원격 `cloud`를 켠다 → **'백업 제외 바이너리'라고 거짓으로 말하게 된다**. DECISIONS의 "mod를 붙인 뒤 마지막에만 쓴다"는 붙이기만 보장할 뿐, mod가 이긴다는 보장은 아니다.
- 지금 app.json에서는 우리 플러그인이 맨 끝이라 실해는 없다. 다만 `npx expo install`은 플러그인을 끝에 붙이고, 손으로 넣는 사람은 아무 곳에나 넣는다. 동결 바이너리의 보안 전제를 '목록 순서'라는 암묵 규칙에 걸고 있는 셈이다.
- 고칠 방향(셋 중 하나 이상):
  1. 플러그인이 `config.plugins`에서 자기가 **마지막**인지 검사하고 아니면 멈춘다. 시험으로도 고정한다.
  2. 덮어쓰기를 감지할 수 있는 늦은 단계를 쓴다. 예: `withDangerousMod('android')`에서 prebuild가 쓴 `AndroidManifest.xml`을 다시 읽어 두 속성이 우리 값인지 확인(dangerous mod가 manifest 쓰기 뒤에 도는지 먼저 실측할 것), 또는 Gradle `processReleaseManifest` 뒤 검사 작업.
  3. 최소한 시험에 "가짜 규칙 플러그인을 앞에 두면 prebuild 실패"를 추가해, 고친 뒤 회귀를 막는다.

## 보통

**M1. '다른 규칙이 있으면 멈춤'은 앞으로 의존성을 넣을 때 빌드를 막는다(질문 3) — 함정이라기보다 의도된 정지지만, 정지 뒤 갈 길이 없다**
- 지금 설치본에는 `fullBackupContent`·`dataExtractionRules`를 쓰는 라이브러리 매니페스트나 Expo 플러그인이 0개다(`node_modules` 전수 검색). Expo SDK 템플릿 자체도 이 속성을 넣지 않는다(prebuild 결과).
- 대표 위험은 `expo-secure-store`다. 기본값 `configureAndroidBackup: true`로 `@xml/secure_store_*` 규칙을 건다(DECISIONS 버린 안 ⓐ가 바로 이 패키지). 나중에 들어오면, 끝에 붙을 경우 prebuild가 멈추고(올바름), 앞에 놓일 경우 H1이다.
- Expo·RN을 판 올림할 때 템플릿이 규칙을 기본으로 넣기 시작하면 내장 mod 쪽이라 '멈춤'으로 드러난다. 조용히 지나가지는 않는다 — 좋은 성질이다.
- 권고: 멈춤 메시지에 '합치는 법'(우리 exclude 네 줄을 그 xml에 넣고, 이 플러그인의 `props.mergeWith`로 상대 파일 이름을 받아 검사만 하는 방식 등)을 적어 둔다. 그래야 업그레이드 날에 빌드 담당자가 가드를 지워 버리는 일을 막는다. DECISIONS에 '이 플러그인은 앱 백업 규칙의 유일한 주인' 원칙을 한 줄 넣는다.

**M2. 03386b9 이력: C10b 일부가 무관한 커밋(C12c·d)에 섞였다**
- 03386b9에 들어간 것: app.json 등록, 모듈 4파일, 플러그인(표시 쓰기 없음), 시험. 커밋 메시지에는 C10b가 없다.
- 상태 자체는 안전하다. 그 판의 플러그인은 `extra`를 쓰지 않으므로 C11은 '제외 아님'으로 본다(fail-closed). 규칙 XML·iOS 구독자는 이미 동작한다.
- 그러나 `git log --grep C10b`로 찾을 수 없고, 되돌릴 때 C12c·d와 함께 묶인다. 남은 미커밋분을 커밋할 때 메시지 본문에 "C10b 첫 부분은 03386b9에 섞여 들어감(app.json·modules/session-backup·plugin 초판·test)"을 적고, DECISIONS C10b 증거 줄에도 커밋 해시를 남길 것. 히스토리 재작성은 권하지 않는다(이미 main).

## 경미

- **L1. AppGroupIdentifier 가드는 config만 본다.** 다른 플러그인이 `withInfoPlist` mod로 `AppGroupIdentifier`를 넣으면(MMKV를 위젯과 나누려는 라이브러리 등) 세션·세이브가 App Group 폴더로 옮겨 간다. 그러면 iOS 제외 경로와 Android 규칙의 뜻이 갈린다. 지금은 C10 위젯이 `MongAppGroup`을 써서 문제없다. H1의 늦은 단계 검사에 Info.plist 키 검사도 함께 넣을 것.
- **L2. 표시 가드는 멱등이 아니다**(`extra`에 키가 이미 있으면 멈춤). 이미 플러그인이 적용된 config에 플러그인을 다시 적용하는 도구가 있으면 거기서 멈춘다. `expo config`(public·introspect)·prebuild·fingerprint에서는 문제없음을 확인했다. EAS 자격 단계는 리허설 12-12 때 확인 항목에 넣을 것[확인 필요].
- **L3. 세션 파일이 지워졌다 다시 생기면 다음 실행까지 표시가 없다.** MMKV `clearAll`은 제자리 ftruncate라 표시가 남는다. 하지만 C11이 `removeStorage`(파일 삭제)를 쓰면 MMKV가 새로 만든 파일에는 다음 실행 전까지 표시가 없다. C11 계약에 "세션 파일을 지우지 말고 `clearAll`/키 삭제로 비운다"를 한 줄 넣을 것.
- **L4. 첫 잠금 해제 전 백그라운드 기동**(푸시 등)에서는 Documents에 파일을 만들 수 없어 생성이 조용히 실패한다. 다음 실행에서 다시 걸리므로 실해는 없고, 로그도 남는다. 기록만 해 둔다.

## 질문별 답

### 1. iOS 빈 파일 선생성이 MMKV를 깨는가 → **깨지 않는다**(MMKVCore 2.4.0 원본으로 확인)
- MMKV 자신도 첫 생성 때 0바이트 파일을 열고 크기를 키운다. `MemoryFile::reloadFromFile`은 크기가 페이지보다 작으면 `truncate`로 페이지 크기까지 늘리며 `zeroFillFile`로 0을 채운다. 이것은 .crc(메타 파일)에도 똑같다.
- 빈 .crc → 0으로 채움 → `m_metaInfo` 판 0. `loadMetaInfoAndCheck`의 '판 ≥ Holder' 분기에 걸리지 않는다.
- 본 파일의 `readActualSize()` = 0 → `checkDataValid`에서 `checkFileCRCValid(0, 0)`(0바이트 CRC32 = 0 = 메타 0) 통과. 이어 `loadFromFile`의 '비었음' 분기에서 `writeActualSize(0, 0, …, KeepSequence)`로 들어간다. **MMKV가 처음 만들 때와 같은 경로**다. CRC 실패·길이 오류 복구 경로를 타지 않는다.
- 파일 이름: id `mong.session`에는 MMKV 특수문자(`\/:*?"<>|`)가 없어 md5 이름으로 바뀌지 않는다. 따라서 `<root>/mong.session`·`.crc`가 맞다(`encodeFilePath`).
- 파일 보호 등급: `FileManager.createFile` 기본 등급으로 만들어도 MMKV iOS는 `reloadFromFile` 끝에서 `tryResetFileProtection`으로 자기 등급을 다시 건다. 차이가 남지 않는다.
- '하나만 있으면 만들지 않는다'는 맞다. 데이터가 있는 본 파일 옆에 빈 .crc를 만들면 판 0 메타로 읽혀, 옛 형식 경로(`oldStyleActualSize`)로 엉뚱하게 해석될 수 있다. 이 조건은 시험이 고정하고, 변이 V2로 확인했다.
- 대안 제안은 필요 없다. 굳이 한 겹 더 하려면 C11 `sessionStore`가 `createMMKV` 직후 `SessionBackup.status()`를 한 번 부르는 정도(확인 겸 재표시)다. 다만 이것은 JS 경로라 동결과 무관하게 OTA로 넣을 수 있다.

### 2. Android 규칙 경로·domain·병합 → **맞다**
- react-native-mmkv 4.3.2 `HybridMMKVPlatformContext.kt`: `context.filesDir.absolutePath + "/mmkv"`. 따라서 `domain="file"`(= `getFilesDir()` 기준) + `path="mmkv/mong.session"`·`.crc`가 정확하다(시험이 설치본 소스를 읽어 고정).
- `exclude`만 쓰므로 세이브 `mmkv/mong`·`mong.widget`·SharedPreferences 등은 그대로 백업된다. `full-backup-content`(API ≤30)와 `data-extraction-rules`의 `cloud-backup`·`device-transfer` 두 갈래가 모두 같다. 이 갈래 구성은 targetSdk 36에서 API 31+ 규칙이 쓰이는 조건과 맞는다.
- 병합: 라이브러리 매니페스트 중 이 속성을 가진 것은 0개다. 앞으로 생기면 Gradle 매니페스트 병합 충돌(오류)로 드러난다. 리허설 항목 ④(`processReleaseManifest` 결과)가 이것을 덮는다.

### 3. '멈춤' 가드의 업그레이드 함정 → M1(정지는 올바르나 탈출 경로 문서화 필요), H1(앞 순서면 아예 못 봄)

### 4. extra와 fingerprint·OTA 채널
- 실측 런타임: env 없음·preview·production 모두 android `3a57b51d…`, ios `a687d8f9…`로 **채널 간 같다**(DECISIONS 기록과 일치). 값이 env에 따라 달라지지 않는 상수라 V21 H1 함정이 없다.
- `extra`는 `expoConfig` 해시에 들어간다. 그래서 이 플러그인이 없는 바이너리(빌드 1)와 런타임이 달라, 표시가 true인 OTA가 빌드 1에 내려가지 않는다(C11이 의도한 성질).
- 덧붙여 OTA에서 `Constants.expoConfig`는 **업데이트 매니페스트의 config**다. 그래서 이 값은 엄밀히 '바이너리 표시'가 아니라 '이 판을 만든 소스에 플러그인이 있었다'는 뜻이다. 같은 런타임 = 같은 플러그인 파일이므로 지금은 같은 뜻이 된다. 단 H1처럼 mod가 덮인 경우는 둘 다 거짓이 된다.

## prebuild 산출물(직접)

- `AndroidManifest.xml` `<application … android:allowBackup="true" … android:fullBackupContent="@xml/mong_backup_rules" android:dataExtractionRules="@xml/mong_data_extraction_rules">`.
- `res/xml/mong_backup_rules.xml`에 exclude 2줄, `mong_data_extraction_rules.xml`에 두 갈래 × exclude 2줄. include는 0개다.
- iOS 자동 링크: `session-backup` → 포드 `SessionBackup`, 모듈 `SessionBackupModule`, `appDelegateSubscribers: ["SessionBackupAppDelegateSubscriber"]`.
- 생성된 `AppDelegate`는 `ExpoAppDelegate`를 상속하고 `super.application(…didFinishLaunchingWithOptions…)`를 부른다 → 구독자가 불린다. Info.plist `UIApplicationSceneManifest`·`SceneDelegate: ExpoAppSceneDelegate` → RN은 그 뒤에 시작하므로 JS보다 앞선다는 주장이 맞다.
- Swift는 컴파일하지 못했다(이 기기에 iOS SDK 없음, 작성자와 같음). 12-12가 첫 컴파일이다.
