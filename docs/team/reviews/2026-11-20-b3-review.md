## 중요

### I1. commit 이동이 일부만 되거나 계정 삭제와 겹치면 공개 버킷에 고아 파일이 남는다. 계정을 지워도 남는다(재현함)
- 위치: `apps/server/src/pages/page.service.ts:213`(트랜잭션 밖 staging→public 이동), `:217`(`lockPage`가 몽망이 없으면 NotFound를 던져서 '방금 옮긴 파일 지우기' 갈래 `:220-222`에 닿지 못함), `apps/server/src/deletion/deletion.service.ts:63-64`(pending_prefix는 staging 버킷만 모음).
- 재현 R1: snap.json 이동만 실패하게 했다 → commit **500**(주석은 503이라고 적음). `public-pages/{pending}/og.jpg·poster.jpg`가 남았고, 대기열 행은 `page-staging` 하나뿐이었다. 이어서 `DELETE /me`(202)를 불러도 **두 파일이 그대로 남았다**.
- 재현 R2: 마지막 이동 직후 같은 사용자가 `DELETE /me`를 불렀다 → commit 404. `public-pages/{pending}/`의 og·poster·**snap.json(이름 공개 판이면 이름 포함)**이 대기열 0행으로 남았고, 공개 주소로 **읽힌다**.
- 영향: pageKey는 HTML에 한 번도 실리지 않았으니 바로 노출되지는 않는다. 그러나 처리방침 6절 '계정을 지우면 공개 페이지를 함께 지움'과 3-8 '흔적 0'을 어긴다. 이동 실패는 B6 실제 Storage에서 흔히 생기고, 재시도해도 회수할 길이 없다. 같은 판을 동시에 commit 두 번 하면 이동이 서로 엇갈려 둘 다 실패할 수 있고, 그때도 같은 고아가 생긴다.
- 권고: ① PUT 트랜잭션에서 `uncommitted` 행을 **staging과 public 두 버킷 모두**에 만들고(public 쪽도 6시간), commit 트랜잭션이 성공했을 때만 둘 다 지운다. ② 계정 삭제 ①은 `pending_prefix`도 public 버킷에 넣는다. ③ commit의 `lockPage` NotFound 갈래에서도 정리한다. ①만 해도 R1·R2가 모두 막힌다. 시험: R1·R2를 그대로 b3.db에 넣는다(이동 실패 주입, 이동 중 삭제).

### I2. 이름 가리기 즉시 삭제가 '바로 앞 판'만 지운다. 그보다 옛 판이 2시간 유예 중이면 이름이 남는다(재현함)
- 위치: `page.service.ts:228-233`. `hideName`일 때 지금 `path_prefix`의 gc 행만 `drainNow`에 넣는다. 그보다 먼저 들어간 `old_version` 행(2시간 유예)은 그대로 둔다.
- 재현 R4: 이름 공개 판 1 → 이름 공개 판 2(판 1은 2시간 유예로 들어감) → 이름 없는 판 3. 판 2는 지워졌지만 **판 1의 snap.json이 공개 주소로 읽히고, 이름도 들어 있다**.
- 영향: 3-5-2 '가리면 어디에도 0'과 DECISIONS B3 '즉시 삭제'를 어긴다. 판 1의 주소는 5분 넘게 캐시된 HTML·방문자 기록·미리보기 크롤러에 이미 퍼져 있을 수 있다.
- 권고: hideName이면 그 몽망이의 `public-pages` `old_version` 행을 **모두** `notBefore = now`로 당겨 함께 비운다. 시험은 R4.

### I3. firebase.json `/m/*` Cache-Control이 서버가 정한 캐시를 덮을 수 있다(B6 실측 필요)
- 위치: `apps/web-static/firebase.json:80`(`/m/*` → `public, max-age=60, s-maxage=300`), 서버 `m.controller.ts:66-83`.
- 서버는 일부러 응답마다 캐시를 다르게 준다. DB 실패 503은 `no-store`(A-3 #44 '거짓 사라짐을 퍼뜨리지 않게'), 429도 `no-store`, 사라진 링크는 `s-maxage=60`이다. 그런데 Hosting의 `headers`는 rewrite 응답에도 붙고, 같은 헤더면 백엔드 값을 덮는 것으로 알려져 있다 **[확인 필요 — B6 curl 실측]**. 정말 덮는다면 503·429가 `public s-maxage=300`이 된다. 그리고 CDN이 그 상태 코드를 캐시한다면 이렇게 된다. (a) **한 IP가 특정 코드로 리밋을 넘기면 그 링크가 모두에게 5분 동안 429** — 표적 DoS. (b) DB 순단이 5분짜리 503이 된다. (c) 사라진 링크도 60초가 아니라 5분이 된다.
- 권고: 캐시의 정본을 서버 하나로 둔다. firebase.json `/m/*`에서 Cache-Control을 빼고 noindex·DENY만 남긴다. 빌드 검사는 'firebase.json `/m/*`에 Cache-Control이 **없다**'로 바꾼다. B6 체크에는 503·429 응답의 `cache-control`과 두 번째 요청의 `x-cache`를 넣는다.

## 보통

- **M1. /m 리밋이 시험 0이고, `/get`에는 리밋이 없다.** 무력화 M9(`m_gone`)·M12(`m_seen`)이 살아남았다. 3-8 표의 `/m` 리밋을 아무 시험도 지키지 않는다. `GET /m/{code}/get`(`m.controller.ts:101`)은 전역 throttler(120/분)만 받고, 부를 때마다 DB 조회와 upsert를 한다. 그래서 `store_*` 퍼널 값 부풀리기와 쓰기 증폭이 된다. 페이지 리밋은 DB 조회 **뒤**에 검사한다(`:66-71`). 넘친 요청도 DB를 한 번씩 친다. 권고: 리밋을 조회 앞으로 옮긴다(gone 여부는 뒤에 따로 센다). `/get`에도 IP당 리밋을 둔다. b3.db에 429 시험 셋(page·gone·seen)을 넣는다.
- **M2. title 변이(M4)가 살아남은 이유: 지금은 무해하지만 B5에서 바로 누출로 바뀐다.** `meta.name`은 PUT이 `name !== null`일 때만 넣고, `name_shown`과 같은 판정에서 나온다. commit이 둘을 한 문장으로 함께 옮기므로 오늘은 'name_shown=false인데 meta.name이 있는' 행이 생기지 않는다. 그래서 조건을 빼도 시험이 차이를 보지 못한다. 그런데 B5 운영자 이름 가리기(`name_blocked`, 3-5-2)를 `name_shown`만 내리는 방식으로 짜면 title·og:title에서 **이름이 그대로 나간다**. 권고: DB에서 `name_shown=false` + `meta.name` 있음을 직접 만들고, title·og:title·h1이 앱 이름인지 보는 시험을 지금 넣는다. 그러면 '이름의 문은 name_shown 하나'가 고정된다. 운영자 가리기는 meta.name과 공개 파일까지 지우는 쪽이 맞다(I2와 같은 처리).
- **M3. 공개 파일 캐시가 1년 immutable이고, 처리방침 '웹 캐시 최대 1시간'과 어긋날 수 있다.** 로컬 흉내(`local-storage.controller.ts:40`)는 `public, max-age=31536000, immutable`이다. B6 Supabase 공개 버킷에도 같은 값을 주면, 링크 끄기·이름 가리기·계정 삭제 뒤에도 본 적 있는 브라우저와 Supabase CDN(삭제 때 퍼지하는 Smart CDN이 아니면)에 poster·og·snap.json이 남는다. 주소가 128비트 비밀이라 새로 보는 사람은 없지만 방침 문구와는 다르다. 권고: B6에서 공개 객체를 `max-age=3600` 이하로 두거나 삭제 퍼지를 확인하고, 그 결과를 B6 체크에 넣는다.
- **M4. B6 서명 업로드 계약 확인.** 계약은 '5분·1회'다(`UPLOAD_URL_TTL_SEC`, page.controller 설명). Supabase `createSignedUploadUrl`은 유효 시간을 정할 수 없고 2시간으로 고정된 것으로 알고 있다. 1회만 쓰이는지도 **[확인 필요]**. 1회가 보장되지 않으면 commit이 끝난 뒤(staging 키는 비고 `uncommitted` 행도 지워진 상태) 같은 토큰으로 다시 올릴 수 있다. 그러면 **대기열 없는 staging 고아**가 생기고 계정 삭제도 그 파일을 모른다. 권고: B6 체크에 '토큰 재사용·만료 실측'을 넣는다. 재사용이 되면 staging 정리를 prefix 수명(예: 판이 끝난 뒤 한 번 더 removePrefix)으로 바꾼다. `STAGING_LIMITS`가 서명 업로드에도 걸리는지 보는 일(이미 적혀 있음)과 함께 한다.
- **M5. 격리 이동이 일부만 되면 공개 버킷에 남은 파일을 다시 시도하지 않는다**(`page.service.ts:299`). 상태는 먼저 quarantined로 바뀌고, 이동이 중간에 실패하면 남은 공개 파일을 아무도 옮기거나 지우지 않는다(계정 삭제 때만 지워진다). 격리의 목적이 노출을 멈추는 것인데 그 목적이 어긋난다. B5에서 경로를 붙일 때 대기열 행을 만들거나 재시도하게 하고, 시험을 넣는다.

## 사소

- **L1.** 사라진 링크 CSP 제거(M8)가 살아남았다. 값이 없는 페이지라 위험은 작다. b3.db '커밋 전 /m은 사라진 링크'에 CSP 단언 한 줄을 넣으면 된다.
- **L2.** `app.rollup_link_daily`에 `REVOKE ALL ON FUNCTION … FROM PUBLIC`이 없다(`migration.sql:61`). B0 `rollup_metric_daily`는 PUBLIC에서 회수했다. anon·authenticated 회수만으로는 PUBLIC 기본 EXECUTE가 남는다(schema USAGE가 없으니 지금은 닿지 못함). 같은 패턴으로 맞춘다.
- **L3.** commit 이동이 실패하면 500이 난다(주석 `:212`은 503). `cdn.request()`가 DB 오류로 던지면 live가 이미 커밋된 뒤에 500이 난다(`:252`). 앱이 재시도하면 409가 된다. 이동 실패는 503 `storage_unavailable`로 감싸고, 무효화 요청은 try로 감싼다(삭제 쪽처럼).
- **L4.** `void wasLive;`(`:251`)는 죽은 코드다. 값을 쓰지 않으면 지운다.
- **L5.** 운영 `STORAGE_DRIVER=none`에서 live 행이 하나라도 있으면(B6 롤백·복원) `NoStore.publicUrl`이 던져 `/m`이 500이 된다(`m.controller.ts:113`). '사라진 링크'나 503으로 내린다.
- **L6.** webLive가 꺼져 있을 때 live.js·manifest·CanvasKit·wasm은 0바이트가 맞다(스크립트 문자열·캡처로 확인). 다만 `/config/v1.json` 요청은 WebGL2 등 조건만 맞으면 늘 한 번 나간다(작고 5분 캐시, 코드 없음). 문서의 '0바이트'에 'config 한 번 제외'를 적는다. `'wasm-unsafe-eval'`이 없는 Safari 15 이하에서는 wasm이 막히지만 포스터가 그대로 남아 무해하다. webLive가 켜지면 셀룰러에서도 wasm 7.16MB(gzip 2.9MB)를 받는다. saveData 신호는 Chrome Android에만 있으니 켤 때 PM이 판단한다.
- **L7.** 루프 해상도가 `contract/src/index.ts:488`·`media-check.ts:5`에서 아직 540×675다. PM 개정(540×676)에 맞춰 바꿔야 한다(지적만). 지금은 실제 인코더 산출물이 모두 `dimensions`로 거부된다.
- **L8.** 비콘 `live()` 확인과 계정 삭제의 `link_daily` 삭제가 겹치면, 지운 코드의 행이 하루치 생길 수 있다(30일 뒤 말림으로 사라짐). upsert에 `EXISTS(creatures)` 조건을 붙이면 닫힌다.
- **L9.** 커밋하지 않은 `pending_meta`(이름 포함)는 6시간 GC가 파일만 지우고 DB 칸은 다음 PUT·commit·끄기까지 남는다. 본인 데이터라 노출은 없지만 '공개하지 않을 값을 무기한 보관'이 된다. GC가 uncommitted 행을 처리할 때 pending 칸도 비운다.
- **L10.** `PATCH nameVisible=false`만으로는 공개 판이 그대로다(정본 '다음 판부터'). 앱(C11)이 PUT과 commit에 실패하면 이름이 계속 공개된다. C11에 '가리기 = PATCH + 다시 만들기 성공까지 재시도, 실패하면 링크 끄기 제안'을 넣는다.

## 확인했고 문제없던 것(근거)

- **XSS·주입**: 값 9개 모두 `text`·`attr`·`url`·`storeHop`을 거치고, 맨 문자열이면 던진다. 속성은 늘 큰따옴표 안에 들어간다. og:image·poster·loop·snap은 `url()`이 `publicOrigin` 출처·http(s)·자격 증명 없음·따옴표와 공백 없음을 검사한다(경로는 서버 난수 pageKey + 고정 파일 이름이라 조작할 수 없음). 인라인 스크립트는 상수 하나뿐이고 CSP 해시가 내용과 같다. `<title>`·`<style>`·`<script>` 안에 사용자 값이 없다(title은 text 이스케이프, RCDATA 안전).
- **이름 문자**: `normalizeName`은 한글 완성형·라틴·숫자·공백·가운뎃점만 허용하고, '정규화 값 == 받은 값'을 요구한다. 그래서 RLO·LRI 같은 방향 제어 문자, 제로폭, 결합 문자, 이모지, NFD 입력, NBSP·U+2028이 모두 거부된다. 숫자 규칙은 전각과 구분자 우회까지 막는다(시험 7건). 한글 숫자 읽기('공일공…')는 통과하는데, 금칙어 목록이 비어 있는 것과 같은 문제라 PM 몫이다.
- **live.js**: snap.json 문자열이 DOM에 들어가는 경로가 없다. 색은 core 상수표에서 enum으로 고르고, 점은 base64 → 숫자로 바꾼다. `data-ck`는 정규식, manifest의 `live` 경로도 정규식으로 검사한다. 빌드 검사가 innerHTML·write·비콘·저장소·쿠키를 막는다.
- **스냅숏 파서**: 모르는 키(`__proto__` 포함), 정수·범위, 점 바이트 길이를 엄격하게 본다. 32KB 상한은 정규화 전과 후 두 번 검사한다. 앱이 보낸 `name`은 늘 버린다.
- **MP4·JPEG 파서**: 상자 크기 8 미만·0·1이면 거부하고, 매번 8바이트 이상 전진하며, 64KB 창에 묶여 있다. 그래서 무한 루프·깊은 재귀·큰 할당이 없다. 범위 밖 읽기는 NaN·`\0`으로 떨어져 실패로 끝난다. 64KB 밖의 mdat 내용과 mdhd·edts 길이는 보지 않는다(10절 #23 감수 범위).
- **존재 오라클**: `seen`은 늘 204, `get`은 늘 같은 302(Location에 코드 없음)라 차이가 없다. 페이지 자체(live와 gone)는 본질상 다르고, gone 30/분·페이지 60/분 리밋을 건다(인스턴스 메모리라는 한계는 B2와 같다). 코드는 40비트다.
- **로그·Referer**: route는 템플릿이고, req.url·query·headers를 가린다(M2로 확인). 서버 로그에 코드·이름·pageKey가 없다. `<meta name="referrer" content="no-referrer">` + 헤더 + `rel=noreferrer` + fetch `referrerPolicy`로 다른 출처에 코드가 새지 않는다.
- **삭제 연쇄**: 공개·격리·staging·지난 판·link_daily가 흔적 0이고, Storage 실패 → 재시도 → done까지 시험이 덮는다. `cdn_purge`는 한 행이고 코드·경로가 없다. `STORAGE_DRIVER=none`이면 PUT·commit은 503, 끄기는 상태만 바꾸고, 대기열은 다음 시도로 넘어간다(운영에는 페이지 행이 생기지 않는다).
- **CSP**: `default-src 'none'`, `script-src 해시 {site}/w/ 'wasm-unsafe-eval'`(unsafe-eval 없음), `connect-src`는 config·/w/·공개 출처뿐, `frame-ancestors 'none'`, `base-uri`·`form-action 'none'`.
- **firebase.json**: `/m/**` rewrite가 맨 앞에 있다. 헤더는 `/m/*`만 걸려서 `/seen`·`/get`의 no-store를 덮지 않는다. 덮을 수 있는 상태 코드 문제는 I3에 적었다.
