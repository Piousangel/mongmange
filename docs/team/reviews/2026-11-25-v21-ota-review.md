## 1. 높음

### H1. fingerprint가 채널 env·인증서 유무에 따라 달라진다 — 문서 절차대로 게시하면 OTA가 영영 안 맞는다
- 위치: `apps/mobile/plugins/withSelfHostedUpdates.js:43-47`(env로 `updates.requestHeaders` 추가, 인증서 없으면 `codeSigningCertificate`·`codeSigningMetadata` 삭제), `docs/design/server-v1/ota-self-host.md:54-56`(실측값 `89d46208…`), `:88`(절차), `:56`('같은 export 폴더를 production으로 게시').
- 근거: `@expo/fingerprint`는 정규화된 expo config 전체를 해시하고 `updates`에서는 `url`만(그것도 `ExpoConfigEASProject` 건너뛰기 때 한정) 지운다(`node_modules/@expo/fingerprint/build/sourcer/Expo.js:244-247`). 실측: 채널 env만 바꿔도 값이 셋 다 다르다(위 표). 인증서 파일 유무도 config를 바꾸므로 값이 또 달라진다.
- 결과: 문서 7절대로 로컬에서 env 없이 `runtimeversion:resolve` → 그 값으로 게시하면, EAS preview·production 빌드(env 있음·인증서 있음)는 다른 값을 보내 **늘 204**. 실패가 조용하다(앱은 '새 판 없음'으로 본다). 또 preview와 production 바이너리의 런타임이 달라 '같은 export를 production으로'가 같은 `--runtime-version`으로는 성립하지 않는다.
- 고칠 방향(택1): ⓐ 채널을 fingerprint 밖으로 — `fingerprint.config.js`의 `sourceSkips`/`ignorePaths`로는 `updates.requestHeaders`를 못 빼므로, 채널 헤더를 config가 아니라 네이티브 쪽(빌드 시 `Expo.plist`/`AndroidManifest` 메타데이터를 config plugin mod로 직접 씀)으로 넣거나, 런타임 `Updates.setUpdateRequestHeadersOverride`류(SDK 58에 있는지 [확인 필요])를 검토 ⓑ 값을 받아들이고 절차를 바꾼다: 게시 때 `MONG_OTA_CHANNEL=<채널>` + 인증서가 있는 상태로 resolve, CLI가 `--channel`과 resolve 결과를 스스로 묶게(사람이 값을 손으로 넘기지 않게). 어느 쪽이든 **빌드 2 리허설에서 EAS 빌드 로그 값 = CLI 값**을 기계적으로 대조하는 검사를 체크리스트 8절에 넣는다.
- 시험 제안: `ota-config.test.ts`에 '채널 env가 runtimeVersion을 바꾸는가'를 고정하는 시험(ⓐ면 같아야, ⓑ면 CLI가 채널별로 resolve하는지).

### H2. PM 11-25 ① 'Firebase Hosting 리라이트'가 V21의 개인정보 전제·IP 판단을 깨뜨린다
- 위치: `DECISIONS.md:470`(PM 11-25 ①) ↔ `ota-self-host.md:23`(Firebase 버린 까닭: '설치 id 실린 요청이 국외 CDN 엣지를 지난다'), `:70`(에셋도 외부 CDN 거치지 않게), `architecture.md` v2.1 정정(앱 API를 Firebase에서 Cloud Run 직접으로 옮긴 까닭), `apps/server/src/common/client-ip.ts:15-18`(`routeGroupOf` — `/m/*`만 web 그룹).
- 문제 ① 개인정보: Firebase Hosting은 전 세계 엣지에서 TLS를 푼다. 매니페스트·에셋 요청마다 `EAS-Client-ID`·`Expo-Fatal-Error`·`Expo-Recent-Failed-Update-IDs`가 실려(FileDownloader.kt `createRequestForRemoteUpdate`·`createRequestForAsset` 모두 `EAS-Client-ID`) 14세 미만 포함 모든 설치자에게서 국외 엣지를 지난다. 저장은 안 하더라도 C-1이 지적한 '국외 이전' 그림이 Google 엣지로 일부 되살아나고, 처리방침의 국외 이전 표(architecture 부록)와도 맞춰야 한다. **이 결정은 설계 문서 1·5·9절과 정면으로 어긋나는데 문서에 반영·재평가가 없다.**
- 문제 ② 레이트 리밋 키: `/api/v1/ota/*`는 api 그룹(`TRUSTED_PROXY_HOPS_API`, Cloud Run 직접 가정)으로 IP를 고른다. Firebase를 거치면 프록시 한 겹이 늘어 ⓐ hops를 그대로 두면 키가 Google 엣지 IP가 되어 많은 사용자가 매니페스트 분당 60·에셋 분당 600을 나눠 쓰고(대량 429), ⓑ 잘못 올리면 XFF 위조로 리밋을 우회한다.
- 고칠 방향: 오너·PM에 재결정 요청(문서 13절 ①의 대안 — 부하 분산기 또는 Cloud Run 도메인 매핑 서울 지원 확인). 그래도 Firebase로 간다면 9절 표·처리방침 국외 이전 행을 갱신하고, `routeGroupOf`에 `/api/v1/ota`를 web 그룹(또는 새 'ota' 그룹, hops 별도)으로 넣고 시험을 붙인다. B6 실측 항목에 'Firebase가 사용자 정의 요청 헤더를 로그에 남기지 않는가'를 더한다.

## 2. 중간

### M1. `console.log` 한 줄이면 설치 id가 운영 로그로 나가는데 아무 검사도 못 잡는다(변이 생존)
- 위치: `apps/server/src/ota/ota.controller.ts:4-6`(주석 '로그·DB·오류 문구에 싣지 않는다 — test/ota-logs.test.ts…'), `eslint.config.mjs`(`no-console` 없음).
- 증거: 변이 M3b(`console.log('ota', headers['eas-client-id'], headers['expo-fatal-error'])`) → 서버 OTA 시험 27/27 통과, lint 규칙 없음. Cloud Run은 stdout을 그대로 Cloud Logging에 넣는다. 같은 변이를 Nest `Logger`로 넣으면(M3a) e2e가 잡는다 — 검사는 pino 경로만 본다.
- 또 주석의 `test/ota-logs.test.ts`는 없는 파일이다(privacy-v3 리뷰가 이미 지적, 아직 그대로).
- 고칠 방향: `apps/server/src/**`에 `no-console: error`(CLI `ota-cli.ts`는 이미 `process.stderr.write`만 씀) + e2e에서 `process.stdout.write`/`console.*`도 가로채 SECRET 0을 단언. 주석 파일 이름 정정.

### M2. 가드 플러그인이 'EAS 빌드'만 출시로 본다 — 로컬 출시 빌드는 서명 없이 OTA를 받는 바이너리가 된다
- 위치: `withSelfHostedUpdates.js:33`(`release = EAS_BUILD === 'true' && profile !== 'development'`), `:44-47`(인증서 없으면 서명 설정 삭제하고 진행).
- 문제: `expo prebuild` 뒤 Xcode Archive·`./gradlew bundleRelease`·`expo run:* --variant release`는 `EAS_BUILD`가 없어 `ready:false`·채널·인증서 검사를 모두 건너뛰고, 인증서가 없으면 `codeSigningCertificate`를 지운 채 운영 URL을 박는다. 그런 바이너리는 **서명 없는 매니페스트를 받아 실행한다**(운영 서버가 서명 없는 판을 안 내보내는 것은 서버가 정상일 때뿐 — 서버·DB·TLS가 뚫리면 임의 JS 실행).
- 고칠 방향(fail-closed): 인증서가 없으면 서명 설정만 빼지 말고 `updates.enabled = false`로 OTA 자체를 끈다(개발 클라이언트는 어차피 OTA를 받지 않는다). 그러면 로컬 출시 빌드가 새어 나가도 '업데이트 못 받음'으로 끝난다. 시험: '인증서 없음 → enabled false'.

### M3. 서명된 매니페스트는 만료·채널 결속이 없다 — 재생·채널 넘나들기
- 위치: `protocol.ts:128-141`(서명 = 본문만), `publish.ts:132-161`(본문에 채널 없음), `ota-self-host.md` 6절(언급 없음).
- 문제: ⓐ 되돌린(rollback) 나쁜 판의 서명은 영구히 유효하다. 롤백 지시 뒤 기기는 내장 번들(commitTime = 빌드 시각)로 돌아가고, 그 뒤 DB 쓰기 권한(M4)·서버·TLS 중 하나를 쥔 쪽이 옛 나쁜 판 행을 다시 내밀면 `commitTime`이 내장보다 늦으므로 클라이언트가 받는다(expo-updates SelectionPolicy는 '실행 중인 판보다 늦은가'만 본다). ⓑ preview(내부 시험용) 판과 production 판이 같은 키로 서명되므로, 같은 런타임이면 preview 번들을 production 기기에 보낼 수 있다(채널은 요청 헤더일 뿐 서명 밖). H1의 ⓐ안을 고르면 두 채널의 런타임이 같아져 이 경로가 실제로 열린다.
- 고칠 방향: 채널별 키·인증서(production 바이너리에는 production 인증서만, keyid `prod`/`preview`) — 'preview에서 확인한 같은 export를 production으로'는 production 키로 다시 서명하면 된다(에셋 재업로드 0). ⓐ는 클라이언트로 막을 수 없으니 문서 6절에 '알려진 남은 위험'으로 적고, 되돌리기는 rollback보다 '고친 새 판 republish'를 1순위로(새 판이 실행 중이면 옛 판은 commitTime에서 진다).

### M4. 게시 경로의 권한이 너무 크다 — 노트북에 '마이그레이션 롤'(모든 표 소유자)
- 위치: `ota-cli.ts:9,60-65`(`OTA_DATABASE_URL ?? DIRECT_URL`), 마이그레이션 머리 주석 3줄('쓰는 쪽은 퍼블리시 CLI(마이그레이션 롤), 서버는 읽기만'), `test/db.db.test.ts`(서버 롤 = 모든 표 소유자).
- 문제: OTA 하나 게시하려고 계정·세이브·신고를 모두 쓸 수 있는 자격 증명을 오너 기기에 둔다. 또 '서버는 읽기만'은 코드 규칙일 뿐 DB가 강제하지 않는다(서버 롤이 `ota_releases` 소유자라 INSERT 가능) — M3 ⓐ의 재생은 서버 쪽 SQL 주입 하나로도 가능해진다.
- 고칠 방향: 마이그레이션에 `ota_publisher` 롤(`ota_releases` SELECT·INSERT만, 로그인 가능, 비밀번호는 오너 보관)과 문서 7절 절차 변경. 서버 쪽 쓰기 차단은 롤 분리가 B6 범위라면 그때로 미루되 문서에 '강제 아님'을 적는다.

### M5. 에셋을 스트리밍하지 않는다 — 출시 순간 메모리 급증
- 위치: `ota.service.ts:93-115`(파일 전체 `read` → 원본은 매 요청 SHA-256), `local-store.ts` `read`(readFile 전체), `ota.controller.ts:84`.
- 문제: 번들 5.1MB(br 1.69MB)를 요청마다 통째로 메모리에 올리고 원본 경로는 매번 해시한다. Cloud Run 동시 요청 80 × 5MB ≈ 400MB(+ 압축 판 첫 검증 때 해제 버퍼). 게시 직후 '하루 한 번 확인'이 몰리면 OOM·지연 위험. B6에서 실제 드라이버를 붙일 때 같은 꼴이 굳는다.
- 고칠 방향(B6과 같이): 서명된 매니페스트가 해시를 담고 앱이 해시를 MUST로 검사하므로, 서버의 '매 요청 해시'는 게시 때 검사 + 저장소 불변성으로 대체 가능. `ObjectStore`에 스트림 읽기를 두고 `reply.send(stream)`. 최소한 해시 검증 결과를 원본에도 `verified`로 캐시.

## 4. 확인한 것(문제 없음)

- **명세 대조**: 공통 헤더 `expo-protocol-version: 1`·`expo-sfv-version: 0`·`cache-control: private, max-age=0`(명세 권장값) — 200·204·400·406 모두(`ota.controller.ts:22-25`). 파트 없는 응답 = 204·content-type 없음(명세 MAY). JSON만 받는 클라이언트에 지시 = 406(명세 SHOULD). 프로토콜 ≠ 1 → 406, 플랫폼 밖 → 400(명세 SHOULD 400/404). `expo-signature` = SFV `sig`(MUST)·`keyid`(MAY). launchAsset `fileExtension` 생략(명세 SHOULD). hash = SHA-256 base64url. 'createdAt 순 가장 늦은 판'(MUST) — 롤백 행도 같은 줄에서 겨룬다.
- **보내지 않는 헤더**: `expo-server-defined-headers`·`expo-manifest-filters` — e2e가 단언(변이 M4로 확인).
- **개인정보**: 앱이 보내는 헤더(FileDownloader.kt 대조: `EAS-Client-ID`·`Expo-Fatal-Error`(최대 1,024자)·`Expo-Recent-Failed-Update-IDs`·`Expo-Current/Embedded-Update-ID`·`Expo-Extra-Params`·채널) 중 `parseManifestRequest`가 꺼내는 것은 고르기 값뿐, 서비스는 요청 객체를 받지 않는다. 표에 설치 칸 없음(열 목록 고정 시험), app 스키마 전 표 행 덤프에 SECRET 0, pino 로그 화이트리스트. 오류 응답은 `{error:{code}}`만. 레이트 리밋 키는 IP 접두(메모리, 1분 창). 30초 고르기 캐시 키는 (채널·런타임·플랫폼)뿐.
- **서명 체계**: 서명 함수는 CLI 경로에서만 호출(`signBody` 사용처 = `publish.ts`), 서버 env에 키 칸 없음, 운영에서 `OTA_ALLOW_UNSIGNED` 부팅 거부(env 시험), 앱이 `expo-expect-signature`를 보내면 서명 없는 판은 허용 설정이어도 204. CLI 되검증으로 키·인증서 짝 확인. `.gitignore`가 `private-key.pem`(codesigning:generate 기본 이름)·`*-private-key.pem` 포함.
- **무결성 두 겹**: 게시(올린 뒤 재읽기 + 행 쓰기 직전 `insertUpdate` 재검사, 매니페스트 해시 목록 = `asset_hashes`) / 내보내기(원본 매 요청 해시, 압축 판 해제 후 해시, 틀리면 원본 또는 503 no-store). 경로 탈출: 키 정규식 43자 + 버킷별 `validObjectKey`, metadata `../` 거부.
- **DB**: 마이그레이션 ↔ schema 차이 0, RLS 켬 + anon·authenticated REVOKE, 채널·플랫폼 CHECK, 롤백 ↔ 에셋 0개 CHECK, 조회 인덱스(created_at DESC).
- **앱**: `checkAutomatically: NEVER` + `ready:false`가 EAS 출시 빌드를 멈춤(시험·변이 M7), URL은 https `*.mongmang.ink`만(유사 도메인 시험 포함), `u.expo.dev` 흔적 0. 개발 클라이언트(`expo-dev-client` 설치됨)는 expo-updates를 끄고 Metro를 쓰므로 개발 흐름 영향 없음 — 단 M2. app.json URL 자리표시자는 '도메인 연결 전'이 문서·체크리스트 8절 1에 명시되어 있고 ready 가드가 막는다.
