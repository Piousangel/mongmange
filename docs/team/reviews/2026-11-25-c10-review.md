## 중요

**H1. 필기 인식 스위치가 '꺼짐인데 ML Kit이 들어가는 바이너리'를 막지 못한다 — 주석·DECISIONS 계약 ③과 다름**
- `plugins/withInkRecognizer.js` `withInkRecognizer()` — `contractProblems()`를 `props.enabled`가 true일 때만 부른다. 주석 ③과 DECISIONS ④는 "켰는데 의존이 안 들어가거나, **껐는데 들어가는** 바이너리를 막는다"고 적었다.
- 직접 확인: V2 스파이크(`mongmange-wt-ink`)의 `modules/ink-recognizer`를 그대로 복사한 루트에서 `enabled: false` → **통과**(막지 않음). 같은 루트에서 `enabled: true` → 두 문제(build.gradle·podspec이 키를 읽지 않음)로 멈춤.
- 위험: 스위치가 지금 false인 채로 V2가 스파이크 build.gradle(`implementation 'com.google.mlkit:digital-ink-recognition:19.0.0'`, 무조건)을 그대로 넣으면, 11-30에 'C′-키보드'로 결정되어도 ML Kit이 동결 바이너리에 조용히 들어간다(크기·처리방침의 ML Kit 진단 정보 문구와 직결). 이것이 스위치를 만든 이유 그 자체다.
- 고칠 방향: `modules/ink-recognizer`가 **있으면** 켬·꺼짐과 관계없이 계약 검사를 돌린다(없으면 꺼짐만 통과). 시험에 "꺼짐 + 스파이크 모양 모듈 → 멈춤" 한 줄.
- 덧붙임(경미): 계약 검사가 `includes('mong.inkRecognizer')`라 주석에 키 이름만 적어도 통과한다. 최소한 Android는 `findProperty('mong.inkRecognizer')`, iOS는 `Podfile.properties.json`을 읽는 모양을 정규식으로 본다.

## 보통

**M1. 키 자리 마감이 '동결 12-19 전'으로 적혀 있지만 실제 마감은 '리허설 12-12 전'이고, Android Play 앱 서명 키는 순서 문제가 있다**
- 가드는 EAS에서 `EAS_BUILD=true`이고 프로필이 `development`가 아니면(= preview·production) 멈춘다. 12-12 리허설을 preview·production으로 돌리면 키가 비어 있는 한 prebuild 단계에서 실패한다(이미 `withSelfHostedUpdates`도 `ready: true`·채널을 요구 — 실측 `CommandError: [withSelfHostedUpdates] 출시 빌드인데 …`).
- 환경 판별 자체는 맞다: 로컬 `expo config`·`prebuild`·`eas update`(EAS_BUILD 없음)·development 프로필은 통과, `eas build --local`도 EAS_BUILD=true라 같은 규칙. iOS는 팀 ID만, Android는 지문만 본다(플랫폼 모르면 둘 다).
- 지문 2개 요구는 맞다: preview·production이 같은 EAS 키스토어(업로드 키)로 서명되어 직접 설치본은 업로드 키, Play 배포본은 Play 앱 서명 키로 검증된다 → assetlinks에 둘 다 필요. 다만 **Play 앱 서명 키는 Play Console에 첫 AAB를 올린 뒤에야 지문이 보이는 것으로 안다**[확인 필요]. 그렇다면 첫 production Android 빌드는 가드에 막힌다. 순서를 적어 둘 것: ① `eas credentials`로 업로드 키 만들기 → ② preview AAB(또는 development 외 빌드)를 Play 내부 테스트에 올려 앱 서명 키 확보 → ③ 두 지문 + 팀 ID를 props·web-static env 두 곳에 → ④ production. props 값은 fingerprint에 들어가므로 ③ 뒤 런타임이 한 번 바뀐다(12-19 전이면 비용 0).
- 고칠 방향: DECISIONS [오너 몫] 줄을 "리허설(12-12) 전"으로, 위 순서를 함께.

**M2. 위젯 Swift·Info.plist는 fingerprint에 들어가지 않는다 — ota-self-host.md 4절 '네이티브가 바뀌면 런타임이 바뀐다'의 빈틈**
- 실측 `fingerprintSources`: `targets/widget/expo-target.config.js`(expoConfigPlugins)만 있고 `targets/widget/MongWidget.swift`·`Info.plist`는 없다(로컬 모듈 `modules/widget-bridge/ios`는 autolinking으로 들어감).
- 결과: C3에서 위젯 Swift만 고친 스토어 빌드는 이전 바이너리와 **같은 런타임**이 된다. 위젯 Swift는 JS와 직접 맞물리지 않아 지금 당장 OTA 사고는 아니지만, 계약 문자열(App Group·`mong.widget.v1`)이 바뀌면 JS 판과 위젯이 어긋난 채 같은 런타임으로 취급된다.
- 고칠 방향: `fingerprint.config.js`에 `extraSources: [{ type: 'dir', filePath: 'targets', reasons: ['appleTargets'] }]`(생성물 `targets/*/Assets.xcassets`는 `ignorePaths`로 제외). 런타임이 한 번 더 바뀌므로 동결 전에. `ota-config.test.ts` 또는 c10 시험에 "targets Swift 한 글자 바꾸면 런타임이 바뀐다" 고정.

**M3. 시험이 놓치는 변이 4개(6절)**
- 위젯 핸들러 등록(`index.ts`) 삭제, intentFilter `path`·`pathPattern` 금지 검사 삭제, 지문 소문자 정규화 삭제, 잉크 스위치 mod 출력값(gradle.properties·Podfile.properties.json) 변조 — 모두 19개 통과로 살아남았다.
- 고칠 방향: ① `index.ts` 원문에 `Platform.OS === 'android'` 안 try로 `registerMongWidget()`가 있는지 문자열 고정 ② bad 목록에 `{...data, path: '/m/x'}` ③ 소문자 FP1·FP2가 production에서 통과 ④ `withInk`를 `compileModsAsync`(또는 mod 함수를 꺼내 modResults에 적용)로 돌려 `mong.inkRecognizer=false`·`"false"` 값을 확인 — 이것이 꺼짐 바이너리를 정하는 유일한 출력이다.

## 경미

- **L1. 위젯 확장 판 번호 고정**: prebuild 산출 pbxproj에서 위젯 타깃 `CURRENT_PROJECT_VERSION = 1`, `MARKETING_VERSION = 1.0.0`(apple-targets가 prebuild 때 `ios.buildNumber || 1`로 박음). `eas.json`은 `appVersionSource: remote` + production `autoIncrement` → 앱 CFBundleVersion과 확장이 어긋나 App Store Connect 경고(ITMS-90473)가 날 수 있다[확인 필요 — EAS가 확장 타깃 판도 맞추는지]. 리허설 12-12 확인 항목에 추가.
- **L2. Android 위젯 헤드리스 기동이 `index.ts` 전체를 돈다**: 위젯 추가·갱신으로 프로세스가 차갑게 깨면 Skia 준비·`require('./App')`·`startOta()`까지 같이 돈다. V24 진입점(동기 등록·두 겹 try·`rethrowLater`)은 **깨지지 않는다** — 새 블록은 맨 뒤, 자체 try, 앞 단계와 독립. 다만 헤드리스에서 App 로드 실패 시 `rethrowLater`가 백그라운드 프로세스를 죽인다. 지금은 `updatePeriodMillis 0`이라 빈도가 낮다. C3에서 헤드리스일 때 OTA·App 로드를 건너뛸지 판단.
- **L3. 계약 검사 문자열 수준**(H1 덧붙임과 같음).
- **L4. prebuild 경고** `[bacons/apple-targets] Expo config is missing required ios.appleTeamId` — 키 자리가 비어 있는 동안 정상. EAS는 프로비저닝 때 타깃별 팀을 넣으므로 리허설 전에 props만 채우면 된다.
- **L5. `react-native-android-widget`가 Android에 `androidx.work:work-runtime:2.12.0`(WorkManager, androidx.startup 초기화)·`com.caverock:androidsvg-aar:1.4`를 끌어온다** — 동결 바이너리 면적. 위젯에 필요한 것이므로 받아들이되 DECISIONS ②에 한 줄 적어 둘 것(처리방침 영향 없음: 네트워크·식별자 없음).

- 스파이크 `modules/ink-recognizer`: Android build.gradle 무조건 `digital-ink-recognition:19.0.0`, iOS는 ML Kit 없는 스텁(`isAvailable { false }`), JS `isAvailable(): boolean`. → 계약의 `isAvailable() = false` 스텁 모양·JS 대체 경로와는 맞는다. 그러나 Android는 그대로 넣으면 켤 수 없고(플러그인이 멈춤 — 의도대로), **끈 채로는 그대로 들어간다(H1)**. ### `src/ota/index.ts` `whenForeground`(L2 반영)
- **V24 진입점 규칙은 깨지지 않는다.** `index.ts`는 바뀌지 않았다(동기 `registerRootComponent`, `ready.catch → rethrowLater`, `try { startOta() }` 그대로). 안쪽 try도 `startOta`·`startNow`·`startOtaWith`로 오히려 한 겹 늘었다. 기존 V24 정적 시험도 통과한다.
- **OTA 확인이 영영 빠지는 경로는 없다.**
  - RN 0.88 `AppState.js`는 생성할 때 `getCurrentAppState`로 초기값을 보정하고, 값이 다르면 `appStateDidChange`를 직접 emit한다(그러면 'change' 리스너가 불린다).
  - Android `AppStateModule.kt`는 `onHostResume`에서 active를 보낸다.
  - 그래서 번들 평가 시점에 background로 잡혀도, 구독은 동기로 먼저 걸리고 첫 active는 반드시 도착한다.
  - 헤드리스로 깬 프로세스에서 사용자가 뒤이어 앱을 열 때도 같은 JS 런타임에 `onHostResume`이 와서 시작된다.
  - active가 한 번도 오지 않는 경로는 위젯 헤드리스뿐이고, 이것이 바로 의도한 동작이다.
- **iOS는 영향 없다.** `platform !== 'android'`면 상태와 관계없이 곧바로 시작한다(V24 그대로). iOS도 active를 기다리게 하는 변이는 시험이 잡는다.
- 남은 경미 1: Android에서 active 전에 죽는 기동은 V24 checker의 '실행'으로 세지 않는다. 그래서 그런 크래시는 크래시 루프 판정에서 빠진다. 다만 active는 첫 화면보다 앞서 오고, 네이티브 `ERROR_RECOVERY_ONLY` 복구는 그대로라 실해는 작다. DECISIONS에 한 줄 적어 두기를 권한다.
- 남은 경미 2: `startOta()`가 실제로 `whenForeground`를 거치는지는 시험이 고정하지 않는다(변이 R3이 살아남음). 대역 Platform이 ios여서 차이가 드러나지 않는다. `src/ota/index.ts` 원문에 `whenForeground(Platform.OS, AppState.currentState`가 있는지 확인하는 문자열 단언 하나면 된다.
