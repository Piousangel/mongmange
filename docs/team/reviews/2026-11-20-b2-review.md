## 잘된 점(유지)

- 세이브: 모든 쓰기가 `saves` 행 `FOR UPDATE` → 같은 sha → 전제 조건 → 할당량 → 이력 → UPDATE → 칸별 3벌 순서. 첫 PUT 동시 경합은 `ON CONFLICT DO NOTHING` + 같은 트랜잭션 재조회(READ COMMITTED라 새 스냅숏)로 결정적. 이력 조회·restore는 늘 `public_id AND creature_id`, 형식이 틀린 id도 같은 404.
- 인증: `jose` `algorithms: ['ES256','RS256']`라 HS256·none은 키를 찾기 전에 떨어지고, iss·aud·exp(30초)·role·sub(uuid) 모두 검사. `SUPABASE_URL`이 없으면 닫힘. Auth Admin은 상태 코드만 읽는다.
- 되살아남 막기: `user_auth` 없음 401 + bootstrap·recover에서 `auth_gc` 거절 + Auth 존재 확인. 삭제가 `users` 행을 `FOR UPDATE`로 잡아 동시 삭제가 하나로 모인다.
- 개인정보: 글귀·영수증은 해시만, 레이트 리밋 키도 IP 접두·해시만, 로그 시험(`cloud-logs.db`)이 B2 흐름 전체를 돈 뒤 토큰·글귀·영수증·IP·sub·코드·본문 0건을 단언. 연령은 판 번호·날짜만, 계약이 strict라 태어난 해가 들어올 칸이 없다.
- 흔적 0 시험이 모든 표를 훑는다. 영수증 무인증 조회는 128비트 난수의 해시 대조라 **존재 여부 오라클이 아니다**(형식 검사 → 해시 → 만료, 모두 같은 404).
- `/delete` 정적 폼: CSP `connect-src` 한 출처·`form-action 'none'`(JS가 죽어도 글귀가 GET 쿼리로 새지 않음)·`credentials:'omit'`·no-referrer·textContent만, 빌드 검사가 이 모두를 고정.

## 중요(커밋 전 또는 B6 전)

**I1. JWKS가 200이 아니면(5xx·429·3xx) 503이 아니라 401 — 익명 세션을 앱이 버릴 수 있다** — `apps/server/src/auth/jwt-verifier.ts:48-51, 64-67`
- jose 6.2.18 `fetchJwks`는 상태가 200이 아니면 기본 `JOSEError`('Expected 200 OK…')를, JSON 파싱 실패도 `JOSEError`를 던진다. `isFetchFailure`는 `JOSEError`면 곧바로 false라 **401**이 된다. 탐침으로 500·503·429·302 모두 401 확인. 지금 시험(`auth-jwt.test.ts:76`)은 연결 거부(127.0.0.1:1)만 본다.
- 결과: Supabase Auth가 잠깐 5xx를 내면 모든 요청이 401 → 앱은 '세션을 새로 고친다'(`unauthorized` 주석). 익명 계정은 다시 로그인할 수단이 없으므로, 앱이 401 반복을 '세션 끝'으로 다루면 3-3 ⑦('끊김 표시만')이 깨지고 사용자는 글귀 없이는 몽망이를 잃는다.
- 함께: `cacheMaxAge` 10분이 지나면 매 검사가 다시 받으려 하고 실패 시 옛 키로 대신하지 않는다(stale-if-error 없음). 10분짜리 JWKS 장애가 곧 전원 401/503.
- 권고: 키 조회 단계 오류(`JWKSTimeout`·`JWKSInvalid`·위 기본 `JOSEError` 두 문구·fetch 실패)는 503, 서명·클레임 오류(`JWSSignatureVerificationFailed`·`JWTClaimValidationFailed`·`JWTExpired`·`JWSInvalid`·`JWKSNoMatchingKey` 등)만 401로 **허용 목록식**으로 나눈다. fake-supabase에 'JWKS 500' 스위치를 더해 503을 단언. 필요하면 마지막 성공 키 집합을 장애 동안 쓰는 래퍼.

**I2. cron 설정이 운영에서 선택이라 삭제 뒤처리·옛 기기 30일 정리가 조용히 멈출 수 있다** — `apps/server/src/config/env.ts:79-80, 84-97`, `src/cron/cron.controller.ts:27`
- `CRON_AUDIENCE`·`CRON_SA_EMAIL`이 없으면 404로 '존재를 숨기는' 것은 좋지만, 운영에서도 없을 수 있다(`superRefine`은 SUPABASE·PEPPER만 필수). 그러면 ① 요청 안에서 실패한 Auth 삭제가 영원히 `pending`(영수증·`/delete` 문구 '24시간 안에 끝나요'와 어긋남) ② 처리방침 6절 '옛 계정 30일 뒤 삭제'가 지켜지지 않음 ③ 아무 로그도 남지 않음.
- 추가 함정: Cloud Scheduler OIDC 토큰의 `aud` 기본값은 **대상 URL 전체**(`…/internal/cron/storage-gc`)다. `CRON_AUDIENCE`를 서비스 URL로 넣고 잡의 audience를 비워 두면 늘 404 — 역시 조용함.
- `auth_gc`·`storage_gc` 실패는 `attempts`만 올리고 상한·알림이 없다(`gc.service.ts:93, 72`).
- `app.prune_save_versions()` 등록도 B6인데, `weekly`는 PUT 안 개수 솎기 대상이 아니라(`cloud-save.service.ts:185-186`) pg_cron이 빠지면 '최대 4주'가 조용히 깨진다.
- 권고: 운영 zod에서 `CRON_AUDIENCE`·`CRON_SA_EMAIL` 필수(env 시험 한 줄), B6 체크에 'Scheduler 잡 audience = `CRON_AUDIENCE` 명시'. `runDue`가 `attempts ≥ 3`이나 24시간 넘은 미완료 `deletion_log`를 error 로그(알림 대상)로. 방어 겹으로 PUT 안에서 `weekly`도 최신 4벌만 남기기(값싼 이중 장치).

**I3. 유일한 무인증 쓰기 경로(`/deletion/web`)의 시도 한도가 시험 밖** — `apps/server/src/account/account.service.ts:140, 145`
- M8(IP 접두 5/시간 제거)·M9(글귀당 10/일 제거) 모두 시험 45개를 통과했다. `/recover` 한도는 시험되지만 웹 삭제는 별도 버킷(`web_delete_ip`)이라 그 시험이 덮지 않는다. 누가 리팩터링에서 한 줄을 지워도 모른다.
- 권고: '틀린 코드·글귀 5번 → 여섯째 429(맞는 쌍이라도)', '같은 글귀를 IP 열 곳에서 → 열한째 429' 두 단언. 아울러 `recover_ip`와 `web_delete_ip`가 따로라 IP 하나당 글귀 대입이 사실상 10/시간인 점을 3-8 표에 적기(엔트로피상 위험은 없음).

## 사소

- **m1 pepper 회전**(`account.service.ts:104, 144`, `recovery-pepper.ts:14-15`): 찾기는 지금 pepper 하나뿐이다. 누가 `RECOVERY_PEPPER`·`_V`를 '회전'하면 모든 글귀가 말없이 무효가 된다. A-3 #21이 '그때 확장'이라 적었으니, 런북에 '코드 변경 없이 pepper를 바꾸지 말 것'을 적거나 `RECOVERY_PEPPER_V > 1`이면 옛 pepper 값도 요구하도록 zod로 막기.
- **m2 백업 복원 때 지운 계정이 되살아남**: `deletion_log`에는 누구인지가 없어 운영 백업(7일)을 복원하면 그 사이 지운 사용자를 다시 지울 근거가 없다. 백업 보존 기간(7일)만 `HMAC(user_id)`를 `deletion_log`에 두고 만료 함수로 NULL로 만드는 안 + 런북 '복원 뒤 재삭제'. 처리방침 '백업 7일'과도 맞는다(B6·B7 리허설 때).
- **m3 영수증이 URL 경로에 있다**(`deletion.controller.ts:62`): 앱 로그는 경로 템플릿이라 0건이지만 Cloud Run 플랫폼 요청 로그(`httpRequest.requestUrl`)에는 남는다. 영수증은 24시간·'pending/done'만 알려 주므로 영향은 작다 — B6 로그 버킷 7일 확인 항목에 함께 적기.
- **m4 숫자 규칙 우회**(`packages/core/src/sim/pillars.ts:188`): 정본 문구('7개 이상 이어지면') 그대로라 구현 잘못은 아니지만, `010123·45678`(12자)처럼 가운뎃점·공백 하나로 11자리 번호가 통과한다. 전각·아라비아-인도 숫자는 허용 문자에서 먼저 떨어짐(시험 있음). 정본에 '구분자(공백··)를 뺀 숫자 합 ≥ 8 거부' 같은 판단을 남길지 결정 필요. 또 불러오기는 `nameShape`만 보므로(D-13 결정성, 타당) **B3 공개 검사는 반드시 `normalizeName`**을 써야 한다 — 조작 세이브로 `01012345678`을 올릴 수 있다. B3 체크에 한 줄.
- **m5 레이트 리밋 메모리**(`common/rate-limiter.ts:31, 48`): sweep이 24시간 지난 창만 지운다. IPv6 /64를 대량으로 가진 쪽이 recover·웹 삭제를 두드리면 Map이 커진다(전역 120/분이 있어 느림). 상한 초과 때 가장 오래된 것부터 버리는 정도로 충분.
- **m6 문서 잔재**: architecture.md 3-2 '인증 공통 규칙'(228줄) '인증 없는 경로는 핑·`/m/**`·삭제 영수증 조회뿐' → `/deletion/web` 추가. 3-8 ②(664줄) '처리한 뒤 받은 메일(글귀 평문 포함)은 지운다'와 3-12(802줄) `ops:delete <code> <글귀>`는 이번 결정과 어긋남 — 지우거나 '대체됨' 표시. `/delete`가 링크하는 `/privacy`는 아직 없다(B8까지 404).
- **m7 웹 삭제 코드 정규화**(`account.service.ts:141`): 글귀는 Crockford(I·L→1, O→0)로 읽지만 인장 코드는 `toUpperCase`만. 사람이 옮겨 적는 값이라 같은 규칙이 맞다(편의).
- **m8 본문 한도**: `BODY_LIMIT` 768KB인데 세이브 상한 512KB는 **이스케이프 전** 문자열 기준이다. 따옴표가 많은 본은 JSON 안에서 커져 Fastify 413(다른 경로)로 먼저 떨어질 수 있다(정상 본 30KB라 실사용 영향은 거의 없음).
- **m9 CGNAT**: 새 계정 IP 접두 5/시간은 통신사 CGNAT 뒤 실사용자를 막을 수 있다(정본 값, Supabase 익명 가입 30/시간과 같은 문제). B7 L5에서 관찰.
- **m10 recover·삭제 교착**: 같은 사용자의 `recover`(creatures 잠금 → user_auth INSERT가 users KEY SHARE)와 `DELETE /me`(users FOR UPDATE → CASCADE가 creatures 잠금)가 겹치면 Postgres 교착 감지로 한쪽이 500. 데이터는 안전(한쪽만 커밋). 빈도가 낮아 기록만.

## 확인한 것(문제 없음)

- 남의 이력 접근: `version`·`restore` 모두 `creature_id` 조건(시험 e2e 7). 동시 restore·PUT은 같은 행 잠금으로 줄을 선다. restore는 할당량을 세지 않지만 새 바이트를 받지 않으므로 타당(A-3 #27).
- 미래 판: +1까지만, 판 번호 없으면 422(시험 e2e 8). 크기: UTF-8 512KB → gzip 256KB → 하루 4MB, 모두 잠근 행 위에서. 60/시간 × 256KB > 4MB라 실제 상한은 4MB.
- 리비전 역행: UPDATE는 `rev = rev + 1`뿐이고 restore도 +1. 같은 sha 200은 서버 rev를 그대로 돌려줄 뿐 바꾸지 않는다.
- 삭제 연쇄: users CASCADE(user_auth·creatures·saves·save_versions) + `auth_gc`(모든 sub, 끊긴 것 포함) + `storage_gc`(FK 없음 → 사용자 삭제 뒤에도 남아 처리됨) + 영수증 해시 24시간. 남는 것: `deletion_log` 개수, 백업 7일, 플랫폼 로그(m3).
- 영수증 무인증 조회: 형식 → 해시 → 만료, 모두 같은 404, IP 30/분. 오라클 없음.
- `/deletion/web` CSRF·남용: 쿠키 없음, form-urlencoded 미파싱, CORS는 응답 읽기만 막고 쓰기는 글귀가 막는다. 코드·글귀 어느 쪽이 틀렸는지 구분하지 않는다.
- 오류 응답: 4xx `details`는 경로·이유만(값 없음), 5xx 메시지 숨김. 401 이유를 나누지 않음.
- jose 6.2.18: MIT, 런타임 의존성 0, 정본 2-4가 지정. 라이선스 장부 기재 맞음. 과설계 없음(supabase-js를 들이지 않은 판단 타당).
- 타이밍: 글귀는 HMAC 뒤 유니크 인덱스 조회라 문자열 비교 타이밍이 없다. 맞는 글귀일 때만 Auth 호출로 느려지지만 그때는 이미 성공 응답이다.
