## 1. 결정적 새 글귀(HMAC) — 안전함, 낮음 2건
- 새 글귀는 `HMAC-SHA256(pepper, "recover-next:" + sub + ":" + 옛 글귀)`의 앞 80비트입니다(`codes.ts:39`). 글귀 해시 `HMAC(pepper, code16)`의 입력은 콜론이 없는 16자라 용도가 겹치지 않습니다(도메인 분리 OK). pepper를 모르면 sub와 옛 글귀를 알아도 계산할 수 없습니다.
- **재사용·탈취**
  - 재시도(replay)는 `a.userId`가 있는 **그 sub 자신의** 몽망이 해시와 비교할 때만 성공합니다(`account.service.ts:110-116·177-191`). 다른 기기가 옛 글귀를 넣으면 옛 글귀가 어떤 몽망이에도 맞지 않아 404이고, 자기 몽망이가 있으면 409입니다.
  - B1(해시 비교 생략) 변이를 시험이 잡았습니다.
  - 글귀를 다시 받으면(reissue) 해시가 무작위 값으로 바뀌므로 replay가 끝납니다(시험 있음).
- **pepper 회전**: replay는 행의 `recovery_pepper_v` 판으로 다시 계산합니다. 옛 판이 목록에서 빠지면 409로 떨어지는데, 이는 안전한 쪽입니다(B5 잡힘).
- **'한 번만 보여 줌'과의 충돌(낮음 L1)**: replay에는 기한이 없습니다. 이 기기 세션과 옛 글귀(종이)를 함께 가진 사람은 **글귀를 다시 받기 전까지 언제든** 지금 글귀를 다시 볼 수 있습니다. 세션을 가진 사람은 앱의 '새 글귀 받기'로도 같은 힘을 가지므로 공격면이 늘지는 않습니다. 다만 원칙과 맞추려면 `recovery_rotated_at`에서 짧은 창(예: 24시간) 안에서만 replay를 허용하기를 권합니다.
- **pepper 유출 때의 영향 변화(낮음 L2)**: 전에는 pepper가 새도 지금 글귀(난수 80비트)를 알 수 없었습니다. 이제 되찾기로 받은 글귀는 **pepper + sub + 옛 글귀**로 계산됩니다(옛 종이 글귀를 아는 사람 + pepper 유출). 조건이 겹쳐야 하므로 낮음이지만, DECISIONS B2b ①의 '저장 0'과 맞바꾼 비용으로 적어 두어야 합니다. 글귀를 다시 받은 뒤에는 무관합니다.

## 2. `no_account`가 계정 존재 오라클이 되는가 — 되지 않음
- 가드는 서명·iss·aud·exp·role을 **DB를 보기 전에** 검증하고, 실패하면 sub와 무관하게 같은 `unauthorized`입니다(시험 '그 sub가 있든 없든 똑같이 401 unauthorized').
- 공격자가 서명된 토큰을 얻는 길은 자기 익명 로그인뿐이라 `no_account`가 알려 주는 것은 **자기 sub의 상태**뿐입니다.
- 남의 sub·사용자 id를 매개변수로 받는 경로도 찾지 못했습니다(웹 /delete는 인장 코드 + 글귀, 실패는 404 한 갈래).
- 지움·Auth 대기·맡긴 적 없음이 모두 같은 `no_account`이므로 '지운 적 있음'도 구별되지 않습니다.
- 응답 시간이 다른 것(unauthorized는 DB 조회 없음)은 토큰 검증 실패 여부를 드러낼 뿐입니다.

## 3. 410 `no_account`와 흔적 0 — 지킴, 단 뜻이 모호함
- 판단 근거는 '토큰 sub에 user_auth 행 없음' 하나이고 새로 저장하는 값이 없습니다. '다시 지운 뒤 모든 표 흔적 0'을 시험으로 확인합니다.
- Auth 삭제 대기(auth_gc) 중에도:
  - DELETE는 410 `no_account`입니다.
  - bootstrap·recover는 `assertLiveLogin`에서 401 `no_account`입니다(B8 잡힘).
  - 토큰은 만료 전까지 유효하지만, 계정을 다시 만드는 길은 막혀 있습니다.
- 401·410 응답은 no-store입니다(B6 잡힘).
- **뜻이 모호함**: 같은 410 `no_account`가 '지워짐'과 '이 로그인은 맡긴 적 없음(새 익명 로그인)'을 함께 뜻합니다(시험도 '맡긴 적 없는 로그인의 DELETE도 410'으로 고정). 흔적 0을 지키려면 서버가 둘을 가를 수 없으므로 이 설계 자체는 옳습니다. 문제는 아래 H1처럼 **앱이 이것을 '지워짐 확정'으로 읽으라는 지침**입니다.

## 4. C12 앱과 맞물릴 때 — '앱이 맞출 것' 목록은 부족함
- **H1(높음) '410 `no_account` = 지워짐 확정' 지침은 거짓 삭제 확인을 만듭니다**
  - 근거:
    - 세이브 MMKV(`mong` — `mong.cloud.v1` 기록 포함)는 D-06대로 OS 백업 대상입니다.
    - 세션 MMKV(`mong.session`)는 architecture 3-3 ④대로 백업에서 뺍니다.
  - 경로:
    1. 새 폰으로 복원하거나 세션 저장소를 잃으면, 앱은 기록이 '켜짐'인 채로 **새 익명 로그인**을 합니다.
    2. 그 상태에서 '지우기'를 하면 새 sub로 DELETE → 410 `no_account`가 옵니다.
    3. 지침대로라면 앱은 "지웠어요"를 보입니다.
  - 결과: **실제 계정과 맡긴 본은 서버에 그대로**입니다. 처리방침의 삭제 약속과 어긋나고(QA-3), 사용자는 웹 삭제를 할 이유를 잃습니다.
  - 고칠 방향(지침 갱신):
    - 앱 기록에 맡겨 두기를 켤 때·되찾을 때의 sub(또는 그 해시)를 남깁니다.
    - 지금 토큰의 sub가 그것과 같을 때만 410 `no_account` = 지워짐으로 봅니다.
    - 다르면 "이 기기의 로그인이 바뀌어 여기서는 지울 수 없어요 — 되찾기 글귀로 이어 붙이거나 웹 삭제"로 안내합니다(재리뷰 2·3의 '서버에 남았을 수 있음' 표시와 같은 갈래).
- **M1 401 `no_account` = '세션·기록 비움' 지침의 같은 모호함**
  - 같은 복원 상황에서 앱은 조용히 '꺼짐'이 됩니다.
  - 사용자가 다시 켜면 **새 계정·새 인장 코드**가 생기고, 옛 계정은 2년 정리 때까지 고아로 남습니다.
  - 고칠 방향: 기록에 남은 sub와 다르면 "새 기기에서는 되찾기 글귀로 이어 주세요"를 먼저 보입니다.
- **M2 지금 C12 앱(main 미커밋 C12c)과 계약이 이미 어긋남**
  - `apps/mobile/src/cloud/api.ts:99`는 모든 410을 `moved`로 읽고, 401은 code를 보지 않습니다. 가짜 서버(`fakeServer.ts:74-75`)도 새 코드를 내지 않습니다.
  - 결과: 지우기가 커밋된 뒤 다시 보낸 DELETE가 410 `no_account`를 받으면, 앱은 '다른 기기로 옮겨졌어요'를 보이고 기록을 `moved`로 둡니다. 사용자는 삭제가 끝났다는 말을 듣지 못합니다.
  - DECISIONS의 "옛 앱은 410을 moved로 읽어 세션만 비우므로 해롭지 않다"는 사실과 다릅니다. 기록과 화면까지 바뀝니다. 플래그가 꺼져 있어 지금 사용자 피해는 없지만, 앱 반영과 가짜 서버 갱신을 C12 쪽 작업으로 명시해야 합니다.
- **M3 replay를 받았는데 이 기기에 기록이 이미 있을 때**
  - 같은 기기에서 며칠 뒤 사용자가 옛 글귀를 다시 넣으면(헷갈림) 서버는 200 replay를 돌려줍니다.
  - 지금 C12 `recover()`는 이를 정상 되찾기로 보고 `FRESH_RECORD`로 **기록을 덮어씁니다**(codeConfirmed·rev·sha 초기화). 그리고 지금 글귀를 다시 보여 줍니다.
  - 유실은 없지만(다음 맡기기가 충돌 확인을 거침) 혼란스럽습니다.
  - 지침에 "기록이 있고 그 creature가 `creature.code`와 같으면 '이미 되찾음'으로 끝내고 기록을 덮지 않는다"를 더하기를 권합니다.
- 지침의 나머지(401 `unauthorized` → 토큰 갱신 뒤 한 번 더, 410 `moved` 그대로, replay면 같은 글귀를 다시 보여 주기)는 맞습니다. replay는 같은 sub + 같은 옛 글귀일 때만 오므로, 앱의 '대상 인장 코드 비교'는 있으면 좋은 정도이지 필수는 아닙니다.
