## 높음

### H1. web-edge 검사를 퍼센트 인코딩 경로로 우회할 수 있다(재현함)

- 위치: `app.factory.ts`의 onRequest 훅 `if (routeGroupOf(request.url) !== 'web') return;`, `client-ip.ts`의 `routeGroupOf`
- `routeGroupOf`는 **원본 URL 문자열**에서 `/m/`로 시작하는지만 본다. Fastify(find-my-way)는 경로를 **디코드한 뒤** 라우팅한다. 그래서 `/%6D/{code}`는 그룹 판정에서 `api`가 되어 검사를 건너뛰지만, 라우터는 `/m/:code` 핸들러로 보낸다. 재현 결과 `/m/{code}`(HTML)·`/report`·`/get`·`/seen` 모두 enforce에서 통과했다.
- 영향: enforce로 바꾸어도 `*.run.app` 직접 호출(CDN을 건너뛴 HTML 홍수, 신고 폼 남용)을 막지 못한다. B6에서 "enforce로 막았다"고 믿게 되는 **조용한 실패**다. log 모드의 `web_edge_unverified` 개수에도 잡히지 않는다.
- 권고: 경로 문자열 대신 **라우팅 결과**로 판정한다. 같은 파일의 ROUTE_TEMPLATE 훅이 이미 onRequest에서 `request.routeOptions?.url`을 쓴다. 예를 들어 `request.routeOptions.url`이 `/m`이거나 `/m/`로 시작하면 web으로 본다. 또는 `routeGroupOf`가 `decodeURIComponent`한 경로로 판정한다(잘못된 인코딩이면 web 쪽으로 닫는다). 시험에는 `/%6D/…`·`/%6d/…/get`·`POST /%6D/…/seen` → 403을 넣는다. `ClientIpService`의 그룹 판정도 같은 함수를 쓰므로 함께 맞춘다. 지금은 인코딩 경로가 `api` 그룹이 되어 오히려 맨 오른쪽 IP를 쓰므로 위조는 안 되지만, 두 판정이 어긋나는 상태 자체가 위험하다.

## 중간

### M1. 종료 flush가 Cloud Run 유예 10초를 넘을 수 있다(예산을 나눠 쓰지 않음)

- `drain()`은 마감 시각을 **반복을 시작할 때만** 확인한다. 7.9초에 시작한 flush 한 번이 연결 얻기 1.5초 + 쿼리 제한 6초까지 걸리면 13초를 넘긴다.
- Nest의 `beforeApplicationShutdown`은 모듈별로 **순서대로** 돈다. MetricsModule 집계 flush(최대 3번 × 최대 6초)와 링크 flush(8초)가 한 유예를 **나눠 쓰지 않는다**. DB가 멈춘 상태에서 SIGTERM이 오면 SIGKILL이 먼저 와서 `link_flush_lost` 로그조차 남지 않는다. 문서에 적힌 "8초 안에 DB가 못 받으면 개수만 로그"가 이 경우에는 성립하지 않는다.
- 권고: 프로세스 전체에 종료 마감 하나(예: SIGTERM + 8초)를 두고, 두 집계기가 그 남은 시간으로 각 시도를 `Promise.race`로 끊는다. 마감 직전에 손실 로그를 먼저 쓴다. 시험에는 '멈춘 DB + close() → 9초 안에 끝남 + lost 로그'를 넣는다.

### M2. 칸이 꽉 찬 채로 DB가 죽어 있으면 재시도가 15초 간격이 아니라 '요청마다'가 된다

- `add()`는 `current.size >= LINK_MAX_CELLS`이면 매번 `flush()`를 부른다. 대기 묶음이 있으면 `flushOnce`가 그 묶음을 곧바로 다시 보낸다. 동시에 하나만 돌기는 하지만 실패하자마자 다음 요청이 또 시작하므로 연속 재시도가 된다. 문서의 "재시도 간격 = 주기(15초)"와 다르다.
- DB 장애가 길고 트래픽이 많을 때 인스턴스마다 쉬지 않고 연결을 시도한다. 그만큼 풀이 묶여 다른 요청의 연결 대기가 늘고, DB가 살아날 때 몰려드는 부하도 커진다.
- 권고: 대기 묶음이 있을 때는 '꽉 참' 경로에서도 `lastFlushAt` 주기를 지킨다(실패가 이어지면 백오프). 시험에는 '실패 중 꽉 찬 상태에서 요청 1,000번 → `$executeRaw` 호출 1번'을 넣는다.

### M3. log 기본값인 동안 web 그룹 XFF 위조로 RateLimiter의 시간·하루 창을 밀어낼 수 있다(기존 구조, B7a가 그대로 둠)

- web 그룹은 hops=2라서 `*.run.app`에 직접 부르면 오른쪽에서 두 번째, 즉 공격자가 쓴 값이 키가 된다. `/m/x/get`은 이제 DB도 전역 throttler도 거치지 않는 가장 싼 경로인데, `m_get` 창을 위조 IP마다 하나씩 `RateLimiter`에 만든다.
- `RateLimiter`는 50,000칸에 닿으면 **넣은 순서대로** 80%까지 버린다(LRU가 아님). 그래서 위조 요청 수만 건으로 `account_ip_day`(하루)·신고 시간당 창 같은 **긴 창이 지워진다.** 계정 상한은 하루 전체 상한이 받쳐 주지만, IP별 하루 한도는 사실상 다시 시작된다.
- 근본 대책은 H1을 고친 뒤의 enforce다. 그 전까지는 ① 긴 창과 분 단위 창을 서로 다른 Map(또는 상한)에 두거나 ② 버릴 때 분 단위 창부터 지우는 방안을 권한다. DECISIONS B7a의 '한계'에는 throttler 저장소만 적혀 있으니 RateLimiter 쪽도 적는다.

## 낮음

- **L1. 1만 칸 버림의 왜곡.** 꽉 차면 '이미 있는 칸만 계속 센다'. 그래서 버림이 생기면 그 15초 동안 **새로 등장한 코드·새 날짜 칸이 체계적으로 덜 세진다**(무작위로 빠지는 것이 아니다). 이 사실과 `link_cells_dropped` 로그는 DECISIONS에 적혀 있다. 하지만 대시보드나 `link_daily` 쪽에는 표시가 없어, 날짜가 바뀌는 순간 버림이 나면 그날 첫 조회가 빠진 것을 알 수 없다. 버림이 0이 아닌 날을 운영 지표나 B6 경보에 넣기를 권한다.
- **L2. 교착 방지 정렬은 보장이 아니다.** `unnest`의 행 순서는 상관 EXISTS(세미 조인) 계획에 따라 달라질 수 있다. `SELECT … ORDER BY d.day, d.code, d.event`를 명시하기를 권한다. 교착이 나더라도 문장 전체가 롤백되고 같은 id로 다시 보내므로 **정확성은 안전**하고, 늦어질 뿐이다.
- **L3. 트랜잭션 도중 소켓을 버린 뒤 서버 쪽 잠금.** 네트워크가 끊긴(블랙홀) 상태에서 소켓을 버리면 Postgres가 끊김을 알아챌 때까지 그 백엔드가 'idle in transaction'으로 잠금을 쥘 수 있다. 데이터 정합은 롤백이라 안전하고, 풀은 소켓을 버리므로 고갈되지 않는다. 다만 트랜잭션 풀러(Supavisor)가 이 경우를 어떻게 처리하는지는 [확인 필요: B6]. 연결 옵션에 `idle_in_transaction_session_timeout`(예: 10초)을 주는 방안을 권한다.
- **L4. 대역 스냅숏 주기.** Google 문서는 "자주 바뀌니 **매일** 자동화"를 권하고, 팀은 월 1회 갱신에 90일 경고를 둔다. enforce에서는 Google 쪽 대역이 바뀌면 정상 Firebase 요청이 403이 된다. 덧붙여 Firebase Hosting의 접속 IP `199.36.158.100`은 goog.json에도 cloud.json에도 **없었다**. goog.json이 Google 인프라 전체 목록이 아니라는 뜻이다. B6 실측을 할 때 'log 모드에서 며칠 동안 `web_edge_unverified`가 0'을 enforce 전환 조건으로 문서화하고, 갱신 주기는 주 1회 이하로 줄이기를 권한다.
- **L5. 대역 파일이 깨지면 부팅 거부.** 스냅숏은 코드에 묶인 상수라 깨지면 빌드와 시험에서 먼저 드러난다. 새 리비전만 실패하고 이전 리비전이 남으므로 장애가 커지지 않는다. 다만 `off`일 때도 `checkRanges`가 던진다(부팅 거부). off인 개발 환경까지 막을 이유는 없으니 off에서는 건너뛰기를 고려한다.
- **L6. 마이그레이션 이름이 내일 날짜(`20261126…`).** 순서에는 문제가 없지만 오늘(11-25) 다른 마이그레이션이 추가되면 순서가 뒤바뀔 수 있다.

## 확인해서 맞다고 본 것

- **조회 합산 유실 0·중복 0**
  - 같은 id 재전송: 원래 시도가 서버에서 아직 실행 중일 때 재시도하면, `INSERT … ON CONFLICT DO NOTHING`이 상대 트랜잭션이 커밋할지 롤백할지 정해질 때까지 기다린다. 커밋이면 0을 더하고 롤백이면 반영한다. 둘 다 맞다. 표지·합계·만료가 한 문장이라 원자적이다.
  - 인스턴스 여럿: 묶음 id가 인스턴스마다 무작위이고 `count + n`으로 더하므로 합계가 맞다(시험이 3 인스턴스 × 5회로 확인).
  - 실패 중 새 실패: 대기 묶음은 합치지 않고 들고 있으며, 새 조회는 새 칸으로 간다.
  - 재시작과 SIGTERM: 문서에 적힌 손실 범위(강제 종료 때 메모리 분량)와 맞다. M1의 예외만 남는다.
- **개인정보**: 칸 키는 (UTC 날짜, 공개 코드, 이벤트)뿐이고 IP·요청 정보가 없다. `link_flush`는 무작위 id와 시각뿐이고, 로그에는 개수만 남는다. throttler 키는 `default:` + IP 접두(guard의 generateKey 재정의 확인)이고, 창 + 최대 10초 뒤 지워진다. web-edge 로그는 개수만 남긴다. **위반 없음.**
- **LRU 저장소**
  - 상한·축출: 20만 키에서 상한을 지키고, LRU 순서와 기본 저장소와 같은 막힘 뜻을 시험이 고정한다.
  - 90% 일괄 축출로 우회할 수 있는가: 활동 중인 키는 요청마다 맨 뒤로 가므로, 활동 중인 남용자의 카운터를 지우려면 그 사람의 요청 간격 안에 새 키 10만 개가 필요하다(초당 수만 건 이상). 실익이 없다.
  - 처리량: 일괄 축출은 상각하면 요청당 1µs 미만이다. 10초마다 하는 전체 쓸기는 10만 키 순회(수 ms)이고 그 시점의 요청 하나가 부담한다. 허용 범위다.
- **쿼리 제한 6초 + 소켓 폐기**
  - pg 8.23은 query_timeout 때 활성 쿼리를 큐에서 빼지 못한다(비 파이프라인). 그래서 소켓을 버리는 것이 맞다.

### 마이그레이션 순서

- main은 `…20261125000000_v25` → **`20261125120000_b7a`** 순서다. B6a worktree(`feat/b6a-supabase-storage`)는 `20261127000000_b6a_upload_tail` 하나를 추가하며, 내용은 `ALTER TYPE storage_gc_reason ADD VALUE 'upload_tail'`이다. 두 마이그레이션은 서로 다른 객체를 다뤄 의존이 없고, 이름 순서도 B7a → B6a라 **충돌이 없다.** 어느 쪽을 먼저 병합해도 폴더 순서는 같다.

### 새 지적

- **N1(중간, L3 반영이 만든 회귀). `idle_in_transaction_session_timeout` 10초가 30초 트랜잭션과 맞지 않는다.**
  - `page.service.ts`의 `COMMIT_TX`(timeout 30초)와 `moderation/name-mask.ts`의 `TX`(30초)는 트랜잭션 **안에서** 저장소 호출(`inspect` 읽기 셋, `store.move` 넷)을 하고, 그동안 DB 쿼리가 없다. 그 사이 세션은 'idle in transaction' 상태다.
  - 저장소가 느려 그 구간이 10초를 넘으면 DB가 세션을 끊는다. 바로 30초 예산을 둔 그 상황에서 게시(commit)와 이름 가리기가 실패하게 된다. DECISIONS의 근거 "대화형 트랜잭션 기본 5초보다 넉넉히"는 이 두 곳을 빠뜨렸다.
  - 권고: 값을 가장 긴 대화형 트랜잭션보다 길게 둔다(예: 35~40초, 두 TX 상수와 시험으로 묶음). 또는 연결 옵션에서 빼고 짧게 두고 싶은 경로에서만 `SET LOCAL`을 쓴다. 시험: '트랜잭션 안에서 DB 없이 12초 대기 → 커밋 성공'(시계는 줄여서).
- **N2(낮음). 종료 여유가 0.5초뿐이다.** 마감 8초 + `$disconnect` 1.5초 = 9.5초이고, 여기에 HTTP 서버 닫기(진행 중 요청 대기)가 더해진다. 마감 7초나 끊기 1초로 1초 이상 여유를 두는 편이 안전하다.
- **N3(낮음, 문서).** `idle_in_transaction_session_timeout`·`statement_timeout`을 시작 매개변수로 보낼 때 Supavisor 트랜잭션 모드가 이를 거부하면 **모든 연결이 실패**한다. B6 스모크(`/readyz`)에서 드러나겠지만, B6 체크리스트에 '풀러가 시작 매개변수를 받는지'를 명시하기를 권한다.
