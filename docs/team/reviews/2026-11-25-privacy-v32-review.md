## 2. 발견 사항

### 높음

**H1. 빌드 2(12-19)부터 앱이 서버로 보내는데, 그때 `/privacy`에 맞는 방침이 없습니다.** `store-listing.md:224·272`, `apps/web-static/scripts/site.mjs:351-380`, `build.mjs:511-519`

- **사실**
  - store-listing 7-0은 OTA 확인과 ML Kit 진단을 `[빌드 2]`로 표시합니다. 모든 설치자에게서 보낸다는 뜻이고, 로드맵 V2도 빌드 2입니다.
  - 7-1·7-3은 빌드 2 제출 전에 Data safety를 '수집 예'로 바꾸고 방침 URL을 넣는다고 적습니다.
  - 그런데 PM 11-25 결정에 따라 지금 `/privacy`는 '출시 전 개인정보 안내'입니다. 이 안내는 '지금 받는 것 = 테스트 신청 메일뿐'이라고 말합니다.
  - 전체 방침은 `SITE_MODE=launch`에서만 렌더되고, `[ ]` 메모가 하나라도 있으면 빌드가 실패합니다. 지금 ko·en 각 25곳입니다. 그중 B6 실측(K6·K17·K26)과 12-05 법률 회신에 달린 메모는 12-19 전에 다 지우기 어렵습니다.
- **문제**
  - 빌드 2 테스터 기기는 IP·업데이트 요청을 보내고, ML Kit 진단(설치별 식별자 포함)이 Google로 갑니다. 그런데 공개된 안내는 '메일뿐'이라고 말해 **사실과 다릅니다.** 이는 Google Play 사용자 데이터 정책의 '처리방침이 앱의 수집·공유를 포괄적으로 공개' 요건과, 「개인정보 보호법」 제30조(처리방침 공개)에 걸립니다.
  - 메모를 서둘러 지워 출시 모드를 통과시키면, 출처 없는 문장이 게시되는 반대 위험이 생깁니다.
- **고칠 안**(PM·오너가 고름)
  - ① 빌드 2 전에 '테스트 빌드용 방침'을 만듭니다. 3-2·3-3·4·7·8·17절만 확정 문구로 두고 출시 모드로 게시합니다. 빌드 2에 실제로 켜진 기능만 적습니다.
  - ② 출시 전 안내에 '테스트 앱이 보내는 것(업데이트 확인·ML Kit 진단)' 절을 더합니다.
  - 어느 쪽이든 7-3 순서표에 '12-19 전 게시본 = 무엇'을 한 줄 박습니다.
- 출처: [Play User Data 정책](https://support.google.com/googleplay/android-developer/answer/10144311), [Data safety 양식 안내](https://support.google.com/googleplay/android-developer/answer/10787469)

### 중간

**M1. 6절 '2년보다 늦어질 수는 있어도 빨라지지는 않습니다'(210, en:157)와 PIA R13 '2년 전엔 절대 안 지움'(`pia-quebec.md:198`)은 코드가 보장하지 못하는 절대 표현입니다.**

- 활동 달 갱신은 실패해도 요청을 그대로 통과시킵니다(`activity.ts:33-35`, 경고 로그만 남김). 그 달 마지막 요청의 갱신이 실패하고 같은 달에 다른 요청이 없으면, 저장된 활동 달이 실제보다 앞섭니다. 그러면 **최대 한 달 일찍** 대상이 됩니다.
- 시계 차단기 ②는 '2달 **넘게**' 앞설 때만 멈춥니다(`inactive-sweep.ts:28·103`). 서버 시계가 1~2달 앞으로 튀면 경계에 있는 계정이 일찍 지워질 수 있습니다.
- 둘 다 드문 경우이지만 되돌릴 수 없는 삭제이고, 이 문장은 정보주체에게 한 약속입니다. 문구를 좁히거나 코드를 고칩니다.
  - 문구 안: '마지막 이용 달 뒤 2년이 지나야 대상이 되며, 하루 상한·멈춤 장치 때문에 그보다 늦어질 수 있습니다'.
  - 코드 안 1: `touch` 실패 시 그 요청을 5xx로 돌려 앱이 다시 시도하게 합니다.
  - 코드 안 2: 대상식을 `< 이달 − 25개월`로 한 달 여유를 둡니다.
- 문구를 고치면 PIA R13도 함께 고칩니다.

**M2. 밥 알림 '예약하거나 보낸 기록은 저장하지 않고'(259, en:206 'No record of scheduling or sending is kept')와 store-listing 7-0의 '예약·발송 기록 0'(209)은 기기 안 사실과 다릅니다.**

- 앱 세이브에 남기지 않는 것은 맞습니다(D-27).
- 그러나 Android expo-notifications는 예약된 알림(울릴 시각·문구)을 재부팅 복구용 SharedPreferences에 둡니다(care-rituals 85·105행, QA-3 R1).
- 울린 알림은 앱을 열 때까지 알림 센터와 잠금 화면에 남습니다.
- 울릴 시각은 '그 깸에 한 마디를 썼는가'에 따라 달라집니다. 그래서 OS 예약에 '썼다/안 썼다' 한 비트가 기기 안에 잠시 남습니다. 위기와는 무관합니다(대조군 7종이 같은 시각을 보장합니다). 흔적 0 원칙상 문제는 아니지만, 방침이 '저장 0'이라고 쓰면 넓게 쓴 것입니다.
- 고칠 문구: '예약은 울리거나 취소될 때까지 기기의 알림 예약에만 있고, 게임 기록에는 남기지 않습니다. 울린 알림은 앱을 열면 치웁니다. 서버나 이용 통계로 보내지 않습니다'.
- K34 증거 칸에 'Android 자동 백업 제외 규칙에 예약 저장소 포함(지금 권고 → 필수 검토)'을 더합니다. 백업에 들어가면 예약 한 건이 Google 계정 백업으로 나갑니다(10절과도 이어짐).

**M3. 클라우드 접속 기록 항목에서 User-Agent가 빠졌습니다.**

- 해당 위치: 3-1 120(en:67), 3-2 131, 6절 205(en:152), 8절 Cloud Run 행 235(en:182).
- 방침은 접속 기록을 'IP 주소·요청 경로·시각'으로 적습니다. 그러나 Cloud Logging의 요청 로그 `httpRequest` 형식에는 `userAgent`·`referer`·`latency`·`responseSize`도 있고, Cloud Run 요청 로그는 이 칸을 채웁니다.
- 3-2는 UA가 요청에 실린다고 이미 적었으므로, 저장되는 기록에도 같은 항목을 씁니다.
- 고칠 문구: 'IP 주소·User-Agent·요청 경로·시각 등'. K6 증거(B6 실측)에 '요청 로그 한 건 원문 캡처'를 더합니다.
- 출처: [LogEntry HttpRequest 형식](https://cloud.google.com/logging/docs/reference/v2/rest/v2/LogEntry#HttpRequest) [B6 실측으로 확정]

**M7. 아동(만 14세 미만): 법정대리인 동의 구조는 맞지만, 남은 쟁점 두 가지가 방침과 스토어 문구에 드러나지 않습니다.**

  - OTA는 설치 id를 상수로 덮었으므로, 14세 미만에게서 근거 없이 나갈 수 있는 것은 사실상 ML Kit 진단뿐입니다(설치별 식별자, Google 자체 목적).

## 3. 지시 항목별 답

1. **문구와 동작**: OTA 식별자 고정값은 코드와 네이티브 적용 순서까지 **일치**합니다(1절 #1·#2). '늦어질 수는 있어도 빨라지지 않음'은 **과장**입니다(M1). 밥 알림 '기록 저장 0'은 세이브 기준으로는 맞지만 기기 OS 예약과 알림 센터를 빠뜨렸습니다(M2).
2. **14절·8절 국외 이전**: 제2항 1·3·4·5호는 충족합니다. 2호(국가)는 경유 거점을 특정하지 못했고, 14절과 8절 Supabase 행이 서로 맞지 않습니다(M4).
3. **아동**: 통계 opt-in을 14세 확인 뒤에 둔 설계는 법정대리인 동의가 필요 없는 구조로 맞습니다. 남은 위험은 ML Kit 진단의 법적 성격과 쉬운 고지입니다(M7).
4. **ko·en**: v3.2에서 바뀐 문장(1·2·3-2·3-5·6·8·11·14·18·변경 이력)의 의미는 같습니다. L1~L3·L5는 두 판에 똑같이 있으니 함께 고칩니다. ko에만 있는 '상호' 줄은 v3.1부터 있던 차이입니다.
5. **게시 차단 장치**: 출시 모드 검사가 'B4 커밋 뒤 대조'를 `[ ]` 메모로 잡습니다. ko·en 각 25곳을 시뮬레이션으로 확인했고, 상자 제거 뒤 K행 0개, 작업 메모 '초안'·'draft' 탐지도 됩니다. 빈틈은 두 가지입니다. B4가 바꾸는 3-3에 표시가 없고(M5), K 정규식이 낡았습니다(L4). 또 이 장치는 일정상 빌드 2 게시를 막는 쪽으로 작동합니다(H1).
6. **스토어 데이터 안전**: 공식 정의와 대조했습니다.
   - Play 정의: 수집은 '기기 밖으로 전송', 기기 안 처리는 공개 대상 아님, 서비스 제공자·사용자 주도 전송은 공유 아님, SDK 전송도 공개 대상.
   - 이에 따라 다음 답은 맞습니다. 밥 알림과 마실은 '새 유형 없음'(기기 안 처리), OTA 때문에 Device ID·Crash를 선언하지 않는 것(상수로 덮어 식별자를 보내지 않음), ML Kit 근거로 Device ID와 진단은 '수집·필수·공유 아님'.
   - Apple 'Linked' 판단은 M6에서 다시 봅니다.
   - 출처: [Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469), [Apple App Privacy](https://developer.apple.com/app-store/app-privacy-details/)
