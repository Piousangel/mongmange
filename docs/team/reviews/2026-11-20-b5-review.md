## 2. 신고 남용(볼 것 1)

### C1 — Origin 검사가 진짜 브라우저를 막는다(치명)
- 사실: `/m` 응답 헤더가 `referrer-policy: no-referrer`(`app.factory.ts:22`)이고, 페이지 안에도 `<meta name="referrer" content="no-referrer">`(`m-html.ts:160`)가 있다. Fetch 표준의 'Origin 헤더 붙이기'에 따르면 GET·HEAD가 아닌 no-cors 요청은 referrer policy가 `no-referrer`일 때 Origin을 `null`로 직렬화한다.
- 측정: 같은 헤더·메타와 `form-action 'self'`를 둔 최소 페이지에서 같은 출처 폼을 제출하면, 서버가 받은 값은 `origin="null"`, Referer 없음이었다(Chrome for Testing 159.0.8154.6).
- 결과: 폼은 `origin !== siteOrigin`이라 403이 된다(`m.controller.ts:146`). 링크 손님은 앱이 없어 웹 폼이 사실상 유일한 신고 길이므로, 신고 기능이 웹에서 통째로 죽는다. 시험(`b5.db.test.ts:140`)과 CI 스모크는 Origin을 손으로 넣거나 빼기만 해서 이 문제를 잡지 못한다.
- 권고(택1·조합):
  1. `Sec-Fetch-Site`를 1차 판정으로 쓴다. `same-origin`이면 통과, `cross-site`·`same-site`면 403, 헤더가 없으면(옛 브라우저) Origin이 사이트와 같거나 `null`일 때만 받는다. `null`을 받으면 샌드박스 iframe 자동 제출 구멍이 남으므로, 옛 브라우저용 예외로만 둔다.
  2. 또는 `/m` 페이지의 referrer policy를 `same-origin`으로 바꾼다. 스토어 링크는 이미 `rel=noreferrer`라 밖으로 나가는 코드 누출은 없다. 다만 정본(5-2 '링크 주소가 밖으로 안 나감')과 B3 리뷰 결정을 다시 확인해야 한다.
  3. 실제 브라우저(Playwright) e2e 하나를 CI에 둔다. 폼 클릭 → 303 → 신고 행 1이 나오는지 본다.
- 작성자 결정 ③(같은 출처 Origin 제한) 판정: **방향은 타당**하다. 남의 사이트 자동 제출은 방문자마다 IP가 달라 3명 문턱을 공짜로 넘기는 실제 공격이고, 정본에 없던 좋은 보강이다. **구현은 실패**했다(C1). JSON 쪽은 전역 CORS가 없어서 다른 출처 브라우저는 사전 요청에서 막힌다. `text/plain` 415, 다른 경로 폼 415도 확인했다(`app.factory.ts:56-62`). Origin이 없는 JSON은 curl과 같으므로 레이트 리밋 말고는 막을 수 없고, 이것은 정본이 받아들인 범위다.

### H2 — 문턱 우회 비용과 되돌림
- IPv6: 신고 키가 /64다. 흔한 VPS는 /48·/56을 주므로 서로 다른 /64 3개를 얻는 비용이 0이다. IPv4 프록시 3개도 거의 무료다. 정본 3-8 '한계'의 '다른 회선·VPN을 쓰는 세 사람'보다 훨씬 싸다. 모바일 CGNAT은 진짜 신고자가 1로 묶이는 쪽이라 안전한 방향이다.
- 5/시간 레이트 리밋은 같은 접두에만 걸리므로 이 공격에는 소용이 없다.
- XFF: `TRUSTED_PROXY_HOPS_WEB`이 실제보다 크면, 공격자가 맨 왼쪽 XFF로 신고자 키를 마음대로 만든다. 그러면 한 사람이 요청 3번으로 아무 페이지나 숨긴다. 정본 L5 ⑤·#26대로 **B6 측정 전에는 신고를 켜지 말 것**(출시 차단 조건으로 명시 권고).
- 되돌림: `restore_page` 뒤 새 신고는 새 행·새 소금으로 다시 3명부터 센다. 같은 공격자가 곧바로 다시 숨길 수 있고, 운영자가 30일을 놓치면 `expire_quarantine`이 확정 삭제한다(`migration.sql:259-275`). 확정은 파일 삭제라서 `reopen_page`로도 판은 돌아오지 않는다.
- 권고:
  ① 신고 키만 IPv6 /48(또는 /56)로 접는다(레이트 리밋은 /64 유지).
  ② 최근 N일 안에 `restored`된 대상은 자동 숨김 대신 대기 목록에만 올린다(면역 창).
  ③ 서비스 전체 차단기: 1시간 자동 숨김이 K건을 넘으면 자동 숨김을 멈추고 `report_auto_hidden_burst` error 알림.
  ④ 30일 기본 확정 전 마지막 알림(예: 25일 error)을 SLA 알림과 별도로 둔다.
  ①~③은 각각 반나절 안팎 규모다. 정본 3-8 '한계' 문구를 실제 비용에 맞게 고칠 것.
- 7일 창: 서비스 창 판정(`report.service.ts:45-47`, `<= now`)과 만료 함수(`+10분`)가 다르지만 둘 다 7일 안이라 개인정보 쪽 문제는 없다.

## 3. 개인정보(볼 것 2)
- 신고자 키: HMAC-SHA256(대상별 소금 32바이트, IP 접두)이다. 소금이 대상마다 달라 대상 간 연결이 안 된다(시험 322줄). 소금은 열린 행에만 있고(CHECK), 닫힐 때 트리거가 키를 지운다. 트리거 본문을 빼는 변이는 시험 4건이 잡았다. 평문 IP가 표·로그에 없는 것도 시험이 고정한다. 소금이 살아 있는 7일 동안은 IPv4 전수 대입이 가능한데, 이는 정본과 처리방침에 그대로 적혀 있다. **양호.**
- 10분 일찍: 창(`expire_reports`)과 격리(`expire_quarantine`)의 경계 변이를 각각 시험이 잡았다. 남은 문제는 L2(DST 세션)다. Supabase 기본 UTC·KST에는 해당이 없다. `interval '720 hours'`로 쓰거나 함수에 `SET timezone = 'UTC'`를 두면 없어진다.
- 감사 기록: `delete_account`는 코드 없이 메모만 남긴다. 메모가 자유 글이라 운영자가 이메일을 적을 위험이 있다(런북 경고뿐, L5). `CHECK (note !~ '@')` 정도의 기계 검사를 권고한다.
- 처리방침 숫자: 3명·7일·30일·1년·사유 코드·글 칸 없음은 코드·계약 상수와 맞다. 어긋나는 곳은 M2(1년 초과 행)와 M5(메모리 '약 1분')다.
- M5 판단: 고치는 것을 권고한다. ① `take()`에서 N번마다 또는 1분 타이머로 **각 창 자신의 `windowMs` 기준**으로 만료 창을 지운다(창마다 windowMs 저장). ② 처리방침 53·88줄을 '최대 1시간(일부 한도는 하루)'으로 고친다. 둘 다 해야 맞다. 키가 IPv4 평문 접두이고 신고 창 이름(`m_report`)이 붙어 있어 '이 IP가 최근 신고했다'는 정보가 메모리에 남는다. 다만 대상은 남지 않는다.

## 4. SQL 함수(볼 것 3)
- 9개 운영 함수와 보조 함수 모두 SECURITY INVOKER다. 동적 SQL(`EXECUTE format`)이 없고, 텍스트 인자는 `mod_code` 정규식으로 8자 Crockford만 통과하므로 **SQL 주입 없음**. RLS 우회는 호출 롤 권한 그대로라 범위가 넓어지지 않는다.
- PUBLIC EXECUTE 회수: 지금 DB에서는 anon·authenticated EXECUTE가 없다(확인). 하지만 ① 회수 문장을 빼도 120개 시험이 모두 통과한다(L1 — `has_function_privilege('anon', …)`·PUBLIC 단언 추가 권고). ② `ALTER DEFAULT PRIVILEGES IN SCHEMA app REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`이 없어서 앞으로 만들 함수마다 다시 회수해야 한다. anon에게 `app` USAGE가 없어 지금 당장 뚫리지는 않는다.
- M4 Studio 롤: ACL이 `prisma=X/prisma`뿐이다. 런북은 Studio(`postgres`)에서 실행한다고 하는데, 시험은 소유자 `prisma`로만 돈다. 운영 Supabase의 `postgres`가 `prisma` 멤버인지, BYPASSRLS인지 검증된 적이 없다. 실패 방향은 대체로 안전하다(권한 오류, 또는 RLS로 0행이면 `mod_creature_id`가 '없습니다'로 멈춤). 예외는 `request_account_deletion`으로, UPDATE 0행이어도 `queued`와 기록을 남긴다(`migration.sql:238`). 권고: 운영자 롤을 정해 `GRANT EXECUTE`(또는 SECURITY DEFINER + `SET search_path = pg_catalog, app` + 그 롤에만 EXECUTE)하고, 시험에 비소유자 운영자 롤로 스니펫을 돌리는 경우를 하나 둔다. `request_account_deletion`은 ROW_COUNT가 0이면 오류를 내게 한다.
- 잘못된 대상을 처리했을 때 되돌림:

| 함수 | 되돌림 |
|---|---|
| `restore_page` | `confirm_hide` |
| `confirm_hide` | `reopen_page`. 파일은 영구 손실 |
| `dismiss_report` | 없음. 신고자가 다시 신고 |
| `mask_name` | `unmask_name`. 단 `name_visible=false`와 판이 바뀌어 주인이 다시 만들어야 함 |

## 5. 이름 가리기(볼 것 4)
- `name_blocked` 뒤 공개 경로를 확인했다.
  - SQL 즉시: `name_shown=false`, `meta - 'name'`, `ogPoster`가 들어간다. HTML title·og:title·h1에서 이름이 사라지고 og:image는 포스터가 된다.
  - 작업 뒤: 새 pageKey에 이름 없는 snap이 쓰이고 옛 폴더는 지워진다. 커밋 전 판과 지난 판도 지금 지운다.
  - 격리 중에 가리면 격리본을 이름 없이 다시 쓰고, 복원하면 이름 없는 판이 돌아온다.
  - 시험이 DB·HTML·세 버킷 파일 바이트에서 이름 0을 확인한다(575~672줄).
- 주인 우회:
  - PATCH: 같은 UPDATE 문에 조건이 있다(`page.service.ts` patch).
  - PUT: 잠근 행에서 확인한다. 이 줄을 빼는 변이를 시험이 잡았다.
  - commit: `mask_name`이 pending을 비운다.
  - 재가입: 새 코드라 `name_blocked`가 따라오지 않는다. 같은 이름을 다시 쓰는 것은 금칙어 목록이 막아야 한다. 정본 범위 안이다.
- **B3 M2 시험 유지 확인**(`b3.db.test.ts:672` '이름의 문은 name_shown 하나'. 바뀐 것은 `nameBlocked` 필드 단언 1줄).

- 의존 불변식: 이름 뺀 판은 poster·loop를 **그대로 복사**한다(`name-mask.ts:50-54`). 앱(C1-M2·C10)이 포스터나 8초 루프에 이름 글자를 그리기 시작하면 가리기가 새어 나간다. 지금 diff는 인장 외곽선(`sealOutlineOf`)만 그린다. contract 또는 architecture 3-5-2에 '포스터·루프에 이름 픽셀 금지'를 불변식으로 적어 둘 것.

## 6. 금칙어 로더(볼 것 5)
- 정규화 접기: 항목과 이름 모두 `normalizeName` → 소문자 → `[\s·]` 제거로, 같은 함수 `foldName`을 쓴다. **일관됨.**
- 우회: `normalizeName`이 한글 완성형·ASCII 라틴·숫자·공백·가운뎃점만 허용하므로 동형 문자(키릴), 자모 분리(ㅅㅂ), 전각은 **이름 단계에서 이미 거부**된다. 남은 우회는 숫자·라틴 끼워 넣기와 발음 변형이다(L4). 권고: 비교 키에서 숫자도 지운 '느슨한 키'를 부분 일치에 하나 더 둔다. 오탐은 `=` 항목으로 조절한다.
- 기동 실패 정책: 잘못된 항목이 있으면 모듈을 읽을 때 throw하고, 오류 문구에 원문을 싣지 않는다. 목록 편집 실수가 배포 실패로 드러나는 쪽이 조용히 못 거르는 것보다 낫다. **타당.** 단 CI에 금칙어 목록 컴파일 시험이 있어야 배포 전에 잡힌다. `name-blocklist.test.ts`가 `NAME_BLOCKLIST`를 import하므로 충족.
