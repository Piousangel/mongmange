**Cloud Run 1 vCPU로 옮길 때의 한계 [팀 추정]**
1. CPU: 로컬 1코어(Apple Silicon, CFS 쿼터)와 Cloud Run 1 vCPU(서버 CPU의 하이퍼스레드 하나)는 단일 스레드 성능이 다르다. **처리량 한계는 ÷2~3으로 본다.**
2. DB 왕복: 로컬은 0.1~0.3ms. Cloud Run 서울 → Supabase 풀러(6543)는 쿼리당 **1~3ms [확인 필요: B6 실측]**. 비콘은 쿼리 2번 + 커밋 1번이라 영향이 가장 크다.
3. 앞단 없음: TLS·Google 프런트엔드·Firebase CDN이 없다. CDN은 `cdn-sim.mjs`로 흉내만 냈다(엣지 수·요청 합치기·stale 처리는 실제와 다를 수 있음 [확인 필요]).
4. 요청 기반 과금의 CPU 조절: Cloud Run은 요청 밖에서 CPU를 거의 주지 않는다 → 레이트 리밋 쓸기 타이머(10초·60초)가 늦게 돌 수 있다. 메모리 수치(4절 B2)는 **더 나빠지는 쪽**이다.
5. 콜드 스타트: 로컬은 컨테이너 시작 → `/healthz` **1.6초**, 첫 `/m` 0.29초(DB 연결). Cloud Run은 여기에 인스턴스 할당·이미지 적재가 더해진다 → L2는 B6 뒤 실측.

## 2. 피크 계수 — 링크 하나 하루 10만 조회

- 하루 평균: 100,000 / 86,400 = **1.16 rps**.
- 입소문 링크는 하루에 고르게 오지 않는다. 가정 [팀 추정]: 큰 단톡방·SNS에 퍼진 **첫 1시간에 하루치의 30%**(→ 시간 평균 8.3 rps), 그 시간 안 **가장 붐비는 1분은 시간 평균의 5배**(공유 직후 몰림) → **약 42 rps**.
- 여유를 두어 **목표 60 rps(일 평균의 약 52배)** — architecture 7절 L1의 '순간 60 rps 10분'과 같은 값이다. 한계는 closed 방식으로 따로 찾았다.
- 조회 한 번이 Nest에 닿는 요청: **HTML은 CDN 미적중일 때만**, 하지만 **`POST /m/{code}/seen` 비콘은 매번**(no-store, `sendBeacon` — m-html.ts 78행), 스토어 이동 `/get`은 누른 사람만(5% 가정).
  → 피크 60 rps 조회 = **Nest 약 63 rps**(비콘 60 + `/get` 3 + HTML 미적중 엣지당 5분에 1번).

## 4. 병목·결함 (보고만 — 코드 수정 없음)

| # | 심각도 | 무엇 | 근거 | 제안(담당) |
|---|---|---|---|---|
| **B1** | 중요 | **조회 비콘은 CDN을 타지 않는다** → 링크 조회 1번 = Nest 요청 1번 + DB 쿼리 2번(live 확인 SELECT + `link_daily` UPSERT 커밋). architecture 3-9의 'CDN 미적중이 12배 늘어도 Nest 요청은 분당 수 건'은 **HTML만 센 값**이고, 실제 피크는 **약 63 rps**(2절). 비콘은 HTML 미적중과 **같은 풀 5개**를 쓰므로, DB가 느려지면 비콘이 풀을 먼저 채우고 **조회수가 소리 없이 빠진다**(300ms에서 96% 손실). L1 기준 '`link_daily` 합계 오차 < 1%'는 DB가 느린 순간 깨진다 | 3-1 혼합, 3-3 비콘 300ms | 정본이 처음 말한 **'메모리 합산'**으로: 비콘은 인스턴스 메모리 `Map<code,count>`에 더하고 10~30초마다 한 번 UPSERT + SIGTERM flush(B0 `metric-aggregator`와 같은 구조). | B6 | 관찰 | DB 왕복 300ms면 인스턴스 하나의 `/m` 처리량이 약 17 rps로 떨어진다(풀 5 ÷ 0.3초). CDN 앞단이 있으면 HTML 미적중은 몇 건뿐이라 영향은 주로 비콘(B1)이다 | 3-3 | B1을 고치면 해소. 풀을 키우는 것은 Supavisor 연결 수(5 × max 3 = 15)와 같이 본다 |

확인된 좋은 점: 같은 행 UPSERT에서 합계 손실 0(680 rps까지), DB 장애 때 503 no-store(거짓 '사라짐' 없음), `/healthz` DB와 분리, `/readyz` 1.5초에 503, 멈춤 해제 즉시 회복, 레이트 리밋 한도는 정본 표와 모두 일치.

|---|---|---|---|
| `--concurrency` | 40 | **40 유지** | 로컬 한계에서 동시 40의 p95가 39ms(HTML)·134ms(비콘). DB 풀이 5라 더 올려도 풀 대기만 길어진다. 피크 63 rps는 인스턴스 하나 환산 한계(HTML 900~1,400·비콘 250~350 rps)의 **약 20~25%** |
| `--min-instances` | 소프트런칭 0, 정식 출시 주 1 | **그대로** | 링크 HTML은 CDN이 콜드 스타트를 가린다. 비콘은 `sendBeacon`이라 사용자가 기다리지 않는다. 정식 출시 주에는 핑 폭주(L3) 때문에 1 |
| `--max-instances` | 3 | **3 유지** | 처리량은 1개로도 남는다. 3은 비용·DB 연결(5 × 3 = 15) 상한. 단 B2를 고치기 전에는 OOM이 연쇄할 수 있다 |
| `--timeout` | (기본 300초) | **60초** | 정상 요청은 수 ms~수백 ms. B3 같은 멈춤이 슬롯을 5분씩 잡지 않게. 자체 OTA 에셋을 같은 서비스가 내면(V21) 느린 회선의 큰 에셋이 60초를 넘을 수 있다 → **B6에서 가장 큰 에셋 × 느린 회선으로 확인 [확인 필요]**, 넘으면 OTA만 별도 서비스·CDN |
| `--memory` | 512Mi | **B2 고치기 전 1Gi, 고친 뒤 512Mi** | 정상 피크는 200MiB 안팎. 1Gi는 min 0에서 요금 차이가 거의 없다 [팀 추정] |
| `--cpu` / `--cpu-boost` | 1 / 켬 | 그대로 | 콜드 스타트 단축 |
| 프로브 | startup·liveness = `/healthz` | 그대로(DB를 보지 않는 것이 맞다) | B3은 프로브가 아니라 쿼리 제한 시간으로 푼다 |
| 앱 환경 변수 | `DB_POOL_MAX=5`, `DB_CONNECT_TIMEOUT_MS=1500`, `DB_STATEMENT_TIMEOUT_MS=5000` | 그대로 + B3의 `query_timeout` | 3-3에서 1.5초 빠른 실패가 줄을 막아 주었다 |

## 6. 업타임 점검·알림 설계 (연결은 B6 뒤)

**점검(Cloud Monitoring 업타임 체크, 3개 지역 이상)**

| # | 대상 | 주기 | 통과 조건 | 알림 조건 | 무엇을 잡나 |
|---|---|---|---|---|---|
| U1 | `https://mong-api-…run.app/healthz` | 1분 | 200 + 본문 `"ok":true`, 10초 안 | **2개 지역 이상에서 연속 2회 실패**(약 2~3분) | 인스턴스·배포 실패 |
| U2 | 같은 서비스 `/readyz` + 머리글 `x-ready-token`(Secret Manager 값) | 5분 | 200 `"db":"up"` | 연속 2회 실패 | DB·풀러 단절(U1은 DB를 안 본다) |
| U3 | `https://mongmang.ink/m/TESTTEST`(B6 시드 링크) | 5분 | 200 + 본문에 앱 이름 | 연속 2회 실패 | Firebase rewrite → Cloud Run → DB 전 경로. DB가 없으면 503이라 여기서 잡힌다 |
| U4 | `https://mongmang.ink/.well-known/apple-app-site-association`, `/.well-known/assetlinks.json` | 15분 | 200 + `application/json` | 1회 실패 | 딥링크가 조용히 깨짐 |
| U5 | `https://mongmang.ink/config/v1.json` | 15분 | 200 + JSON 파싱 | 1회 실패 | 원격 플래그(앱은 번들 기본값으로 계속 동작 — 급하지 않음) |
| U6 | 자체 OTA 매니페스트(`/api/v1/ota/manifest`, V21 확정 경로) | 15분 | 200 또는 204(업데이트 없음) | 연속 2회 실패 | OTA 배포 서버 |

- U1의 1분 점검은 min 0에서 인스턴스를 데우는 효과도 있다(요청 기반 과금이라 비용은 작다 [팀 추정]). U3 등 `/m` 점검은 비콘을 부르지 않으므로 조회수에 섞이지 않는다.

**지표·로그 알림**

| 신호 | 조건 | 등급 |
|---|---|---|
| Cloud Run 5xx 비율 | 5분 동안 > 2% | 경고 |
| 로그 `m_db_unavailable` | 분당 > 10, 5분 | 경고(3-3: DB 장애 때 503마다 한 줄) |
| 지연 p95(`/m/:code`·`/api/v1/*`) | 10분 동안 > 1초 | 경고 |
| 인스턴스 수 | = max(3) 10분 | 경고(포화 — B2 공격이나 B1 폭주) |
| **컨테이너 메모리 사용률** | > 80% 5분 | **긴급**(B2 OOM 전조) |
| 컨테이너 재시작·OOM | 1회 | 긴급 |
| 기존 항목(B2·B3·B5 체크) | `gc_stuck`·`report_auto_hidden_burst`·`moderation_sla` 등 error 로그 | 각 정의대로 |
| 예산 | GCP 30·60·120달러, Firebase 전송량(3-8) | 알림만 |

- 알림 채널: 오너 이메일 + 개인 슬랙 워크스페이스(회사 슬랙 아님) [확인 필요: Cloud Monitoring 슬랙 채널 연결]. 긴급은 둘 다, 경고는 슬랙만.
- 업타임 체크 무료 한도·`x-ready-token`이 체크 설정에 평문으로 남는 문제(프로젝트 편집자에게 보임) [확인 필요] — 남으면 U2를 토큰 없는 별도 내부 경로로 바꾸는 대신 **토큰을 업타임 전용 값으로 따로 발급**한다.

## 7. 스테이징 환경 계획

| 항목 | 계획 |
|---|---|
| 구성 | Supabase `mong-staging`(Free, 서울) + Cloud Run `mong-api-staging`(같은 이미지, `--min-instances=0 --max-instances=1`, 512Mi) + Firebase 스테이징 사이트(`/m/**` rewrite 같은 규칙) |
| 배포 | `main` 머지 → CI가 이미지 빌드 → **스테이징 자동 배포** → 스모크(`/healthz`·`/readyz`·`/m/TESTTEST`·`.well-known`) → 운영은 같은 이미지 다이제스트를 손으로 승격 |
| 데이터 | **시드만**(`seed` 스크립트 + B7 `seed.sql` 같은 고정 코드). 운영 데이터·백업을 넣지 않는다(3-8 '백업' — Free·넓은 접근·지운 사용자 부활). 복원 리허설은 **새 임시 프로젝트**에서 하고 바로 지운다 |
| 비밀 | 운영과 **다른 값**(`READY_TOKEN`·`RECOVERY_PEPPER`·서비스 롤 키·서명 키). 서명 키는 시험용 키 쌍 |
| 환경 차이(알고 쓰기) | Free라 Smart CDN·일일 백업·PITR 없음 → **Q12(약 1분 숨김) 검증은 운영 설정에서**(3-9). 일시 정지(7일 무활동) [확인 필요] → 시험 전날 깨우기. 컴퓨트가 작아 부하 수치는 운영보다 나쁘게 나온다 — **상한 검증이 아니라 경계·모양 검증**에 쓴다 |
| 쓰임 | B7 12월분(L2 콜드 스타트, L4 축소, L5 우회 5종, L6 느린 서버 — 앱 C13과), XFF hops 실측 고정물, Firebase `Cache-Control` 보존 확인(B3 리뷰 I3), 운영 전환 리허설 |
| 앱 연결 | 개발 빌드·`preview` 채널은 `EXPO_PUBLIC_API_BASE`=스테이징. 운영 빌드에 스테이징 주소가 들어가지 않게 빌드 검사 |
| 비용 | Cloud Run·Firebase 무료 한도 안, Supabase Free → 0~1달러/월 [팀 추정] |

## 8. B6 뒤 할 일

1. **B3 확인 후 이 보고의 B1~B5를 담당에게 넘기고**, 고친 뒤 시나리오 1·3·4·5를 다시 돌린다(`scenarios.sh`).
2. 스테이징에서 실측으로 바꿀 것: Supabase 풀러 왕복(쿼리당 ms), 인스턴스 하나의 `/m`·비콘 한계(1절 ÷2~3 환산 검증), **L2 콜드 스타트 10회**(20분 유휴 → 첫 응답 < 3초), Firebase가 `/m` 429·503에 캐시를 거는지.
3. **XFF hops 실측**(B5 체크·출시 차단 조건) — 틀리면 3-2 마지막 줄처럼 모든 방문자가 한 키가 되어 비콘이 분당 30건만 세진다. `*.run.app` 직접 호출 차단 여부를 B2와 함께 결정.
4. 업타임 체크 U1~U6·알림(6절) 등록, 알림 채널 시험 발송.
5. Cloud Run 설정 반영(5절): `--timeout=60`(OTA 에셋 확인 뒤), 메모리(B2 상태에 따라).
6. `run.mjs` 허용 목록에 **스테이징 호스트 하나만** 추가(별도 리뷰), 12월 L2·L4·L5·L6 실행 → 결과는 `docs/ops/loadtest/YYYY-MM-DD.md`(정본 7절).
7. 01월 L1·L3(운영 설정 min 1) — 이 보고의 2절 피크 계수와 3-1 혼합 시나리오를 실제 CDN으로.
8. 복원 리허설 1회(임시 프로젝트, `reapply-deletions` 한 바퀴 — 0-3 B7 관찰 항목).
